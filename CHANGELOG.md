# Changelog

Notable changes to understudy, in the form of [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions follow [Semantic Versioning](https://semver.org/); before 1.0 a minor version may break compatibility. A release's GitHub notes are its section here: `release.yml` refuses a tag without one.

## [Unreleased]

### Added

- `lambda.hotReloadRoots` in the configuration file lists the directories a hot-reload binding made through the admin API (`understudy lambda hot-reload`) may come from. With it set, a directory that does not resolve, after symbolic links, to one of them or a directory below one is refused with `invalid_request` on `dir`, naming the setting and the resolved path, and nothing is bound; the absolute-path, directory and owner checks still apply. Left out, any directory the user running understudy owns binds, as before. Bindings under `lambda.hotReload` are not checked. SECURITY.md names it as the control on hosts with other local users, who on loopback can otherwise bind the understudy user's home directory and read it from a function.
- SES identities can carry a default configuration set: v2 `CreateEmailIdentity` takes `ConfigurationSetName` (it must name an existing set; it no longer answers 501), `GetEmailIdentity` returns it, and `PutEmailIdentityConfigurationSetAttributes` sets or clears it, so `aws_sesv2_email_identity` with `configuration_set_name` applies. A send naming no set records its sender identity's default when that identity is verified, an address's default over its domain's; a set named in the request or `X-SES-CONFIGURATION-SET` always wins. v2 `PutEmailIdentityDkimSigningAttributes` is stored only and changes no DKIM status. A default naming a deleted set applying nothing, and the missing-identity and missing-set answers, are inferred.
- SES account sending can be paused: v1 `GetAccountSendingEnabled` and `UpdateAccountSendingEnabled` work per account and Region, and v2 `GetAccount` reports `SendingEnabled` from the setting. While sending is paused every v1 and v2 send fails with `AccountSendingPausedException` (v2: `SendingPausedException`) after the configuration-set check and before the sender check. The message text and the check's position are inferred.
- SES configuration sets: v1 `CreateConfigurationSet`, `DescribeConfigurationSet`, `DeleteConfigurationSet`, `ListConfigurationSets` and v2 `CreateConfigurationSet`, `GetConfigurationSet`, `DeleteConfigurationSet`, `ListConfigurationSets` (both bindings) work over one store per account and Region, at most 10,000 sets, so `aws_ses_configuration_set` and `aws_sesv2_configuration_set` apply. They are stored only: no event destination, tracking, reputation, delivery or suppression option takes effect, and v2 echoes the options it was given. A send's `ConfigurationSetName` (v1 `SendEmail`, `SendRawEmail`, `SendTemplatedEmail`; v2 `SendEmail`, every content kind) and the raw `X-SES-CONFIGURATION-SET` header no longer answer 501: a missing set is refused before the sender with AWS's `ConfigurationSetDoesNotExist` `Configuration set <name> does not exist.` (v2: `NotFoundException`, inferred), and an existing one is recorded on the message as `configurationSet` and touched in the send's journal event. The v2 tag operations accept a configuration set's ARN. The name rules, the duplicate and limit answers are inferred.
- Under `--iam-enforce enforce` and `advise`, SES evaluates the condition keys `ses:ApiVersion`, `ses:FromAddress` and `ses:Recipients`, where a policy testing them answered 501. Every SES operation carries `ses:ApiVersion`: `"2"` on v2, as AWS documents, and `"1"` on v1 (switch `ses.condition.api-version-v1`, inferred). v1 `SendEmail` and `SendTemplatedEmail` and v2 `SendEmail` with Simple or Template content carry `ses:FromAddress`, the sender as written with its `+label`, and `ses:Recipients`, the `To`, `Cc` and `Bcc` addresses (multivalued, so test it with `ForAnyValue` or `ForAllValues`); an address written as `Name <address>` gives the address alone, and `ReplyToAddresses` are not recipients (switch `ses.condition.address-form`, inferred). A matching `Deny` refuses the send with SES's denial answer. `ses:FromDisplayName` and `ses:FeedbackAddress` still answer 501 everywhere, and so do `ses:FromAddress` and `ses:Recipients` on v1 `SendRawEmail`, v2 Raw content and the operations that do not send.
- `understudy ses messages --follow` prints the matching recorded SES messages, then each new one that matches the same filters as it is accepted, until interrupted. It ignores `--limit`, prints one message per line with `--output json`, and loses or repeats nothing recorded while it starts. It is woken by the journal stream and reads through the existing `GET /_understudy/v1/ses/messages`; there is no new endpoint.
- `ses.productionAccess` also takes a list of `{"account": "<12 digits>", "region": "<region>"}` entries: only the listed account and Region pairs leave the SES sandbox, and every other pair keeps the sandbox recipient check and quota. `GetSendQuota` and v2 `GetAccount` answer per pair. `true` and `false` behave as before; any other value, or an entry with a missing or malformed account or Region, is refused at start with an error naming `ses.productionAccess` and the entry.
- SQS `SendMessage` and `SendMessageBatch` to a queue with a `KmsMasterKeyId` ask KMS for a data key as the caller, as AWS does, so under `--iam-enforce enforce` a caller allowed `sqs:SendMessage` but not `kms:GenerateDataKey` on the key is refused with AWS's 400 `KmsAccessDenied` (`x-amzn-query-error` `KMS.AccessDeniedException;Sender`): KMS's denial followed by the KMS client's suffix, `(Service: AWSKMS; Status Code: 400; Error Code: AccessDeniedException; Request ID: <id>; Proxy: null)`. Recorded for `SendMessage`; `SendMessageBatch` refusing the whole request is inferred. SNS and EventBridge deliveries into such a queue need the key policy to allow the delivering service. Whatever `--iam-enforce` says, a send to a queue whose key KMS does not hold, has disabled or is deleting now fails with `KmsNotFound`, `KmsDisabled` or `KmsInvalidState` (inferred), where it succeeded; create the key in understudy first, or use `alias/aws/sqs`. Messages are still stored unencrypted, and KMS is asked on every send rather than once per `KmsDataKeyReusePeriodSeconds`.
- Visiting the `SubscribeURL` of the `UnsubscribeConfirmation` an unsigned SNS unsubscribe sends an HTTP or HTTPS endpoint restores the subscription, as AWS recorded: the answer is a `ConfirmSubscriptionResponse` with the old subscription ARN, and the subscription is listed again with `PendingConfirmation` and `ConfirmationWasAuthenticated` `false`. `ConfirmSubscription` with the message's `Token` restores it too. It keeps its attributes, and until it is restored it is not listed, readable or delivered to. The token restores it for two days of emulator time, then answers `Invalid parameter: Token`; that lifetime, keeping the attributes, and treating the subscription as gone meanwhile are inferred.
- Parameter Store puts a `Parameter Store Change` event on the account and Region's default EventBridge bus for each committed create, overwrite, label and delete, with the envelope and detail AWS recorded: source `aws.ssm`, the parameter ARN in `resources`, and `name`, `description`, `type` and `operation` (`Create`, `Update`, `LabelParameterVersion` or `Delete`) in `detail`, plus `label`, `fromVersion` and `toVersion` on a label event. A refused call sends nothing. One event per parameter for `DeleteParameters`, `"description": ""` for a parameter without one, and no event for `UnlabelParameterVersion` are inferred.
- Step Functions runs a `lambda:invoke` Task whose `InvocationType` is `Event`, given literally or through a path, where it refused a literal `Event` as `UNSUPPORTED_BY_UNDERSTUDY` and failed a path to it with `States.Runtime`. The Task hands the payload to Lambda's asynchronous invoke and succeeds without waiting for the function, with the recorded result: `StatusCode` 202, `Payload` `null`, no `ExecutedVersion`, and `SdkHttpMetadata` with AWS's six headers in AWS's orders. `DryRun` is still refused at create and fails at run time. The Step Functions snapshot section moves to state version 2, so a snapshot or `--persist` state file holding Step Functions state written by an earlier version is refused with a message naming both versions.
- Under `--iam-enforce enforce`, S3 `PutBucketNotificationConfiguration` refuses a queue, topic or function whose resource policy does not let `s3.amazonaws.com` deliver from the bucket, with AWS's `InvalidArgument` `Unable to validate the following destination configurations` and a numbered `ArgumentName`/`ArgumentValue` pair for each, such as `Permissions on the destination queue do not allow S3 to publish notifications from this bucket`. The check sends `aws:SourceArn` and `aws:SourceAccount` as deliveries do, and `x-amz-skip-destination-validation: true` skips it. Under `advise` the call is served and each denial journaled; under `off` nothing is asked.
- S3 `PutObject`, `CopyObject` and `CreateMultipartUpload` supply the condition keys `s3:x-amz-server-side-encryption`, `s3:x-amz-server-side-encryption-aws-kms-key-id` and `s3:x-amz-server-side-encryption-customer-algorithm` from their request headers, so a bucket or identity policy testing them is evaluated as on AWS instead of journaling `condition-key-unsupplied`. A request without encryption headers into a bucket whose default encryption is SSE-KMS takes the key-id key from the default's key, and leaves `s3:x-amz-server-side-encryption` absent, as AWS does: AWS's "require SSE-KMS" bucket policy then allows and refuses the same uploads. The `s3.condition.sse-from-default` switch records it, recorded for `PutObject` and inferred for the other two. The keys go with the `s3:PutObject` question only: a `CopyObject`'s `s3:GetObject` read of its source does not carry the destination's encryption headers.
- Under `--iam-enforce enforce`, Lambda `CreateFunction`, and `UpdateFunctionConfiguration` when it passes a `Role`, refuse an execution role that `lambda.amazonaws.com` may not assume, because its trust policy does not allow it or it does not exist, with AWS's `InvalidParameterValueException` `The role defined for the function cannot be assumed by Lambda.` Under `advise` the call is served and the denial journaled; under `off` nothing is asked. The check on `UpdateFunctionConfiguration` is inferred: only `CreateFunction` was recorded.
- Under `--iam-enforce enforce`, Lambda `PutFunctionEventInvokeConfig` and `UpdateFunctionEventInvokeConfig` refuse an SNS or SQS destination the function's execution role may not write to, with AWS's `InvalidParameterValueException` `The function execution role does not have permissions to call Publish on <topic arn>` (`SendMessage` for a queue). Under `advise` the call is served and the denial journaled; under `off` nothing is asked. Function, event bus and S3 bucket destinations are not checked.
- The journal records SQS moves between queues as `redrive` events: a receive that moves messages past a queue's `maxReceiveCount` to its dead-letter queue, and each step of a message move task. Each names both queues, the moved message ids and why, and is a child of the receive or of the move task's timer, so `understudy journal --kind redrive` and traces show how a message reached a dead-letter queue. The CLI and the web UI summarize them.
- `serve --tls --persist` keeps the TLS listener's key and certificate in the data directory and reuses them at the next start, so a CA bundle `env --tls` wrote keeps working across restarts. A kept certificate that is unreadable, expires within a day, or differs from the one the running build issues is replaced, with a warning naming why. Without `--persist` the certificate is still new at every start.
- `GET /_understudy/v1/health` names the TLS listener as `tlsEndpoint` once it accepts, the value the ready file and the banner give; it is absent without `--tls`. `understudy env --tls` reads it, so it finds a TLS listener on any port without `--tls-endpoint`. It still tries the endpoint's host at port 4567 when health names none or cannot be read, and `--tls-endpoint` still wins.
- STS answers `GetAccessKeyInfo` with the account an AKIA or ASIA access key id encodes, whether or not the key still exists, as AWS answered for a deleted key. An id that does not decode is refused with `ValidationError` in understudy's own text, which is inferred.
- SES v2 serves `GET /v2/email/identities`, the `ListEmailIdentities` binding that SDKs and CLIs generated before 2026-09-29 send, with `NextToken` and `PageSize` in the query: it answers the same pages as `POST /v2/email/list-identities`, as AWS recorded, where it answered sesv2's unknown operation. `GET /v2/email/configuration-sets`, the old `ListConfigurationSets` binding, now reaches that operation; that AWS still serves it is inferred. `POST /v2/email/identities` is still `CreateEmailIdentity`.
- DynamoDB answers `DescribeContributorInsights` without Local: `{"ContributorInsightsStatus":"DISABLED","TableName":<name>}` for a table that exists, as AWS recorded, and `ResourceNotFoundException` for a missing one, by inference from the time to live answers. It is marked partial: `UpdateContributorInsights` is unbound, so `DISABLED` is always true.
- S3 `PutObjectRetention` sends the `s3:ObjectRetention:Put` event notification to each configuration that names it, where a configuration naming it was stored and sent nothing. The record is `ObjectRetention:Put` with an `objectRetentionEventData` block after `s3` holding the version's `mode` and `retainUntilDate`, as S3 documents it; the event-hold members never appear, because event holds answer 501. The event is unrecorded, so three choices are inferred: the object block carries `key`, `eTag` and `versionId` but no size or sequencer, as a tagging record does; `retainUntilDate` is ISO 8601 UTC with milliseconds; and removing a retention sends nothing.
- CloudWatch `PutMetricData` with `StrictEntityValidation` false and more than two `EntityMetricData` entries stores the data and answers 200 with `X-Amzn-Failure-Message: EntitySizeTooLarge`, as the CloudWatch model documents (no capture). It is the only entity error understudy detects, so the header's other values are never sent. With `StrictEntityValidation` true the request is still refused.
- A call from a Lambda function's container that carries credentials understudy did not mint for it, as when the function's configuration sets `AWS_ACCESS_KEY_ID=test`, journals an `unminted-credentials` advisory naming the function (`understudy journal --kind advisory`), so a call missing from its invocation's trace is explained. The call itself is served as before and roots its own trace. Only the Linux bridge network and understudy running in a container journal it, where the call's remote address is the container's own; on Docker Desktop and with a remote daemon nothing is journaled.

### Changed

- A Lambda image function's pending pull shows as `image-pull` in `settle` timeouts and the status listing, where it showed as `invocation-running`. Settling still waits for pulls.
- A resource-scoped request-phase fault rule matches every Lambda operation that addresses a resource: the layer operations (`PublishLayerVersion`, `GetLayerVersion`, `GetLayerVersionByArn`, `ListLayerVersions`, `DeleteLayerVersion`, `AddLayerVersionPermission`, `RemoveLayerVersionPermission`, `GetLayerVersionPolicy`) now match on the layer or layer-version ARN they address, as the function, alias and mapping operations already did. Under `--iam-enforce` the same operations are evaluated against that ARN instead of `*`; a policy granting the action on `*` still allows them.
- **BREAKING:** The SQS snapshot section moves to state version 7, SNS to version 4, S3 to version 3, SES to version 4 and the outbox (pending cross-service deliveries) to version 6, so a snapshot or `--persist` state file holding any of them written by an earlier version is refused with a message naming both versions.
- SQS receipt handles are as long as AWS's: 412 characters from a standard queue and 304 from a FIFO queue, where they were 36. Like AWS's they are `AQEB` and padded base64; what lies inside AWS's is unknown, so understudy's are random beyond the prefix. A run with a fixed `--seed` therefore receives different handles than the same run on an earlier version, and a handle in the old 36-character form is refused as `ReceiptHandleIsInvalid`.
- SNS `throttlePolicy.maxReceivesPerSecond` on an HTTP or HTTPS subscription is validated, stored and read back but no longer spaces deliveries. AWS delivered a burst of 10 messages at rate 1 without pacing them, and how it paces a longer burst is unrecorded.
- `understudy journal --limit N` fetches the newest events in one request, where it paged through every match. The notice for left-out events no longer gives the total: it reads `showing the newest N matching events; ...`, where it read `showing the newest N of M matching events; ...`.
- Each release pins the Lambda runtime images to the digests public.ecr.aws serves when the release is prepared, and tests them before the tag. Releases 0.1.0 to 0.1.2 shipped the pins of 2026-10-14.
- Under `--persist`, a running clock advanced with `understudy clock advance` keeps that advance across a restart, however long the server was stopped. A restart used to resume it at the later of its saved time and wall time, so a downtime longer than the advance absorbed it. Checkpoints record the wall time of their cut in the manifest (`cutWall`); an explicit `snapshot save` does not, so its archives stay byte-deterministic. A state file written before this resumes as before.
- The warning for an operation missing from the vendored model names the model it checked, as the `model_source` log attribute (`api-models-aws@1cfdfb4 sqs-2012-11-05.json`: the model commit and file), so a client newer than the pinned model is easy to spot.
- awsJson success bodies (SQS, DynamoDB, DynamoDB Streams, CloudWatch, Logs, KMS, Secrets Manager, EventBridge, Step Functions, SSM and Kinesis) list each structure's members sorted by name, as AWS writes them, where they were in model order. Map entries, such as an SQS message's `Attributes`, and document values keep their order, and error bodies do not change. For Kinesis, which has no recording, the order is inferred. A client that decodes the JSON is unaffected; one that compares bytes now matches AWS.
- With neither `--docker` (`UNDERSTUDY_DOCKER`) nor `DOCKER_HOST` set, understudy uses the current Docker context's endpoint, found as the Docker CLI finds it: `DOCKER_CONTEXT`, else `currentContext` in `config.json` under `DOCKER_CONFIG`, else `~/.docker`. The context `default`, or none, keeps `unix:///var/run/docker.sock`, and no other socket path is probed. A machine whose `docker context use` names a context other than `default` now reaches that context's Engine where it used the default socket. A context understudy cannot use (an `ssh://` endpoint, a TLS context, a missing or unreadable meta file) turns containers off with a warning naming the context and the fix, as an unusable `DOCKER_HOST` does; an unreadable `config.json` keeps the default socket with a warning. `understudy doctor` says where the endpoint came from: the setting, `DOCKER_HOST`, the context, or the default. Lambda on Colima stays unsupported and has not been run: its context now resolves, but understudy takes its daemon for a Linux bridge whose gateway it cannot bind on the Mac host.

### Removed

- The `s3.maxObjectBytes` and `dynamodb.registry` configuration keys. `serve` parsed them and then refused to start, because nothing applied either. A file that names them now fails as an unknown key, naming it. S3 already enforces AWS's 5 GiB single-PUT limit, and DynamoDB Local already falls back from Docker Hub to the ECR Public mirror when a pull fails.

### Fixed

- Lambda `CreateFunction` and `UpdateFunctionConfiguration` check a `DeadLetterConfig` target before storing it, where any ARN was stored unchecked. As AWS recorded, each refusal is 400 `InvalidParameterValueException` with `Type` `User`: a missing queue `Error occurred while SendMessage. SQS Error Code: AWS.SimpleQueueService.NonExistentQueue. SQS Error Message: The specified queue does not exist.`, a FIFO queue `Invalid dead letter queue ARN: FIFO SQS queue is not supported for dead letter configuration`, and an ARN of a service other than SQS or SNS `Invalid dead letter queue ARN: The service specified by the TargetArn is not supported for dead letter configuration.` Under `--iam-enforce enforce` an execution role that may not send to the queue is refused with `The provided execution role does not have permissions to call SendMessage on SQS`; under `advise` the denial is journaled and the target stored; under `off` nothing is asked. Only the update was recorded: `CreateFunction`'s answers, the order of the checks, and the answers for a missing SNS topic and for the role's `sns:Publish` are inferred. `{"TargetArn": ""}` still clears the target and `{}` still leaves it.
- Lambda's 413 `RequestEntityTooLargeException` answers carry the text under `Message`, as AWS recorded, where they sent `message`. An `Event` Invoke over 1 MB answers `<n> byte payload is too large for the Event invocation type (limit 1048576 bytes)`, n being the payload's size. `PublishLayerVersion` caps its request at 70,167,211 bytes, the base64 body rather than the archive, and a body over a Lambda operation's cap answers `Request must be smaller than <cap> bytes for the <operation> operation`, where it answered understudy's own text. The form is recorded for `PublishLayerVersion` and `CreateFunction` and inferred for the other operations. Other services' 413 answers are unchanged.
- The 2.0 event a Lambda function URL hands its function keeps the `cookie` header in `headers` (`x=1; y=2`) as well as splitting it into `cookies`, and its `x-amzn-trace-id` header carries the `Root=` part alone, as AWS recorded; the function's own `_X_AMZN_TRACE_ID` is unchanged. HTTP API events are unchanged. Joining repeated `Cookie` headers with `; ` is inferred.
- Lambda `GetFunctionCodeSigningConfig` for a function without a code signing config leaves out `CodeSigningConfigArn` and `FunctionName`, where it sent an empty ARN and the function's name. AWS recorded both as `null`, which SDKs read the same as absent.
- Lambda function URLs look like AWS's: a new id is still 32 characters of lowercase base32 but has `0` at index 26, as every recorded id does, and `CreationTime` and `LastModifiedTime` carry nine fractional digits, not six. A `Timeout` over 900 on `CreateFunction` is refused with AWS's text, which has no `1 validation error detected: ` prefix; `UpdateFunctionConfiguration` answers alike, inferred. The memory-size and ephemeral-storage limit texts are unchanged.
- Lambda `CreateEventSourceMapping` and `UpdateEventSourceMapping` for an SQS queue make AWS's three checks with AWS's texts, each a 400 `InvalidParameterValueException`. A batching window on a FIFO queue is refused with `Batching window is not supported for FIFO queues`, where it was accepted and ignored. `ProvisionedPollerConfig` is range-checked before the check that refuses it together with `ScalingConfig`: `MinimumPollers` 2 to 200 and `MaximumPollers` from `MinimumPollers` to 10000, else `MinimumPollers should be between [2, 200] and MaximumPollers should be between [MinimumPollers, 10000]`. Six filters answer `Too many filter patterns, maximum allowed 5 patterns, provided 6 patterns.` A `ProvisionedPollerConfig` that leaves out a limit is not checked on that limit, and the text for `ScalingConfig` with an in-range `ProvisionedPollerConfig` is still inferred.
- SQS event records an event source mapping hands a function leave out `md5OfMessageAttributes` when the message has no attributes, standard and FIFO, as AWS recorded, where they carried `"md5OfMessageAttributes": null`. A message with attributes still carries the digest.
- The event a DynamoDB stream mapping hands a function writes `dynamodb.ApproximateCreationDateTime` as whole epoch seconds with a fraction (`1793725107.0`), so a Python handler reads a float as on AWS, where it read an int. The float type is recorded; the `.0` spelling is inferred. DynamoDB Streams' `GetRecords` answer is unchanged.
- Lambda `Invoke` with `RequestResponse` answers `Content-Type: application/json`, a function error (`X-Amz-Function-Error: Unhandled`) included, as AWS recorded, where it answered `application/octet-stream`. An `Event` invoke still answers 202 with no `Content-Type`, and other services' blob payloads keep `application/octet-stream`.
- A Lambda function deleted and created again under its name publishes from the number after the highest its name ever had, as AWS recorded, where numbering started again at 1. The Lambda snapshot section moves to state version 5 to keep these numbers; a version 4 section still loads, with no numbers kept for functions deleted before it was saved.
- Lambda function URLs frame their responses as AWS recorded. A function error, a timeout or a malformed response answers 502 `Internal Server Error` with `Content-Type: application/json`, where it was `text/plain`. A structured response with a numeric `body`, such as `{"statusCode":200,"body":123}`, answers with the number's text (`123`), and an `isBase64Encoded` body that is not valid base64 is decoded leniently, skipping characters outside the alphabet (`not base64!!` gives AWS's six bytes), where both answered 502; the rule beyond the recorded sample is inferred. Every answer carries `Content-Length`, so a large body is no longer chunked, and `HEAD` runs the function and answers `Content-Length: 0` with no body. HTTP APIs answer as before.
- Lambda `GetLayerVersionPolicy` on a version whose last statement was removed answers 404 `ResourceNotFoundException` `Layer version <version arn> does not have any resource policy.`, as AWS recorded, where it answered `No policy is associated with the given resource.`, which a version that never had a statement still answers. `AddLayerVersionPermission` refuses a statement that takes the version's policy past 20,480 bytes with AWS's `PolicyLengthExceededException` `The final policy size (<n>) is bigger than the limit (20480).`, where it had no limit. As AWS recorded, the size counts each principal as sent, so an account id counts 18 bytes less than the root ARN `GetLayerVersionPolicy` shows. The Lambda snapshot section moves on to state version 6, so a snapshot or `--persist` state file holding Lambda state written by an earlier version is refused with a message naming both versions.
- Lambda `CreateFunction` and `UpdateFunctionConfiguration` refuse another account's layer version that its owner's policy does not grant the caller's account, or that does not exist, with AWS's 403 `AccessDeniedException` `User: <caller arn> is not authorized to perform: lambda:GetLayerVersion on resource: <layer version arn> because no resource-based policy allows the lambda:GetLayerVersion action`, where understudy attached an ungranted version with an advisory and refused a missing one with 400. `GetLayerVersionByArn` and `GetLayerVersion` give the same answer on such a version, where they read it. - SES v1 `GetIdentityNotificationAttributes` leaves the `BounceTopic`, `ComplaintTopic` and `DeliveryTopic` elements out of an identity with no topics, as AWS recorded, where it sent them empty, and writes the three `HeadersIn*NotificationsEnabled` elements (bounce, delivery, complaint) before `ForwardingEnabled`, in AWS's recorded order rather than the model's.
- Under `--iam-enforce enforce`, a denied SES send, v1 `SendEmail`, `SendRawEmail` and `SendTemplatedEmail` and v2 `SendEmail`, answers SES's own text, `User '<principal arn>' is not authorized to perform '<action>' on resource '<identity arn>'`, naming the sender's identity, where it answered the IAM grammar; other SES actions keep the IAM grammar, as AWS recorded. - The Go `admin.Client` no longer tells a caller to start a server that is running. A call whose context ended, such as an `understudytest` `Settle` in a test that timed out, fails with an error naming the call that wraps the context's error, so `errors.Is` sees `context.Canceled` or `context.DeadlineExceeded`. A call the server took and sent no answer to, because the HTTP client's response bound ran out or the connection failed after the request was sent, is the new `*admin.NoAnswerError`, exit code 3. Only a failure to connect is still `*admin.UnreachableError`.
- The CLI no longer tells a user to start a server that is running. A command ended by the CLI itself, by Ctrl-C or by `settle` running past its grace, exits 1 with an error naming the call it gave up, where it exited 3 saying to start the server; `coverage` then fails rather than printing the offline report. A server that closes the connection after taking a call exits 3 saying it took the call but sent no answer.
- Under `--persist`, a periodic checkpoint saves a clock freeze, set or scale, a seeded id draw and a journaled event, where it waited for a state change or shutdown. After a crash, a seeded run no longer draws ids it already drew, and the journal no longer reissues event ids already in `journal.file`. Any API traffic now causes one write per `--persist-every`; an idle server still writes nothing.
- Under `--persist`, a periodic or shutdown checkpoint waits for a running reset instead of cutting inside it. A cut between a reset's DynamoDB table deletion and its cell reset, or before its fault-rule clear, saved a state a crash would then restart into.
- A request-phase latency fault on one delivery's target call, such as SQS `SendMessage` on one queue, delays that delivery alone. Every delivery due after it waited too, so an SNS fan-out to N queues under such a rule took N times the latency.
- With `journal.file` set, `serve` exits within 5 seconds of a shutdown even when the file's disk has stopped answering, such as a stalled network mount, where it waited for the disk forever. It then exits with an error that names the journal file and says how many events it may lack; the file ends at an event boundary except for a write in progress.
- `understudy version` names the version of a binary installed with `go install github.com/sustinbebustin/understudy/cmd/understudy@vX.Y.Z`, where it said `dev`. Without the release's stamp, the version is the module version the go command records, or the git version of a build in a checkout.
- Under `--iam-enforce enforce`, a denied Kinesis call carries its message under `Message`, as AWS does, where it said `message`.
- Under `--iam-enforce enforce`, a denied call to API Gateway (REST), CloudWatch (JSON), DynamoDB, DynamoDB Streams, EventBridge, KMS, CloudWatch Logs, Scheduler, SES v2, Step Functions or SQS (JSON) carries its message under `Message`, and API Gateway v2 under `message`, as AWS does, where each said the other.
- Under `--iam-enforce enforce`, a denied CloudWatch call over JSON or CBOR that does not send `x-amzn-query-mode: true` answers 400 without `x-amzn-query-error`, as AWS does over JSON, where it answered 403 with `AccessDenied;Sender`. In query mode it still answers 403 with the header, and Query denials and other CloudWatch errors are unchanged.
- The access record and generated policies hold the version actions AWS needs for a versioned S3 read: a `HeadObject` with a version ID records `s3:GetObjectVersion`, and a `GetObjectAttributes` with one records `s3:GetObjectVersion` and `s3:GetObjectVersionAttributes`. The Service Reference omits them, so a generated policy lacked them and failed on AWS.

## [0.1.0] - 2026-11-09

The release stopped before its Homebrew cask and Testcontainers modules, which are available from 0.1.2.

### Added

- First release: one binary and a multi-arch image (`ghcr.io/sustinbebustin/understudy`, linux/amd64 and linux/arm64) that stand in for eighteen AWS services through `AWS_ENDPOINT_URL`: SQS, SNS, S3, DynamoDB and DynamoDB Streams, Kinesis Data Streams, Lambda, CloudWatch Logs, Secrets Manager, KMS, IAM, STS, EventBridge, EventBridge Scheduler, CloudWatch, API Gateway (HTTP and REST APIs), SSM Parameter Store, Step Functions and SES. Coverage is partial and listed operation by operation in `docs/coverage.md`; an unimplemented operation answers 501.
- Binaries for linux and darwin on amd64 and arm64, and a Homebrew cask: `brew install --cask sustinbebustin/tap/understudy`.
- One emulator clock for every AWS timer, a causal journal of every call and delivery with a web UI, fault injection, snapshots and opt-in persistence.
- Lambda functions run in AWS's base images through Docker, with DynamoDB Local behind DynamoDB. Docker Desktop on macOS is supported, not CI-tested.
- Testcontainers modules for Go (`github.com/sustinbebustin/understudy/testcontainers/go`), Python and Node (`testcontainers-understudy` on PyPI and npm), versioned with understudy, whose default image is the release's.
- `understudy iam policy` prints the least-privilege policy the recorded calls imply, and `--iam-enforce advise|enforce` evaluates identity, resource, trust and key policies.

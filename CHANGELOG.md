# Changelog

Notable changes to understudy, in the form of [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions follow [Semantic Versioning](https://semver.org/); before 1.0 a minor version may break compatibility. A release's GitHub notes are its section here: `release.yml` refuses a tag without one.

## [Unreleased]

### Added

- `understudy ses messages --follow` prints the matching recorded SES messages, then each new one that matches the same filters as it is accepted, until interrupted. It ignores `--limit`, prints one message per line with `--output json`, and loses or repeats nothing recorded while it starts. It is woken by the journal stream and reads through the existing `GET /_understudy/v1/ses/messages`; there is no new endpoint.
- `ses.productionAccess` also takes a list of `{"account": "<12 digits>", "region": "<region>"}` entries: only the listed account and Region pairs leave the SES sandbox, and every other pair keeps the sandbox recipient check and quota. `GetSendQuota` and v2 `GetAccount` answer per pair. `true` and `false` behave as before; any other value, or an entry with a missing or malformed account or Region, is refused at start with an error naming `ses.productionAccess` and the entry.
- SQS `SendMessage` and `SendMessageBatch` to a queue with a `KmsMasterKeyId` ask KMS for a data key as the caller, as AWS does, so under `--iam-enforce enforce` a caller allowed `sqs:SendMessage` but not `kms:GenerateDataKey` on the key is refused with AWS's 400 `KmsAccessDenied` (`x-amzn-query-error` `KMS.AccessDeniedException;Sender`): KMS's denial followed by the KMS client's suffix, `(Service: AWSKMS; Status Code: 400; Error Code: AccessDeniedException; Request ID: <id>; Proxy: null)`. Recorded for `SendMessage`; `SendMessageBatch` refusing the whole request is inferred. SNS and EventBridge deliveries into such a queue need the key policy to allow the delivering service. Whatever `--iam-enforce` says, a send to a queue whose key KMS does not hold, has disabled or is deleting now fails with `KmsNotFound`, `KmsDisabled` or `KmsInvalidState` (inferred), where it succeeded; create the key in understudy first, or use `alias/aws/sqs`. Messages are still stored unencrypted, and KMS is asked on every send rather than once per `KmsDataKeyReusePeriodSeconds`.
- Visiting the `SubscribeURL` of the `UnsubscribeConfirmation` an unsigned SNS unsubscribe sends an HTTP or HTTPS endpoint restores the subscription, as AWS recorded: the answer is a `ConfirmSubscriptionResponse` with the old subscription ARN, and the subscription is listed again with `PendingConfirmation` and `ConfirmationWasAuthenticated` `false`. `ConfirmSubscription` with the message's `Token` restores it too. It keeps its attributes, and until it is restored it is not listed, readable or delivered to. The token restores it for two days of emulator time, then answers `Invalid parameter: Token`; that lifetime, keeping the attributes, and treating the subscription as gone meanwhile are inferred.
- Parameter Store puts a `Parameter Store Change` event on the account and Region's default EventBridge bus for each committed create, overwrite, label and delete, with the envelope and detail AWS recorded: source `aws.ssm`, the parameter ARN in `resources`, and `name`, `description`, `type` and `operation` (`Create`, `Update`, `LabelParameterVersion` or `Delete`) in `detail`, plus `label`, `fromVersion` and `toVersion` on a label event. A refused call sends nothing. One event per parameter for `DeleteParameters`, `"description": ""` for a parameter without one, and no event for `UnlabelParameterVersion` are inferred.
- Step Functions runs a `lambda:invoke` Task whose `InvocationType` is `Event`, given literally or through a path, where it refused a literal `Event` as `UNSUPPORTED_BY_UNDERSTUDY` and failed a path to it with `States.Runtime`. The Task hands the payload to Lambda's asynchronous invoke and succeeds without waiting for the function, with the recorded result: `StatusCode` 202, `Payload` `null`, no `ExecutedVersion`, and `SdkHttpMetadata` with AWS's six headers in AWS's orders. `DryRun` is still refused at create and fails at run time. The Step Functions snapshot section moves to state version 2, so a snapshot or `--persist` state file holding Step Functions state written by an earlier version is refused with a message naming both versions.
- Under `--iam-enforce enforce`, S3 `PutBucketNotificationConfiguration` refuses a queue, topic or function whose resource policy does not let `s3.amazonaws.com` deliver from the bucket, with AWS's `InvalidArgument` `Unable to validate the following destination configurations` and a numbered `ArgumentName`/`ArgumentValue` pair for each, such as `Permissions on the destination queue do not allow S3 to publish notifications from this bucket`. The check sends `aws:SourceArn` and `aws:SourceAccount` as deliveries do, and `x-amz-skip-destination-validation: true` skips it. Under `advise` the call is served and each denial journaled; under `off` nothing is asked.
- S3 `PutObject`, `CopyObject` and `CreateMultipartUpload` supply the condition keys `s3:x-amz-server-side-encryption`, `s3:x-amz-server-side-encryption-aws-kms-key-id` and `s3:x-amz-server-side-encryption-customer-algorithm` from their request headers, so a bucket or identity policy testing them is evaluated as on AWS instead of journaling `condition-key-unsupplied`. A request without encryption headers into a bucket whose default encryption is SSE-KMS takes the key-id key from the default's key, and leaves `s3:x-amz-server-side-encryption` absent, as AWS does: AWS's "require SSE-KMS" bucket policy then allows and refuses the same uploads. The `s3.condition.sse-from-default` switch records it, recorded for `PutObject` and inferred for the other two. The keys go with the `s3:PutObject` question only: a `CopyObject`'s `s3:GetObject` read of its source does not carry the destination's encryption headers.
- Under `--iam-enforce enforce`, Lambda `CreateFunction`, and `UpdateFunctionConfiguration` when it passes a `Role`, refuse an execution role that `lambda.amazonaws.com` may not assume, because its trust policy does not allow it or it does not exist, with AWS's `InvalidParameterValueException` `The role defined for the function cannot be assumed by Lambda.` Under `advise` the call is served and the denial journaled; under `off` nothing is asked. The check on `UpdateFunctionConfiguration` is inferred: only `CreateFunction` was recorded.
- Under `--iam-enforce enforce`, Lambda `PutFunctionEventInvokeConfig` and `UpdateFunctionEventInvokeConfig` refuse an SNS or SQS destination the function's execution role may not write to, with AWS's `InvalidParameterValueException` `The function execution role does not have permissions to call Publish on <topic arn>` (`SendMessage` for a queue). Under `advise` the call is served and the denial journaled; under `off` nothing is asked. Function, event bus and S3 bucket destinations are not checked.
- The journal records SQS moves between queues as `redrive` events: a receive that moves messages past a queue's `maxReceiveCount` to its dead-letter queue, and each step of a message move task. Each names both queues, the moved message ids and why, and is a child of the receive or of the move task's timer, so `understudy journal --kind redrive` and traces show how a message reached a dead-letter queue. The CLI and the web UI summarize them.
- `serve --tls --persist` keeps the TLS listener's key and certificate in the data directory and reuses them at the next start, so a CA bundle `env --tls` wrote keeps working across restarts. A kept certificate that is unreadable, expires within a day, or differs from the one the running build issues is replaced, with a warning naming why. Without `--persist` the certificate is still new at every start.
- `GET /_understudy/v1/health` names the TLS listener as `tlsEndpoint` once it accepts, the value the ready file and the banner give; it is absent without `--tls`. `understudy env --tls` reads it, so it finds a TLS listener on any port without `--tls-endpoint`. It still tries the endpoint's host at port 4567 when health names none or cannot be read, and `--tls-endpoint` still wins.
- STS answers `GetAccessKeyInfo` with the account an AKIA or ASIA access key id encodes, whether or not the key still exists, as AWS answered for a deleted key. An id that does not decode is refused with `ValidationError` in understudy's own text, which is inferred.
- DynamoDB answers `DescribeContributorInsights` without Local: `{"ContributorInsightsStatus":"DISABLED","TableName":<name>}` for a table that exists, as AWS recorded, and `ResourceNotFoundException` for a missing one, by inference from the time to live answers. It is marked partial: `UpdateContributorInsights` is unbound, so `DISABLED` is always true.

### Changed

- **BREAKING:** The SQS snapshot section moves to state version 7, SNS to version 4 and the outbox (pending cross-service deliveries) to version 6, so a snapshot or `--persist` state file holding any of them written by an earlier version is refused with a message naming both versions.
- SQS receipt handles are as long as AWS's: 412 characters from a standard queue and 304 from a FIFO queue, where they were 36. Like AWS's they are `AQEB` and padded base64; what lies inside AWS's is unknown, so understudy's are random beyond the prefix. A run with a fixed `--seed` therefore receives different handles than the same run on an earlier version, and a handle in the old 36-character form is refused as `ReceiptHandleIsInvalid`.
- SNS `throttlePolicy.maxReceivesPerSecond` on an HTTP or HTTPS subscription is validated, stored and read back but no longer spaces deliveries. AWS delivered a burst of 10 messages at rate 1 without pacing them, and how it paces a longer burst is unrecorded.
- `understudy journal --limit N` fetches the newest events in one request, where it paged through every match. The notice for left-out events no longer gives the total: it reads `showing the newest N matching events; ...`, where it read `showing the newest N of M matching events; ...`.
- Each release pins the Lambda runtime images to the digests public.ecr.aws serves when the release is prepared, and tests them before the tag. Releases 0.1.0 to 0.1.2 shipped the pins of 2026-10-14.
- Under `--persist`, a running clock advanced with `understudy clock advance` keeps that advance across a restart, however long the server was stopped. A restart used to resume it at the later of its saved time and wall time, so a downtime longer than the advance absorbed it. Checkpoints record the wall time of their cut in the manifest (`cutWall`); an explicit `snapshot save` does not, so its archives stay byte-deterministic. A state file written before this resumes as before.
- The warning for an operation missing from the vendored model names the model it checked, as the `model_source` log attribute (`api-models-aws@1cfdfb4 sqs-2012-11-05.json`: the model commit and file), so a client newer than the pinned model is easy to spot.
- awsJson success bodies (SQS, DynamoDB, DynamoDB Streams, CloudWatch, Logs, KMS, Secrets Manager, EventBridge, Step Functions, SSM and Kinesis) list each structure's members sorted by name, as AWS writes them, where they were in model order. Map entries, such as an SQS message's `Attributes`, and document values keep their order, and error bodies do not change. For Kinesis, which has no recording, the order is inferred. A client that decodes the JSON is unaffected; one that compares bytes now matches AWS.

### Removed

- The `s3.maxObjectBytes` and `dynamodb.registry` configuration keys. `serve` parsed them and then refused to start, because nothing applied either. A file that names them now fails as an unknown key, naming it. S3 already enforces AWS's 5 GiB single-PUT limit, and DynamoDB Local already falls back from Docker Hub to the ECR Public mirror when a pull fails.

### Fixed

- SES v1 `GetIdentityNotificationAttributes` leaves the `BounceTopic`, `ComplaintTopic` and `DeliveryTopic` elements out of an identity with no topics, as AWS recorded, where it sent them empty.
- An SQS JSON request without `QueueUrl` answers `QueueDoesNotExist` (400, `x-amzn-query-error` `AWS.SimpleQueueService.NonExistentQueue;Sender`, `The specified queue does not exist.`), where it answered `MissingParameter`, also under `--iam-enforce enforce`. Recorded for `ReceiveMessage`; inferred for every other operation that takes `QueueUrl`. A request that names a queue but omits another required member still answers `MissingParameter`.
- SQS JSON validation errors answer AWS's `__type`, `com.amazon.coral.service#InvalidParameterValueException` and `com.amazon.coral.service#MissingRequiredParameterException`, where they answered `com.amazonaws.sqs#...`; the Query codes are unchanged.
- SQS JSON errors send AWS's `x-amzn-query-error`: `MalformedInput;Sender` for a body that does not decode, where it sent `SerializationException;Sender`, and `InvalidAction;Sender` for an unknown `AmazonSQS` target, where it sent `UnknownOperationException;Sender`. A target naming another service, such as `AmazonSNS.ListQueues`, answers without the header, as does any request a service's front end answers without claiming it (inferred). A Query request whose parameters do not decode answers Code `MalformedInput` to match (inferred). CloudWatch's headers are unchanged.
- Every SQS Query response body, success and error, starts with `<?xml version="1.0"?>` and no newline, as AWS sends it. SNS and the other Query services still send no declaration.
- An SQS Query request without `Version`, such as a legacy `SendMessage`, is served when it is signed for `sqs` or posted to a queue URL, where it was declined with 404 `<UnknownOperationException/>`.
- SQS dead-letter and move-task details match AWS's recordings. A message moved to a FIFO dead-letter queue keeps its original `SentTimestamp`, while its retention restarts at the move. A FIFO message a move task sends back keeps the dead-letter copy's `MessageDeduplicationId`. `CancelMessageMoveTask` on a finished task answers 400 `InvalidParameterValue` `Only active tasks can be cancelled.`, where it answered `ResourceNotFoundException`. A refused `RedrivePolicy` is quoted as the request sent it, and the queue `Policy` attribute reads back compacted with key order kept.
- SQS receipt handles from an earlier receive act as AWS's do. On a standard queue an older handle of a message received again since deletes it and changes its visibility, alone or in a batch, where understudy deleted nothing and refused the change. On a FIFO queue it answers 400 `InvalidParameterValue` `The receipt handle has expired.`, where it succeeded. A handle another queue issued fails its `DeleteMessageBatch` or `ChangeMessageVisibilityBatch` entry as `ReceiptHandleIsInvalid` `The receipt handle "<H>" is not valid for this queue.`; outside a batch it keeps its old answer, since AWS's is unrecorded.
- Changing one SQS message no longer copies the queue's whole backlog, so receives and visibility changes cost the same on a queue of 10,000 messages as on one of 10.
- A message SNS delivers to an SQS queue, and an SNS subscription's dead letter, carries `SenderId` `<AROA role id>:AWS-CLOUDCAST`, where it carried `sns.amazonaws.com`; the role id is fixed and inferred. SNS message ids (`Publish`, `PublishBatch` and the envelope's `MessageId`) are version 5 UUIDs, as AWS's are, and so is the `x-amzn-RequestId` of an SQS or SNS answer; SQS message ids and other services' request ids stay version 4.
- The `Records` event SNS hands a Lambda subscription writes `Subject` after `SigningCertUrl` and types `Number` and `String.Array` message attributes as `String`, keeping their values, as AWS recorded.
- A failed SNS delivery to a Lambda subscription goes to the subscription's dead-letter queue as the SQS notification envelope, with the topic's message, subject and message attributes inside, as AWS sends it, where understudy sent the Lambda `Records` event.
- An SNS HTTP or HTTPS delivery answered with any status but 429 or 5xx, a 3xx or a 4xx such as 404 included, ends as delivered after one attempt, with no retry and no dead letter, as AWS recorded; it was dead-lettered as a permanent failure. The journal still records each attempt's status, and the journal's HTTP class `permanent` is gone: those answers are classed `success`, so a consumer that matched `class == "permanent"` should read `status` instead.
- A repeated SNS `Subscribe` of a pending HTTP or HTTPS endpoint sends a `SubscriptionConfirmation` with a new token, where it resent the first, and returns the same subscription ARN. Every token sent confirms until the subscription is confirmed or expires; once confirmed, `ConfirmSubscription` with any other of its tokens answers 403 `AuthorizationError` `Subscription already confirmed`, as AWS recorded.
- SNS validates a topic or subscription `DeliveryPolicy` in AWS's order and with AWS's recorded texts. **BREAKING:** a retry policy must carry `numRetries` and then `minDelayTarget`, so a partial `healthyRetryPolicy` (including a Terraform `delivery_policy` that sets only some retry members) is now refused, as on AWS. Also newly refused: a `sicklyRetryPolicy` checked like the healthy one, a total retry time over 3,600 seconds, an unknown member, a member of the wrong type, and, with raw delivery off or at topic level, a `headerContentType` other than `application/json` or `text/plain`. The per-member bound texts and the exact 3,600-second boundary are inferred, and malformed JSON keeps understudy's own text.
- SNS refuses in AWS's words: a `Number` attribute that is not a number, an attribute name starting `AWS.` or `Amazon.`, any protocol but `sqs` on a FIFO topic (`Invalid parameter: Invalid protocol type: <protocol>`, inferred beyond `lambda` and `http`), and an `application` endpoint that is not an ARN (a valid ARN still answers 501). `MessageStructure=json` with a duplicate key is accepted and the last value wins, where it was refused.
- SNS `PublishBatch` reports an entry with an invalid `Subject` in `Failed` and publishes the other entries, where it failed the whole call. A subscription's `FilterPolicy` reads back compacted with key order kept. `ListSubscriptions` lists a deleted topic's subscriptions for as long as understudy keeps them, where it left them out.
- SNS and SES v1 answer an unknown Query `Action` as AWS does: 400 `InvalidAction` in the `http://webservices.amazon.com/AWSFault/2005-15-09` namespace with `Could not find operation <Action> for version <Version>`. A REST request signed for `ses` that names no SES v2 operation answers AWS's 404 with the body `<UnknownOperationException/>` and no `Content-Type`. SQS and the other Query services keep their answers.
- SNS `ListTopics`, `ListSubscriptions` and `ListSubscriptionsByTopic`, and EventBridge `ListEventBuses`, `ListRules`, `ListRuleNamesByTarget` and `ListTargetsByRule`, no longer skip a resource that exists throughout a listing when another is deleted between pages (inferred). SNS subscriptions now list ordered by subscription ARN, where they came in creation order.
- Two concurrent publishes to one FIFO topic and message group reach a subscribed FIFO queue in the order of their SNS sequence numbers, where the second could arrive first. The same holds for any producer delivering into one message group of a FIFO queue, such as concurrent `PutEvents` calls whose rule targets it.
- SNS filter policies, EventBridge event patterns and Lambda event source mapping filters accept Event Ruler's `exactly` operator, as AWS does in all three. `{"a":[{"exactly":"x"}]}` matches a string that is exactly `x`, not a number with that text or another spelling of an IP address.
- SNS filter policies match and count keys as AWS recorded. In MessageAttributes scope a message without attributes never matches and `exists:true` fails on an empty value; in MessageBody scope `{}` can still match, and `exists:true` fails on `null`, `[]` and `{}`. `equals-ignore-case` is accepted under `anything-but`, `prefix` and `suffix`. Keys are counted across the whole policy, `$or` branches included, against the limit of five; a key repeated in two branches counts once (inferred).
- SNS filter policy and EventBridge event pattern refusals carry AWS's texts, ending with Jackson's location line (`at [Source: (String)"<pattern>"; line: 1, column: N]`) where AWS sends one. SNS quotes the policy as it writes it back, with a number beyond binary64 as `"Infinity"`, and uses AWS's wildcard, size and `anything-but` texts. EventBridge refuses a malformed `$or` with the reason of reading `$or` as a plain key and more than 1000 `$or` combinations with `Or operator is producing over 1000 rule combinations`.
- Lambda event source mapping filters accept `cidr`, `wildcard`, `anything-but` with `prefix` or `suffix`, and `prefix` with `equals-ignore-case`, as AWS recorded, where understudy refused them. A filter on `eventSource` never matches, a string rule such as `["10"]` matches the number `10`, and a wildcard rule matches nothing (one recording, no positive control). A cidr `/32` or `/128`, where AWS answers HTTP 500, is still refused as an invalid filter pattern.
- A list of structures over its length limit, such as IAM `TagRole` with 51 tags or Logs `PutLogEvents` with 10,001 events, is reported as `Value at 'tags' failed to satisfy constraint: ...` with no rendered value, as AWS does, where understudy rendered Java text such as `Value '[, , ]'`. Applying this to every service, and to maps of structures, is inferred.
- IAM validation errors leave out the value and an enum violation's value set, as AWS does: `Value at 'status' failed to satisfy constraint: Member must satisfy enum value set`, where understudy sent `Value 'x' at 'status'` and the list. A pattern violation still quotes the pattern. DynamoDB Streams validation errors leave out the value too, a missing member's `null` included, and keep the enum value set: `Value at 'limit' failed to satisfy constraint: ...`.
- IAM `ListEntitiesForPolicy` refuses a `PathPrefix` that is neither `/` nor a string that begins and ends with a slash, such as `/svc` or `x/a/`, with the pattern `ValidationError` that `CreateRole`, `CreateUser`, `UpdateUser` and `CreateInstanceProfile` send for such a path, where it filtered by it. The model's pattern anchors each of its alternatives on one side only; understudy now reads it as the model's documentation does, for every input that takes an IAM path.
- IAM and STS refuse policies with AWS's texts. A role trust policy statement without `Principal` is `MalformedPolicyDocument` `Missing required field Principal`, checked before the other trust rules, where understudy reported its missing actions; a trust statement naming anything but an STS AssumeRole action, `sts:assumerole` and `sts:*` included, is `AssumeRole policy may only specify STS AssumeRole actions.`, where understudy sent moto's text; and an STS session policy statement without `Action` is `Missing required field Action`. IAM `CreatePolicy` keeps `Policy statement must contain actions.`, since IAM's text is unrecorded.
- Every IAM `CreateDate` is whole seconds, as AWS writes a user's and an access key's, where understudy kept milliseconds; for roles, managed policies and their versions, and instance profiles it is inferred. The time is truncated, which may differ from AWS by under a second, since whether AWS truncates or rounds is unrecorded. Entities stored by an earlier version keep their dates.
- STS `AssumeRole` refuses more than ten `PolicyArns` with AWS's text, `The limit of ARNs for the PolicyArns parameter was exceeded. 10 ARNs can be requested at most in an API request.`, where it sent a constraint-violation text.
- KMS refusals carry the codes and texts AWS recorded. A key pending deletion is `<key ARN> is pending deletion.`, without `(or pending replica deletion)`; the not-pending text drops the same clause by inference. `CreateAlias` with an `alias/aws/` name is `NotAuthorizedException`, its message under the key `Message`, where it was `InvalidAliasNameException`. The key policy quota counts characters other than whitespace, and a policy past it is `LimitExceededException` `Keys support only policies up to 32768 characters long in this region. The supplied policy was N characters long.` A policy name other than `default` is `ValidationException` `Invalid policy name`, where it was `NotFoundException` (recorded for `PutKeyPolicy`, inferred for `GetKeyPolicy`). A marker no page issued is `InvalidMarkerException` with no message. `ScheduleKeyDeletion` with `PendingWindowInDays` outside 7 to 30 is `ValidationException` `PendingWindowInDays must be between 7 and 30`. The `kms.pending-deletion.crypto-error` switch is now aws-recorded.
- Secrets Manager `CreateSecret` answers as AWS does in three cases. A `Name` whose only character outside the secret-name set is `!`, such as `a!b`, is `InvalidParameterException` `You provided an invalid name for the secret.`, where it was `ValidationException`; any other character outside the set, such as a space, keeps `ValidationException`, as does a `SecretId` with a `!`. A `Name` over 512 characters is `ValidationException` `Invalid name. Must be a valid name containing alphanumeric characters, or any of the following: -/_+=.@!`, where it sent the generic length text. A disabled KMS key is `InvalidParameterException` `The operation failed because the specified KMS key is disabled.`, where it was `EncryptionFailure`; `UpdateSecret` and `PutSecretValue` under a disabled key are inferred to answer alike.
- Secrets Manager keeps a `KmsKeyId` of `alias/aws/secretsmanager` given explicitly, and `DescribeSecret` and `ListSecrets` show it, as AWS does, where it was dropped as the default key. A secret created without `KmsKeyId` still shows none. The managed key named by its alias ARN, key id or key ARN is still not shown, since AWS's answer is unrecorded.
- Secrets Manager's deletion lifecycle follows AWS's dates. A second `DeleteSecret` of a secret already scheduled for deletion reschedules it to that call plus its recovery window and answers `ARN`, `Name` and the new `DeletionDate`, where it was refused as marked for deletion; the secret is deleted at the new date. `DescribeSecret`'s `DeletedDate` is when `DeleteSecret` was called, where it was the scheduled deletion date. `DeleteSecret` and `RestoreSecret` advance `LastChangedDate`, a `RestoreSecret` of a secret not scheduled for deletion included. The Secrets Manager snapshot section moves to state version 3, so a snapshot or `--persist` state file holding Secrets Manager state written by an earlier version is refused with a message naming both versions.
- DynamoDB errors understudy raises itself (validation, not-found, the TTL, tagging and point-in-time recovery shim refusals, an unknown target, and edge refusals such as clock skew) carry `x-amz-crc32`, the CRC-32 of the body, as every AWS answer does. They carried none; Local's answers and shim successes already did.
- DynamoDB refuses a request body that repeats a member name with 400 `SerializationException` `Duplicate key found in payload`, as AWS does, before DynamoDB Local sees it. understudy kept the last value and forwarded the request. AWS was recorded refusing a top-level repeat; refusing one at any depth, attribute-value maps included, is inferred. The other awsJson services still keep the last value; what AWS does there is unrecorded.
- DynamoDB `UpdateTimeToLive` refuses a change to a table's TTL within one hour of emulator time of its last change, with AWS's 400 `ValidationException` `Time to live has been modified multiple times within a fixed interval`, where it served every change. The `TimeToLive is already enabled` and `TimeToLive is already disabled` checks come first, so a repeated enable inside the hour still gets that text, and a disable after a refused disable gets the interval text, because TTL is still enabled. The instant of the last change is kept in snapshots and `--persist` state. The hour is AWS's documented interval; the order of the checks is recorded.
- DynamoDB `CreateTable`, `UpdateTable` and `DeleteTable` answers carry the members AWS's do. `CreateTable` leaves out `WarmThroughput` and `BillingModeSummary.LastUpdateToPayPerRequestDateTime`; `DeleteTable` leaves out `AttributeDefinitions`, `KeySchema`, `CreationDateTime` and `WarmThroughput`; an `UpdateTable` switching a table from `PAY_PER_REQUEST` to `PROVISIONED` stamps `ProvisionedThroughput.LastIncreaseDateTime` with the update's instant in its answer, which a later `DescribeTable` does not report. `DescribeTable` still carries `WarmThroughput`. The global secondary indexes in a `CreateTable` answer keep their `WarmThroughput`, since AWS's answer for an indexed table is unrecorded.
- DynamoDB `CreateTable` and `UpdateTable` refuse an SSE key KMS does not find with AWS's text: `KMS validation error: com.amazonaws.services.kms.model.NotFoundException: Key '<arn>' does not exist (Service: AWSKMS; Status Code: 400; Error Code: NotFoundException; Request ID: <uuid>; Proxy: null)`. Recorded for a key ARN; a key id or alias is named by the ARN understudy resolves it to, by inference.
- CloudWatch Logs answers a log group or log stream name over 512 characters with AWS's `InvalidParameterException` `Invalid LogGroup or LogStream, both must have length less than or equal to 512.`, where it sent the generic validation text naming the member. The text is recorded at `CreateLogGroup`; the other operations taking a log group or stream name are inferred to answer alike. An empty name keeps the generic text, since AWS's answer to one is unrecorded.
- An HTTP API refuses a request whose request line plus headers are over 10,240 bytes with `431` `{"message":"Request Header Fields Too Large"}`, where it did not limit headers, and answers a body over 10 MiB (10,485,760 bytes) with `413` `{"message":"Request Entity Too Large"}` without a `Content-Type`, as AWS's front layer does; both carry `apigw-requestid`. A body over 10,000,000 bytes but not over 10 MiB, or an event over Lambda's 6 MB limit, keeps the gateway's `413` with `Content-Type: application/json`.
- API Gateway HTTP API `GetApis` lists APIs by id ascending, where it listed them in creation order, and its `nextToken` is AWS's form (the URL-escaped base64 of `id=S` and the page's last id), as REST `GetResources` already was. The id order is inferred from one recorded page; the token form is recorded. `GetRoutes`, `GetIntegrations` and the other lists keep creation order and their own tokens, which are unrecorded. The API Gateway HTTP API snapshot section moves to state version 2, so a snapshot or `--persist` state file holding HTTP APIs written by an earlier version is refused with a message naming both versions.
- API Gateway HTTP API `UpdateIntegration` on an AWS service integration refuses `requestParameters` that leave out a parameter the subtype requires, with AWS's `BadRequestException` `Invalid integration URI specified`, and changes nothing, where understudy merged the sent map into the stored one and stored the update. An update that sends every required parameter, as Terraform does, or sends no `requestParameters`, merges as before. The rule is inferred from one recorded case.
- Step Functions accepts a JSONPath function such as `$.a.length()` in a path at create, as AWS does, where it refused it as `UNSUPPORTED_BY_UNDERSTUDY`. As on AWS, the execution fails when a state evaluates the path, with `States.Runtime` and the cause `The JSONPath '$.a.length()' specified for the field 'len.$' could not be found in the input '...'`. Other function names are inferred to fail the same way. Multi-clause filters and filter scripts are still refused.
- Step Functions `StartExecution` limits `input` to 262,144 bytes in UTF-8, as AWS does, where it counted characters, so a non-ASCII input AWS refuses is now refused. The refusal reads `Member must have size less than or equal to 262144 bytes in UTF-8 encoding`, AWS's recorded text, where it read `Member must have length less than or equal to 262144`.
- Parameter Store's `InvalidKeyId` and `AccessDeniedException` for a failed KMS call end KMS's message with the KMS client's suffix, as AWS does: ` (Service: AWSKMS; Status Code: 400; Error Code: DisabledException; Request ID: <uuid>; Proxy: null)`. The request id is a fresh one, since understudy's KMS call has no id of AWS's to name. A KMS server error still answers `InternalServerError` in understudy's own words.
- SSM and API Gateway REST report a scalar list element's validation failure once at the list, as AWS does: the value is the whole list and the constraint lists every constraint on the element, as in `Value '[WRONG]' at 'createRestApiInput.endpointConfiguration.types' failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy enum value set: [PRIVATE, EDGE, REGIONAL]]`, where understudy named the element (`types.1.member`). A member of a structured element keeps its indexed path. API Gateway lists `EndpointType` values in AWS's order. The rolled-up forms for map keys and values are inferred for both services.
- Under `--iam-enforce enforce`, IAM `GetRole` of a role that does not exist, and every other IAM operation naming a user, role or instance profile by name, is denied to a caller not allowed the action, as AWS does, where it answered `NoSuchEntity`. Secrets Manager operations that take a `SecretId` deny a missing secret the same way, where they answered `ResourceNotFoundException`. The denial names the resource as the request gave it: `role <name>` for `GetRole` (`user <name>` and `instance-profile <name>` by inference), and the `SecretId` for Secrets Manager whether or not the secret exists, where it named the ARN. A caller allowed the action on `*`, `role/*` or `secret:*` still gets the not-found error. The `iam.enforce.missing-resource.by-name` and `secretsmanager.enforce.missing-resource.by-name` switches are now `deny-first` and aws-recorded, and `iam.enforce.missing-resource` names the services that resolve first.
- The access record, and so the generated policy, holds `iam:PassRole` on the role SNS `SetTopicAttributes` passes in a delivery status attribute such as `LambdaSuccessFeedbackRoleArn`, and on the `SubscriptionRoleArn` role of `Subscribe` and `SetSubscriptionAttributes`, as `CreateTopic` already did. A call that passes no role records none. The policy guide no longer lists them as unrecorded.
- Under `--sigv4 verify`, S3 refuses a header-signed request that carries an `x-amz-*` header it did not sign, with 403 `AccessDenied` "There were headers present in the request which were not signed" and a `HeadersNotSigned` element naming the headers, as AWS does. Only presigned requests were checked before. The SSE-C key and key-MD5 headers need not be signed, as on presigned requests. Other services still check presigned requests only, because AWS's answer for them is not recorded; `--sigv4 parse` checks nothing, as before.
- A resource policy naming a bare account id as an AWS principal, `"Principal":{"AWS":"123456789012"}`, is stored and read back as `"arn:aws:iam::123456789012:root"`, as AWS does, for SQS `CreateQueue` and `SetQueueAttributes`, SNS `CreateTopic` and `SetTopicAttributes`, S3 `PutBucketPolicy`, and KMS `CreateKey` and `PutKeyPolicy`. The rest of the policy reads back as sent, and evaluation is unchanged. The `sqs.`, `sns.`, `s3.` and `kms.resource-policy.account-id-principal` switches record it, and the `iam.policy.principal-existence` switch discloses that a principal a policy names is not checked for existence, which AWS checks.
- Under `--iam-enforce enforce`, Lambda `CreateFunction`, and `UpdateFunctionConfiguration` when it passes a `Role`, refuse a caller without `iam:PassRole` on the execution role with `AccessDeniedException`, as AWS does, before the role's trust is checked. The role was recorded in the access record but never asked about. The pass carries `iam:PassedToService` `lambda.amazonaws.com`, so a policy from `/iam/policy` grants it on that condition.
- Under `--iam-enforce enforce`, a denied list operation names the resource AWS names: `on resource: arn:aws:cloudwatch:<region>:<account>:alarm:*` for CloudWatch `DescribeAlarms`, `table/*/stream/*` for DynamoDB Streams `ListStreams`, `schedule/*/*` for Scheduler `ListSchedules`, `stateMachine:*` for Step Functions `ListStateMachines`, `arn:aws:ssm:<region>:<account>:*` for SSM `DescribeParameters` and `*` for SES v2 `ListEmailIdentities`. The message named no resource. Policies are still evaluated, and generated, on `*`.
- Under `--iam-enforce enforce`, a call naming an SQS queue or S3 bucket that does not exist answers `QueueDoesNotExist` or `NoSuchBucket` before it is authorized, as AWS does, where it answered the denial. A `GetObject`, `HeadObject` or `GetObjectAttributes` of a missing key asks `s3:ListBucket` on the bucket before `s3:GetObject`, so a caller denied both gets the `s3:ListBucket` denial AWS gives, and one allowed `s3:ListBucket` gets `NoSuchKey`. The `sqs.enforce.missing-resource` and `s3.enforce.missing-resource` switches record the order, and `kms.enforce.missing-resource.by-name` is now aws-recorded for key ids. S3 Control's tag operations still deny first.
- `GetSessionToken` signed with temporary credentials from an earlier `GetSessionToken` is refused under `--sigv4 parse`, as it already was under `verify` and as AWS refuses it.
- The Go `admin.Client` no longer tells a caller to start a server that is running. A call whose context ended, such as an `understudytest` `Settle` in a test that timed out, fails with an error naming the call that wraps the context's error, so `errors.Is` sees `context.Canceled` or `context.DeadlineExceeded`. A call the server took and sent no answer to, because the HTTP client's response bound ran out or the connection failed after the request was sent, is the new `*admin.NoAnswerError`, exit code 3. Only a failure to connect is still `*admin.UnreachableError`.
- The CLI no longer tells a user to start a server that is running. A command ended by the CLI itself, by Ctrl-C or by `settle` running past its grace, exits 1 with an error naming the call it gave up, where it exited 3 saying to start the server; `coverage` then fails rather than printing the offline report. A server that closes the connection after taking a call exits 3 saying it took the call but sent no answer.
- Under `--persist`, a periodic checkpoint saves a clock freeze, set or scale, a seeded id draw and a journaled event, where it waited for a state change or shutdown. After a crash, a seeded run no longer draws ids it already drew, and the journal no longer reissues event ids already in `journal.file`. Any API traffic now causes one write per `--persist-every`; an idle server still writes nothing.
- Under `--persist`, a periodic or shutdown checkpoint waits for a running reset instead of cutting inside it. A cut between a reset's DynamoDB table deletion and its cell reset, or before its fault-rule clear, saved a state a crash would then restart into.
- A request-phase latency fault on one delivery's target call, such as SQS `SendMessage` on one queue, delays that delivery alone. Every delivery due after it waited too, so an SNS fan-out to N queues under such a rule took N times the latency.
- With `journal.file` set, `serve` exits within 5 seconds of a shutdown even when the file's disk has stopped answering, such as a stalled network mount, where it waited for the disk forever. It then exits with an error that names the journal file and says how many events it may lack; the file ends at an event boundary except for a write in progress.
- `understudy version` names the version of a binary installed with `go install github.com/sustinbebustin/understudy/cmd/understudy@vX.Y.Z`, where it said `dev`. Without the release's stamp, the version is the module version the go command records, or the git version of a build in a checkout.
- Under `--iam-enforce enforce`, a denied Kinesis call carries its message under `Message`, as AWS does, where it said `message`.
- Under `--iam-enforce enforce`, a denied call to API Gateway (REST), CloudWatch (JSON), DynamoDB, DynamoDB Streams, EventBridge, KMS, CloudWatch Logs, Scheduler, SES v2, Step Functions or SQS (JSON) carries its message under `Message`, and API Gateway v2 under `message`, as AWS does, where each said the other.
- Under `--iam-enforce enforce`, a denied CloudWatch call over JSON or CBOR that does not send `x-amzn-query-mode: true` answers 400 without `x-amzn-query-error`, as AWS does over JSON, where it answered 403 with `AccessDenied;Sender`. In query mode it still answers 403 with the header, and Query denials and other CloudWatch errors are unchanged.
- The access record and generated policies hold the version actions AWS needs for a versioned S3 read: a `HeadObject` with a version ID records `s3:GetObjectVersion`, and a `GetObjectAttributes` with one records `s3:GetObjectVersion` and `s3:GetObjectVersionAttributes`. The Service Reference omits them, so a generated policy lacked them and failed on AWS.

## [0.1.0] - 2026-11-09

The release stopped before its Homebrew cask and Testcontainers modules, which are available from 0.1.2.

### Added

- First release: one binary and a multi-arch image (`ghcr.io/sustinbebustin/understudy`, linux/amd64 and linux/arm64) that stand in for eighteen AWS services through `AWS_ENDPOINT_URL`: SQS, SNS, S3, DynamoDB and DynamoDB Streams, Kinesis Data Streams, Lambda, CloudWatch Logs, Secrets Manager, KMS, IAM, STS, EventBridge, EventBridge Scheduler, CloudWatch, API Gateway (HTTP and REST APIs), SSM Parameter Store, Step Functions and SES. Coverage is partial and listed operation by operation in `docs/coverage.md`; an unimplemented operation answers 501.
- Binaries for linux and darwin on amd64 and arm64, and a Homebrew cask: `brew install --cask sustinbebustin/tap/understudy`.
- One emulator clock for every AWS timer, a causal journal of every call and delivery with a web UI, fault injection, snapshots and opt-in persistence.
- Lambda functions run in AWS's base images through Docker, with DynamoDB Local behind DynamoDB. Docker Desktop on macOS is supported, not CI-tested.
- Testcontainers modules for Go (`github.com/sustinbebustin/understudy/testcontainers/go`), Python and Node (`testcontainers-understudy` on PyPI and npm), versioned with understudy, whose default image is the release's.
- `understudy iam policy` prints the least-privilege policy the recorded calls imply, and `--iam-enforce advise|enforce` evaluates identity, resource, trust and key policies.

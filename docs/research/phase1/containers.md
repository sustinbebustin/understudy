# Running Lambda functions through the Docker Engine API

Primary-source research for understudy phase 1: how to run Lambda zip and container-image functions as Docker containers using only `net/http` over the Engine socket, how the AWS Runtime Interface Emulator (RIE) actually behaves, and what the other emulators do.

## 0. How to read this document

- Every claim carries an inline URL to the file, doc page or line that owns it. GitHub links are pinned to the commit that was read (table below), so line anchors stay valid.
- **(observed Ex)** marks behavior I reproduced against a real daemon on 2026-10-08 (Docker Engine 29.6.2, API 1.55, containerd image store, Ubuntu 24.04, cgroup v2, `json-file` logging, amd64) using `public.ecr.aws/lambda/provided:al2023` (`sha256:e10c4765865b384b15eacc855a3f25ac61745d8dd1f510217deecf23b88fdbd5`) and `public.ecr.aws/lambda/python:3.13` (image id `sha256:0fddf7542198843bd5a488b17e35473659fdf69f0788c7b3563f0231edf3384d`). The experiment index is in section 13. Each observed claim is also tied to the source that explains it where one exists.
- **UNVERIFIED** marks anything I could not confirm from source or by running it. Podman, macOS, Docker Desktop, rootless Docker and SELinux were not available here; those sections are source/docs-only unless stated.
- Where docs and code disagree I say so and prefer what clients and daemons actually do.

## 1. Findings that change the design (read this first)

1. **The RIE in the AWS base images is not a faithful Lambda control plane, and two of its behaviors break understudy's contract.**
   - It never sets `X-Amz-Function-Error`: a handler error comes back as HTTP 200 with the raw `{"errorMessage":...}` body and `Content-Type: text/plain` (observed E4; open upstream issue [#20](https://github.com/aws/aws-lambda-runtime-interface-emulator/issues/20)).
   - A second concurrent invoke to the same container panics RIE with a nil dereference and the container exits with code 2 (observed E4; source [server.go#L663-L666](https://github.com/aws/aws-lambda-runtime-interface-emulator/blob/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/internal/lambda/rapidcore/server.go#L663-L666); open upstream fix [#133](https://github.com/aws/aws-lambda-runtime-interface-emulator/issues/133)).
   - It also hard-codes the invoked ARN to `arn:aws:lambda:us-east-1:012345678912:function:<name>` ([handlers.go#L143](https://github.com/aws/aws-lambda-runtime-interface-emulator/blob/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/internal/lambda/rie/handlers.go#L143)), reports `Memory Size == Max Memory Used` in REPORT lines (observed E3), and reports timeouts as a 200 text body `Task timed out after N.00 seconds` ([handlers.go#L199-L202](https://github.com/aws/aws-lambda-runtime-interface-emulator/blob/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/internal/lambda/rie/handlers.go#L199-L202)).
2. **The AWS base images work without RIE.** `/lambda-entrypoint.sh` only starts RIE when `AWS_LAMBDA_RUNTIME_API` is unset; if it is set it `exec`s `/var/runtime/bootstrap` directly (observed E2, script text in section 4.1). I ran the Python 3.13 image and a `provided.al2023` Go binary built with aws-lambda-go against my own Runtime API server and both worked (observed E6). Floci does exactly this: it runs a Runtime API server per container and sets `AWS_LAMBDA_RUNTIME_API` ([ContainerLauncher.java#L183-L184](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/launcher/ContainerLauncher.java#L183-L184), [#L227](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/launcher/ContainerLauncher.java#L227)). LocalStack replaces RIE with its own init binary ([docker_runtime_executor.py#L54](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/lambda_/invocation/docker_runtime_executor.py#L54)). SAM CLI and MiniStack use stock RIE ([lambda_container.py#L175-L177](https://github.com/aws/aws-sam-cli/blob/b82defc74a38ab7822aed3cda1d37b745620aee1/samcli/local/docker/lambda_container.py#L175-L177), [lambda_svc.py#L4009-L4014](https://github.com/ministackorg/ministack/blob/a63cb7ccc84261291fd41002256698f3de9719af/ministack/services/lambda_svc.py#L4009-L4014)).
3. **Container-image functions built `FROM` non-AWS bases have no RIE at all** ([images-create](https://docs.aws.amazon.com/lambda/latest/dg/images-create.html): such images must include a runtime interface client, RIE ships only in AWS base images). Only the "serve the Runtime API ourselves" design runs them without modifying the image.
4. **Host reachability needs the emulator to listen beyond 127.0.0.1.** `host.docker.internal:host-gateway` resolves to the docker0 bridge gateway IP (172.17.0.1 here), and a listener bound to `127.0.0.1` was unreachable from the container while `0.0.0.0` worked (observed E5; [container_operations.go#L78-L90](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/daemon/container_operations.go#L78-L90), [daemon_unix.go#L897-L912](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/daemon/daemon_unix.go#L897-L912)). The brief's default of binding 127.0.0.1 needs an additional listener (or an opt-in) for the Runtime API and the SDK endpoint the functions use.
5. **`HostConfig.Binds` silently creates missing host source directories (as root); `HostConfig.Mounts` with `Type: bind` fails instead.** Observed E7: a `Binds` entry for `/nonexistent/path/xyz` returned 201/204 and left a root-owned `/nonexistent` on the host (I removed it); the same path via `Mounts` returned `400 bind source path does not exist`. Use `Mounts` for code directories (cite for the error text: [swagger Mount.Source L397-L407](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L397-L407)).
6. **`PUT /containers/{id}/archive` fails with 400 `container rootfs is marked read-only` when `ReadonlyRootfs` is true** (observed E7). Code injection by tar copy and a read-only root filesystem are mutually exclusive; bind mounts and volumes are not affected.
7. **Python and Node-style RICs as PID 1 ignore SIGTERM.** `POST /containers/{id}/stop` took 10.2 s and ended with exit 137 on the Python image, while RIE (which handles SIGTERM) stopped in 0.25 s with exit 0 (observed E8). Function containers should be removed with `DELETE ...?force=1` (SIGKILL) or stopped with `t=0`.
8. **A Runtime API implementation must always send `Content-Type` on `/next`.** Omitting it made the Python 3.13 runtime exit 139 (SIGSEGV) at startup (observed E6); the cause is `curl_easy_getinfo(CURLINFO_CONTENT_TYPE)` returning NULL being passed to `set_content_type` in [aws-lambda-cpp runtime.cpp#L274-L276](https://github.com/awslabs/aws-lambda-cpp/blob/f2f0545cb31671b3dbf0c0f69949ff22317fb265/src/runtime.cpp#L274-L276). aws-lambda-go posts responses and errors with `Transfer-Encoding: chunked` and HTTP trailers (`Lambda-Runtime-Function-Error-Type`, `Lambda-Runtime-Function-Error-Body`) ([rapi_client.go#L28-L29](https://github.com/aws/aws-lambda-go/blob/41118539f90fa1989458560031d82a16b3686722/lambda/rapi_client.go#L28-L29), observed E6), so the server must decode chunked request bodies and read trailers.
9. **Log lines and the invocation response race at sub-millisecond scale** (observed E9: `response->log-line` delta between -0.1 and +0.3 ms over 15 invocations). Attributing log lines to an invocation by arrival order is unsafe without a barrier.
10. **Rootless Docker blocks container access to host loopback by default** (`--disable-host-loopback`, [dockerd-rootless.sh#L23-L24](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/contrib/dockerd-rootless.sh#L23-L24), [#L170-L173](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/contrib/dockerd-rootless.sh#L170-L173)) and silently ignores cgroup limit flags without cgroup v2 + systemd ([tips.md#L139-L145](https://github.com/docker/docs/blob/7ba25eeb0c4c594f79e6efadad1af5eaca0500a8/content/manuals/engine/security/rootless/tips.md#L139-L145)).

## 2. Docker Engine HTTP API, as an implementer needs it

### 2.1 Transport and endpoint discovery

- Default endpoint is `unix:///var/run/docker.sock` ([client_unix.go#L13](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/client/client_unix.go#L13)). `DOCKER_HOST` overrides it; `DOCKER_API_VERSION` pins a version and disables negotiation ([client_options.go#L93-L94](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/client/client_options.go#L93-L94), [Docker API docs](https://docs.docker.com/reference/api/engine/)).
- Host URL grammar: `scheme://addr`; for `tcp` the path is kept as a base path ([client.go#L380-L400](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/client/client.go#L380-L400)). The Go client sends a dummy `Host` header (`api.moby.localhost`) over unix sockets ([client.go#L100-L103](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/client/client.go#L100-L103)); any valid host header works with the daemon.
- The docker CLI resolves the context in this order: `-c`/`--context`, then `-H`/`DOCKER_HOST` (=> `default` context), then `DOCKER_CONTEXT`, then `currentContext` in `~/.docker/config.json`, else `default` ([cli.go#L456-L474](https://github.com/docker/cli/blob/e7c0f5c53c079d9c6775069fe5cd87715d228d0f/cli/command/cli.go#L456-L474)). A named context is stored at `<config dir>/contexts/meta/<sha256(name) hex>/meta.json` with shape `{"Name":..., "Metadata":..., "Endpoints":{"docker":{"Host":"unix://...","SkipTLSVerify":false}}}` ([metadatastore.go#L17-L36](https://github.com/docker/cli/blob/e7c0f5c53c079d9c6775069fe5cd87715d228d0f/cli/context/store/metadatastore.go#L17-L36), [store.go#L70-L74](https://github.com/docker/cli/blob/e7c0f5c53c079d9c6775069fe5cd87715d228d0f/cli/context/store/store.go#L70-L74), [store.go#L531-L533](https://github.com/docker/cli/blob/e7c0f5c53c079d9c6775069fe5cd87715d228d0f/cli/context/store/store.go#L531-L533), [endpoint.go#L4-L7](https://github.com/docker/cli/blob/e7c0f5c53c079d9c6775069fe5cd87715d228d0f/cli/context/endpoint.go#L4-L7), [config.go#L25-L29](https://github.com/docker/cli/blob/e7c0f5c53c079d9c6775069fe5cd87715d228d0f/cli/config/config.go#L25-L29)). Context resolution is what makes Colima, Docker Desktop on macOS and rootless installs work for people who never set `DOCKER_HOST`; a stdlib-only implementation can read `meta.json` itself (the directory name is the lowercase hex SHA-256 of the context name, per `digest.FromString(name).Encoded()`).
- Well-known socket locations, each from its owner:
  - Docker Desktop macOS: `~/.docker/run/docker.sock`, with an optional `/var/run/docker.sock` symlink created only if the user enables "Allow the default Docker socket to be used" (needs a password; `/var/run` is tmpfs, so a launchd task re-creates it) ([mac-permission-requirements.md#L42-L44](https://github.com/docker/docs/blob/7ba25eeb0c4c594f79e6efadad1af5eaca0500a8/content/manuals/desktop/setup/install/mac-permission-requirements.md#L42-L44), [settings.md#L355](https://github.com/docker/docs/blob/7ba25eeb0c4c594f79e6efadad1af5eaca0500a8/content/manuals/desktop/settings-and-maintenance/settings.md#L355)).
  - Rootless Docker: `$XDG_RUNTIME_DIR/docker.sock`, typically `/run/user/$UID/docker.sock` ([tips.md#L50-L51](https://github.com/docker/docs/blob/7ba25eeb0c4c594f79e6efadad1af5eaca0500a8/content/manuals/engine/security/rootless/tips.md#L50-L51)).
  - Colima >= 0.4.0: `$HOME/.colima/default/docker.sock` ([Colima FAQ](https://raw.githubusercontent.com/abiosoft/colima/main/docs/FAQ.md)).
  - OrbStack: creates a Docker context named `orbstack` and, with admin access, a `/var/run/docker.sock` symlink ([OrbStack docs](https://docs.orbstack.dev/docker/)); the socket path itself is UNVERIFIED (not stated on that page).
  - Podman: rootful `/run/podman/podman.sock`, rootless `$XDG_RUNTIME_DIR/podman/podman.sock` ([podman-system-service.1.md](https://github.com/containers/podman/blob/f239badbab04a32bea367d431479c630efbd9dec/docs/source/markdown/podman-system-service.1.md)).
- TCP daemons (superseded 2026-10-14: the brief scoped this to the unix socket; the dependency-policy consensus adds `tcp://`, plain and TLS). The Docker CLI reads them as follows, all at docker/cli `dfc520dc`:
  - `tcp://host` without a port is port 2375, with or without TLS, and an empty host is `localhost`; a path is kept as a base path ([opts/hosts.go#L99-L144](https://github.com/docker/cli/blob/dfc520dcc28994c4c699b9b219fd2f5a6bcec0ff/opts/hosts.go#L99-L144), [hosts_unix.go#L9](https://github.com/docker/cli/blob/dfc520dcc28994c4c699b9b219fd2f5a6bcec0ff/opts/hosts_unix.go#L9)). Port 2376 is only the default when no host is given at all with TLS on.
  - Any non-empty `DOCKER_TLS_VERIFY`, `0` included, turns on TLS with verification ([cli/flags/options.go#L53](https://github.com/docker/cli/blob/dfc520dcc28994c4c699b9b219fd2f5a6bcec0ff/cli/flags/options.go#L53), [#L143](https://github.com/docker/cli/blob/dfc520dcc28994c4c699b9b219fd2f5a6bcec0ff/cli/flags/options.go#L143), [#L150](https://github.com/docker/cli/blob/dfc520dcc28994c4c699b9b219fd2f5a6bcec0ff/cli/flags/options.go#L150)). The files are `ca.pem`, `cert.pem` and `key.pem` in `DOCKER_CERT_PATH`, else the config directory: `DOCKER_CONFIG`, else `~/.docker` ([options.go#L30-L34](https://github.com/docker/cli/blob/dfc520dcc28994c4c699b9b219fd2f5a6bcec0ff/cli/flags/options.go#L30-L34), [#L111](https://github.com/docker/cli/blob/dfc520dcc28994c4c699b9b219fd2f5a6bcec0ff/cli/flags/options.go#L111), [cli/config/config.go#L78-L80](https://github.com/docker/cli/blob/dfc520dcc28994c4c699b9b219fd2f5a6bcec0ff/cli/config/config.go#L78-L80)). The CLI drops a missing `cert.pem` or `key.pem` silently ([options.go#L156-L161](https://github.com/docker/cli/blob/dfc520dcc28994c4c699b9b219fd2f5a6bcec0ff/cli/flags/options.go#L156-L161)); `DOCKER_TLS` alone, TLS without verification, is a CLI-only variable.
  - dockerd serves through Go's `net/http`, which answers a plain HTTP request on a TLS listener with `400` and `Client sent an HTTP request to an HTTPS server.` ([server.go#L1999](https://github.com/golang/go/blob/go1.27.2/src/net/http/server.go#L1999)), so a client can tell "TLS required" from other 400s.
  - understudy follows these, except: it requires all three files and says which one it could not read, rather than handshaking without a client certificate the daemon then refuses; it refuses a base path; it does not read `DOCKER_TLS`, so a TLS daemon without `DOCKER_TLS_VERIFY` is reported as requiring TLS; and `ssh://` stays unsupported (a `DOCKER_HOST` warning that turns containers off).
  - Observed 2026-10-14 against `docker:dind` (Engine 29.9.0) from a container on the service's network: plain `tcp://docker:2375` and TLS `tcp://docker:2376` with the service's `/certs/client` both ran a `provided.al2023` zip function and DynamoDB Local; the dind server certificate names `docker`, `localhost` and the container ID only, so the TLS host in `DOCKER_HOST` must be the alias `docker`.

### 2.2 Version negotiation

- Every route may be prefixed `/v<major.minor>`. A prefix above the daemon's maximum returns `400 {"message":"client version 1.99 is too new. Maximum supported API version is 1.55"}`; below the minimum returns `400 {"message":"client version 1.39 is too old. Minimum supported API version is 1.40, please upgrade your client to a newer version"}` (observed E1; source [version.go#L59-L61](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/daemon/server/middleware/version.go#L59-L61)). Unprefixed use is deprecated ([swagger L48-L60](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L48-L60)).
- Negotiation: `HEAD /_ping` (fallback `GET`), read response header `Api-Version`, use `min(clientMax, serverMax)`; if the header is absent assume an old daemon and use the client's lowest supported version; fail if the server is below the client's minimum ([ping.go#L13-L31](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/client/ping.go#L13-L31), [ping.go#L100](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/client/ping.go#L100), [client.go#L337-L363](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/client/client.go#L337-L363)). `/_ping` is never versioned. The ping response is `200`, body `OK` (GET) and headers include `Api-Version`, `Builder-Version`, `Docker-Experimental`, `Swarm`, `Ostype` ([swagger L10765-L10862](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L10765-L10862); observed E1: `Api-Version: 1.55`, `Ostype: linux`, `Server: Docker/29.6.2 (linux)`).
- The moby client's own range is `MinAPIVersion = "1.40"` to `MaxAPIVersion = "1.56"` ([client.go#L111-L115](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/client/client.go#L111-L115)). Engine release to API range, latest rows ([API docs matrix](https://docs.docker.com/reference/api/engine/)): 29.8 max 1.55 (page links 1.56), 29.7/29.6 max 1.55, 29.5-29.3 max 1.54, **29.2/29.1/29.0 had min 1.44**, 29.0-29.1 max 1.52, 28.5 max 1.51 min 1.24. The docs page is internally inconsistent about 29.8 (matrix says 1.55, sample output says 1.56); my local 29.6.2 daemon reports max 1.55 / min 1.40 (observed E1).
- The server "ignores extra query parameters and request body properties" and the client must ignore extra response fields ([swagger L65-L69](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L65-L69)). Decode responses leniently (no `DisallowUnknownFields`).
- **Recommendation for the version window.** Target **1.44**, floor **1.41**:
  - 1.41 adds the `platform` query on `containers/create` and `HostConfig.CgroupnsMode` ([CHANGELOG v1.41](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/docs/CHANGELOG.md#L556)).
  - 1.42 adds `signal` on stop ([v1.42](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/docs/CHANGELOG.md#L450)).
  - 1.44 makes read-only bind mounts recursively read-only on kernel >= 5.12 (`BindOptions.ReadOnlyNonRecursive`/`ReadOnlyForceRecursive`), allows multiple `EndpointSettings` on create, and adds `DNSNames` ([v1.44](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/docs/CHANGELOG.md#L368)).
  - 1.45 changes `Aliases` in inspect to return exactly what create submitted ([v1.45](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/docs/CHANGELOG.md#L352)).
  - Podman's compat tree reports `CurrentAPI 1.44.0`, `MinimalAPI 1.24.0` ([version.go#L37-L48](https://github.com/containers/podman/blob/f239badbab04a32bea367d431479c630efbd9dec/version/version.go#L37-L48)), so 1.44 is also the natural target there. Podman "does not reject requests with an unsupported version set" ([podman-system-service.1.md#L9-L16](https://github.com/containers/podman/blob/f239badbab04a32bea367d431479c630efbd9dec/docs/source/markdown/podman-system-service.1.md)), so never rely on a 400 to detect a too-new prefix there; read `Api-Version` from `/_ping` and clamp.
  - Request `min(1.44, server)`; refuse to start Lambda execution below 1.41 with an error that states the detected version, the minimum, and the upgrade path.
- Reading `GET /info` (versioned) yields capability signals used elsewhere in this document: `SecurityOptions` (contains `name=rootless`, `name=selinux`, `name=seccomp,...`), `CgroupDriver`/`CgroupVersion`, `OperatingSystem` (`Docker Desktop` on Desktop - the exact string is UNVERIFIED here; mine returned `Ubuntu 24.04.4 LTS`), `OSType`, `Architecture`, `MemoryLimit`/`SwapLimit`/`PidsLimit` booleans, `LoggingDriver`, `Driver`, `DriverStatus` ([swagger SystemInfo L7289](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L7289); observed E7b).

### 2.3 Errors

### 2.4 Images: inspect, pull with progress, platform, auth

- `GET /images/{name}/json` returns the image config; `404` means absent. Fields used here: `Id`, `Os`, `Architecture`, `Size`, `RepoDigests`, `Config.{Entrypoint,Cmd,Env,WorkingDir,User,Labels,ExposedPorts}`. Since API 1.52 the daemon omits `Config.Cmd/Entrypoint/Env/Labels/User/WorkingDir` when unset instead of returning null/empty, so treat absent and empty as equal ([CHANGELOG v1.52](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/docs/CHANGELOG.md#L82-L90)). Since 1.49 a `platform` query (JSON-encoded OCI platform, e.g. `{"os":"linux","architecture":"arm64"}`) selects the variant of a multi-platform image ([CHANGELOG v1.49](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/docs/CHANGELOG.md#L177)); observed E7c: with the containerd image store, the same tag resolved to a different `Id` when asked for arm64.
- `POST /images/create?fromImage=<repo>&tag=<tag>&platform=linux/amd64` pulls ([swagger L10104](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L10104)): tag precedence is `tag` param over a tag in `fromImage`; a digest in `fromImage` wins and `tag` is ignored; **with no tag or digest it pulls all tags** (so always send a tag; default to `latest` explicitly).
- Response is `application/json` NDJSON. Message shape is `{stream, status, progressDetail{current,total,start,hidecounts,units}, id, errorDetail{code,message}, aux}` ([jsonstream/message.go#L8-L15](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/types/jsonstream/message.go#L8-L15), [progress.go#L4-L10](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/types/jsonstream/progress.go#L4-L10)). The legacy `error` and `progress` string fields are deprecated since 1.48 - use `errorDetail`/`progressDetail` ([CHANGELOG v1.48](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/docs/CHANGELOG.md#L190-L198)). A failure after the stream starts arrives as an `errorDetail` line in a `200` response, so the reader must scan every line, not just the status code (UNVERIFIED by experiment: I could not force a mid-stream failure; the shape is from the type above).

- Registry auth is client-side: send `X-Registry-Auth` = base64url(JSON `{"username","password","serveraddress"}` or `{"identitytoken"}`) per request ([swagger info L72-L90](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L72-L90)). For phase 1, anonymous pulls of `public.ecr.aws/lambda/*` and Docker Hub cover the brief's "pull images for Lambda and DynamoDB Local on first use"; private-registry auth should be an explicit later decision. **I accidentally printed `~/.docker/config.json` (it contains an ECR auth token) while probing; nothing from it is reproduced here.**
- AWS publishes each runtime as a multi-arch tag on `public.ecr.aws/lambda/<runtime>:<tag>`; LocalStack and SAM map runtimes to that registry ([docker_runtime_executor.py#L51](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/lambda_/invocation/docker_runtime_executor.py#L51), [lambda_image.py#L100-L115](https://github.com/aws/aws-sam-cli/blob/b82defc74a38ab7822aed3cda1d37b745620aee1/samcli/local/docker/lambda_image.py#L100-L115)). - **Platform**: Lambda `Architectures` `x86_64`/`arm64` map to Docker platform `linux/amd64`/`linux/arm64` ([docker_runtime_executor.py#L67-L85](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/lambda_/invocation/docker_runtime_executor.py#L67-L85); LocalStack offers `LAMBDA_IGNORE_ARCHITECTURE` to skip it). ### 2.5 Containers: create, start, wait, stop, kill, remove

`POST /containers/create?name=<n>&platform=<p>` ([swagger L8407](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L8407)):

- `name` must match `^/?[a-zA-Z0-9][a-zA-Z0-9_.-]+$` (at least two characters).
- Body is `ContainerConfig` plus `HostConfig` and `NetworkingConfig`; responds `201 {"Id":"<64 hex>","Warnings":[]}` ([swagger ContainerCreateResponse L6150](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L6150)). Surface `Warnings` in debug logs (it carries the platform-mismatch and swap-limit warnings).
- `POST /containers/{id}/start` takes no body ("starting container with non-empty request body was deprecated since API v1.22 and removed in v1.24", [container_routes.go#L296](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/daemon/server/router/container/container_routes.go#L296)).
- `POST /containers/{id}/wait?condition=not-running|next-exit|removed` returns `{"StatusCode":<int>,"Error":{"Message":...}}` ([swagger L9486](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L9486), [ContainerWaitResponse L6794](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L6794)). `not-running` (default) returns immediately on an already-stopped container; **`next-exit` must be issued before `start`** to avoid a race. Observed E7: `wait?condition=next-exit` issued before start returned `{"StatusCode":7}` for `exit 7`; the response headers are sent immediately so the server has registered the waiter ([CHANGELOG v1.30](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/docs/CHANGELOG.md#L830)). `condition=removed` also returns for `AutoRemove` containers ([CHANGELOG v1.34](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/docs/CHANGELOG.md#L764)).
- `POST /containers/{id}/stop?t=<seconds>&signal=<SIG>`: `204`, or `304` if already stopped; `t` is the grace before SIGKILL; `signal` was added in 1.42 ([swagger L8980](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L8980)). `POST /containers/{id}/kill?signal=SIGKILL` default signal `SIGKILL`, `409` if not running ([swagger L9054](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L9054)).
- `DELETE /containers/{id}?force=1&v=1`: `force` kills a running container first; `v` removes anonymous volumes; `409` for a running container without `force` ([swagger L9531](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L9531)). Use `force=1&v=1` for function containers.
- `GET /containers/{id}/json` yields `State{Status,Running,OOMKilled,ExitCode,Error,StartedAt,FinishedAt}`, `NetworkSettings.Ports` (published host ports), `NetworkSettings.Networks[net]{IPAddress,Gateway,Aliases,DNSNames}`, `Mounts[]` ([ContainerState L6084](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L6084), [MountPoint L255](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L255)). Since 1.52 the deprecated top-level `NetworkSettings.IPAddress`, `Gateway`, `MacAddress`, etc. are gone - always read `NetworkSettings.Networks[<name>]` ([CHANGELOG v1.52](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/docs/CHANGELOG.md#L92-L98)).
- `GET /containers/json?all=1&filters=<urlencoded JSON>`, e.g. `{"label":["understudy.dev/managed=true"]}`; filters are a JSON map of string to string-array ([swagger L8333](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L8333)).

### 2.6 Output capture: logs, attach, the multiplexed frame format

- `GET /containers/{id}/logs?stdout=1&stderr=1&follow=1&since=<unix>&timestamps=1&tail=all` is a plain chunked response (no connection upgrade, no `Content-Type` set by the daemon per the spec; observed header `Content-Type: application/vnd.docker.multiplexed-stream`) and **works only for containers whose logging driver is readable** (`json-file`, `local`, `journald`; `none`, `syslog`, `awslogs`, etc. return `501`) ([swagger L8680-L8700](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L8680-L8700), [logs.go#L48-L72](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/daemon/logs.go#L48-L72); observed E7 `501` for `LogConfig.Type=none`). The daemon default may be anything on a user's machine, so **set `HostConfig.LogConfig` explicitly** to `{"Type":"json-file","Config":{"max-size":"10m","max-file":"2"}}` on every function container (Floci applies log rotation to every container, [ContainerBuilder.java withLogRotation use at ContainerLauncher.java#L274](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/launcher/ContainerLauncher.java#L274)). `since` is a Unix timestamp parameter ([swagger L8719-L8728](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L8734-L8738)).
- **Multiplexed frame format** (applies when `Tty` is false, to both `logs` and `attach`) ([swagger L9306-L9343](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L9306-L9343)):

```
header := [8]byte{STREAM_TYPE, 0, 0, 0, SIZE1, SIZE2, SIZE3, SIZE4}   // SIZE = uint32 big endian
STREAM_TYPE: 0 stdin (delivered on stdout), 1 stdout, 2 stderr, 3 systemerr (an error from the daemon)
```

  Systemerr (type 3) terminates the stream and carries a daemon error ([stdcopy.go#L14-L19](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/pkg/stdcopy/stdcopy.go#L14-L19)). A frame is at most the writer's buffer (32 KiB read buffer in `StdCopy`, [stdcopy.go#L21-L26](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/pkg/stdcopy/stdcopy.go#L21-L26)); the json-file copier splits a single log line at 16 KiB ([copier.go#L20-L22](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/daemon/logger/copier.go#L20-L22)), so a long line arrives as several frames and the last one carries the newline. Reassemble per stream by buffering until `\n`.
  Verbatim first bytes from E3 (stderr frame of 96 bytes):

```
00000000: 0200 0000 0000 0060 3038 204f 6374 2032  .......`08 Oct 2
```

- With `timestamps=1` each payload is prefixed `2026-10-08T04:39:15.496885431Z ` (RFC 3339 nano, then one space) (observed E7). Use `since=<unix seconds>` to resume a dropped follow without replaying everything.
- **`attach`** (`POST /containers/{id}/attach?stream=1&stdout=1&stderr=1`) hijacks the HTTP connection: the daemon answers `101 UPGRADED` (if the client sent `Upgrade: tcp`/`Connection: Upgrade`) or `200`, then speaks the raw/multiplexed stream on the same socket ([swagger L9266-L9305](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L9266-L9305)). `net/http` can do it only via `http.Hijacker`-like manual dialing, so prefer `logs?follow=1` (a normal streaming GET). `logs?follow=1` returns everything since the container started (default `since=0`), so opening it right after `start` loses nothing.
- Pitfall: `Tty: true` changes the stream to raw (no framing) ([swagger L9344](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L9344)); never set it for function containers.

### 2.7 Events (exit, OOM and crash detection)

- `GET /events?filters=<urlencoded JSON>&since=<ts>&until=<ts>` is a streaming response. Since 1.52 it supports content negotiation (`application/x-ndjson` or RFC 7464 `application/json-seq`) and since 1.53 `application/jsonl` ([CHANGELOG v1.52](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/docs/CHANGELOG.md#L103), [v1.53](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/docs/CHANGELOG.md#L59)); the observed `Content-Type` on 1.55 was `application/jsonl` (E7). The legacy `status`, `id`, `from` fields are gone from 1.52, so read `Type`, `Action`, `Actor.ID`, `Actor.Attributes`, `scope`, `time`, `timeNano` ([swagger EventMessage L7797](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L7797)).
- Filter by `{"type":["container"],"event":["die","oom"],"label":["understudy.dev/managed=true"]}`. Observed E7 sequence for a short container: `create`, `start`, `die` (attribute `exitCode: "7"`), `destroy`. For an OOM kill the sequence is `oom` then `die` with `exitCode: "137"` (observed E7d).
- `Actor.Attributes` includes the **image's own labels** merged with the container's (the Lambda base image's `com.amazonaws.lambda.platform.*` labels appeared on every event and on `GET /containers/json`), so filter on understudy-specific label keys only (observed E7).
- Reconnect protocol: remember the last `timeNano`, reconnect with `since=<that>` after a drop; de-duplicate on `(Actor.ID, Action, timeNano)`. The events stream is the cheapest way to learn about container death for the whole warm pool with one connection (Floci uses a per-container exit watcher instead, [LambdaExitWatcher.java](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/launcher/LambdaExitWatcher.java)).

### 2.8 Networks

- `POST /networks/create` body `{"Name","Driver":"bridge","Labels":{...},"CheckDuplicate"}`; since 1.44 a duplicate name always fails with `409` and `CheckDuplicate` is deprecated (unversioned) ([CHANGELOG v1.44](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/docs/CHANGELOG.md#L368)); response `201 {"Id":"...","Warning":""}` (observed E7e). `DELETE /networks/{id}` -> `204`.
- Attach to a user-defined network at create time with `HostConfig.NetworkMode: "<net>"` plus `NetworkingConfig.EndpointsConfig{"<net>":{"Aliases":["understudy.internal","emu"]}}`. Observed E7e: another container on the same network resolved both aliases and the container name to `172.22.0.2`, and inspect returned `Aliases` = exactly the submitted list and `DNSNames` = `[name, aliases..., short id]`. Since 1.44 create accepts multiple endpoints ([CHANGELOG v1.44](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/docs/CHANGELOG.md#L368)).
- On the default `bridge` network containers cannot resolve each other by name, only by IP ([bridge.md#L51-L53](https://github.com/docker/docs/blob/7ba25eeb0c4c594f79e6efadad1af5eaca0500a8/content/manuals/engine/network/drivers/bridge.md#L51-L53)). Docker's embedded DNS provides no wildcards, so `bucket.s3.<alias>` style hostnames are not resolvable through aliases (see 8.5).

### 3.3 `Binds` versus `Mounts`

- `Binds` strings (`src:dst:ro,z`) are shorthand and **create missing host directories** (observed E7: root-owned `/nonexistent/path/xyz` appeared). `Mounts` objects are strict: a missing bind source returns `400` unless `BindOptions.CreateMountpoint` is true (default false) ([swagger Mount L397-L465](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L397-L465)).
- `Mounts` has no SELinux relabel option (`z`/`Z` exist only in the `Binds` string) ([swagger Binds L985-L1030](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L985-L1030) vs `BindOptions` in [Mount](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L430-L465)). On an SELinux-enforcing host (`SecurityOptions` contains `name=selinux`) a `Mounts` bind of a host directory is unreadable inside the container; use `Binds` with `:ro,z` there, after the implementation itself has verified the directory exists and is the emulator's own extraction directory (never a user-supplied path: `z` relabels the tree; Podman warns "Do not relabel system files and directories", [volume.md#L106-L135](https://github.com/containers/podman/blob/f239badbab04a32bea367d431479c630efbd9dec/docs/source/markdown/options/volume.md#L106-L135)). I did not run on SELinux; the failure mode is UNVERIFIED but follows from these docs.
- Since 1.44, read-only binds are recursive-read-only on kernel >= 5.12; set `BindOptions.ReadOnlyForceRecursive` only if you want a hard failure on older kernels ([CHANGELOG v1.44](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/docs/CHANGELOG.md#L368)).
- Podman's compat layer translates `Mounts` to `--mount` using only `type`, `source`, `target`, `ro`, `consistency`, `bind-propagation`, `bind-nonrecursive` for binds; `CreateMountpoint`, `ReadOnlyForceRecursive` and friends are not forwarded ([containers_create.go#L291-L345](https://github.com/containers/podman/blob/f239badbab04a32bea367d431479c630efbd9dec/pkg/api/handlers/compat/containers_create.go#L291-L345)).

### 3.4 Environment the emulator must supply (own-Runtime-API mode)

RIE fills several of these itself (section 4.3); with a self-hosted Runtime API nobody does, so the emulator owns the list. Reserved set from the docs ([configuration-envvars](https://docs.aws.amazon.com/lambda/latest/dg/configuration-envvars.html)): `_HANDLER`, `_X_AMZN_TRACE_ID` (set per invoke by the runtime from the `Lambda-Runtime-Trace-Id` header; absent for `provided`), `AWS_DEFAULT_REGION`, `AWS_REGION`, `AWS_EXECUTION_ENV` (set by each runtime's `bootstrap` shim, observed E2: `AWS_Lambda_provided.al2023`, `AWS_Lambda_python3.13`), `AWS_LAMBDA_FUNCTION_NAME`, `AWS_LAMBDA_FUNCTION_MEMORY_SIZE`, `AWS_LAMBDA_FUNCTION_VERSION`, `AWS_LAMBDA_INITIALIZATION_TYPE` (`on-demand`), `AWS_LAMBDA_LOG_GROUP_NAME`, `AWS_LAMBDA_LOG_STREAM_NAME`, `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_SESSION_TOKEN`, `AWS_LAMBDA_RUNTIME_API`, `LAMBDA_TASK_ROOT`, `LAMBDA_RUNTIME_DIR`. Unreserved: `LANG`, `PATH`, `LD_LIBRARY_PATH`, `TZ` (docs say `:UTC`; the images set `TZ=:/etc/localtime`, observed E2), `AWS_XRAY_*`.

- The AWS images already set `LANG`, `TZ`, `PATH`, `LD_LIBRARY_PATH`, `LAMBDA_TASK_ROOT=/var/task`, `LAMBDA_RUNTIME_DIR=/var/runtime` in the image `Env` (observed E2), so the emulator need only add the function-specific ones.
- `aws-lambda-go` reads `AWS_LAMBDA_LOG_GROUP_NAME`, `AWS_LAMBDA_LOG_STREAM_NAME`, `AWS_LAMBDA_FUNCTION_NAME`, `AWS_LAMBDA_FUNCTION_MEMORY_SIZE`, `AWS_LAMBDA_FUNCTION_VERSION` and `AWS_LAMBDA_MAX_CONCURRENCY` once at package init ([context.go#L51-L66](https://github.com/aws/aws-lambda-go/blob/41118539f90fa1989458560031d82a16b3686722/lambdacontext/context.go#L51-L66)); a missing memory size is tolerated but yields a zero in the context.
- Log stream naming convention used by both LocalStack and Floci: `YYYY/MM/DD/[<version>]<32-hex id>` ([execution_environment.py#L92-L93](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/lambda_/invocation/execution_environment.py#L92-L93), [ContainerLauncher.java#L221](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/launcher/ContainerLauncher.java#L221)).
- Credentials: Lambda sets the execution-role session credentials as env vars. RIE logs `Starting runtime without AWS_SESSION_TOKEN , Expected?: false` when the variable is empty (observed E3). For understudy the brief says the account is derived from the access key, so each function's `AWS_ACCESS_KEY_ID` must encode the function's account/role so the IAM access recorder can attribute calls (design item, not a container item).
- SDK redirection inside the function: LocalStack injects `AWS_ENDPOINT_URL=http://<host>:<port>` ([execution_environment.py#L169-L172](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/lambda_/invocation/execution_environment.py#L169-L172)) and Floci sets an SDK baseline env (region, credentials, endpoint) via `LaunchedContainerAwsEnv`. Also set `AWS_EC2_METADATA_DISABLED=true` to avoid IMDS probes (design recommendation, not exercised).
- Env size: the Lambda API enforces 4 KB total for user environment variables ([quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html)); the Docker API itself has no such cap, so this is a Lambda-API validation concern.

`/lambda-entrypoint.sh` (verbatim, E2):

```sh
#!/bin/sh
# Copyright 2020 Amazon.com, Inc. or its affiliates. All Rights Reserved.

if [ $# -ne 1 ]; then
  echo "entrypoint requires the handler name to be the first argument" 1>&2
  exit 142
fi
export _HANDLER="$1"

RUNTIME_ENTRYPOINT=/var/runtime/bootstrap

  exec /usr/local/bin/aws-lambda-rie $RUNTIME_ENTRYPOINT

  exec $RUNTIME_ENTRYPOINT

```

`/var/runtime/bootstrap` in `provided.al2023` (verbatim, E2): sets `AWS_EXECUTION_ENV="${AWS_EXECUTION_ENV-AWS_Lambda_provided.al2023}"`, then for `candidate in /var/task/bootstrap /opt/bootstrap` execs the first regular file with the handler as `$@`; if none exists it POSTs `/2018-06-01/runtime/init/error` with `Lambda-Runtime-Function-Error-Type: Runtime.InvalidEntrypoint` and body `{"errorMessage":"no bootstrap found at /var/task/bootstrap or /opt/bootstrap","errorType":"Runtime.InvalidEntrypoint"}` and exits 1. (So a layer can supply `/opt/bootstrap`.) In `python:3.13` it is a bash script that exports `AWS_EXECUTION_ENV=AWS_Lambda_python3.13`, honors `AWS_LAMBDA_EXEC_WRAPPER` (exit 127 if missing, 126 if not executable), and runs `/var/lang/bin/python3.13 /var/runtime/bootstrap.py`, which prepends `$LAMBDA_TASK_ROOT`, `/opt/python/lib/python3.13/site-packages`, `/opt/python` to `sys.path` and calls `awslambdaric.main([$LAMBDA_TASK_ROOT, $_HANDLER])` (observed E2). `/var/runtime/runtime-release` contains `LOGGING=amzn-stdout-tlv`; without `_LAMBDA_TELEMETRY_LOG_FD` set the Python runtime writes plain text to stdout, which is what I saw (observed E6).

Both images contain `/usr/local/bin/aws-lambda-rie` (9,293,986 bytes in `provided.al2023`, observed E2); the architecture inside matches the image's platform.

### 4.2 RIE: what the source says

All from [rie/](https://github.com/aws/aws-lambda-runtime-interface-emulator/tree/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/internal/lambda/rie) at the pinned commit unless noted.

- Binary selection: `main.go` runs the "managed instances" path when `AWS_LAMBDA_MAX_CONCURRENCY` is set, otherwise `rie.Run()` ([main.go](https://github.com/aws/aws-lambda-runtime-interface-emulator/blob/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/cmd/aws-lambda-rie/main.go)). Do not set `AWS_LAMBDA_MAX_CONCURRENCY` for standard functions.
- Flags: `--log-level` (or env `LOG_LEVEL`, default `info`), `--enable-init-caching`, `--runtime-api-address`, `--runtime-interface-emulator-address` (default `0.0.0.0:8080`) ([run.go#L25-L31](https://github.com/aws/aws-lambda-runtime-interface-emulator/blob/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/internal/lambda/rie/run.go#L25-L31)). The in-container Runtime API listens on `127.0.0.1:9001` (observed E3: `AWS_LAMBDA_RUNTIME_API=127.0.0.1:9001`; source default [sandbox_builder.go#L62](https://github.com/aws/aws-lambda-runtime-interface-emulator/blob/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/internal/lambda/rapidcore/sandbox_builder.go#L62)).
- Bootstrap resolution: with no extra args it uses `/var/task/bootstrap` if it is a file, else `/opt/bootstrap`, else `/var/runtime/bootstrap`; with args, `args[1:]` is the command and the **last arg is the handler** ([run.go#L107-L154](https://github.com/aws/aws-lambda-runtime-interface-emulator/blob/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/internal/lambda/rie/run.go#L107-L154)).
- Invoke endpoint: exactly `POST /2015-03-31/functions/function/invocations` (the function segment is literally `function`) ([http.go#L20](https://github.com/aws/aws-lambda-runtime-interface-emulator/blob/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/internal/lambda/rie/http.go#L20); SAM notes the same, [container.py#L500](https://github.com/aws/aws-sam-cli/blob/b82defc74a38ab7822aed3cda1d37b745620aee1/samcli/local/docker/container.py#L500)). The README documents `docker run -p 9000:8080 ...` and `curl -XPOST "http://localhost:9000/2015-03-31/functions/function/invocations" -d '{}'` ([README](https://github.com/aws/aws-lambda-runtime-interface-emulator/blob/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/README.md)).
- Request headers it reads: `X-Amz-Client-Context` (**base64-decoded; decoding failure => 500**, and an absent header decodes to empty and is fine), `X-Amzn-RequestId` (else a random UUID), `X-Amzn-Trace-Id`, `X-Amzn-Segment-Id`, `X-Amz-Tenant-Id`, `X-Amz-Cognito-Identity` (JSON with `cognitoIdentityId`/`cognitoIdentityPoolId`) ([handlers.go#L86-L141](https://github.com/aws/aws-lambda-runtime-interface-emulator/blob/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/internal/lambda/rie/handlers.go#L86-L141)).
- Env it reads: `AWS_LAMBDA_FUNCTION_TIMEOUT` (**default 300 s**, `panic` on a non-integer), `AWS_LAMBDA_FUNCTION_VERSION` (default `$LATEST`), `AWS_LAMBDA_FUNCTION_MEMORY_SIZE` (default 3008, used only in the REPORT line), `AWS_LAMBDA_FUNCTION_NAME` (default `test_function`), `AWS_LAMBDA_FUNCTION_HANDLER`/`_HANDLER`, `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_SESSION_TOKEN`; it also defaults `AWS_LAMBDA_LOG_GROUP_NAME=/aws/lambda/Functions` and `AWS_LAMBDA_LOG_STREAM_NAME=$LATEST` ([handlers.go#L94-L102](https://github.com/aws/aws-lambda-runtime-interface-emulator/blob/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/internal/lambda/rie/handlers.go#L94-L102), [#L217-L260](https://github.com/aws/aws-lambda-runtime-interface-emulator/blob/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/internal/lambda/rie/handlers.go#L217-L260)). The README lists only credentials, `AWS_REGION`, `AWS_LAMBDA_FUNCTION_TIMEOUT` and the three optional `AWS_LAMBDA_FUNCTION_*` variables as configuration.
- **Init is lazy**: the runtime is started on the first invoke (`initDone` flag), not when the container starts ([handlers.go#L105-L116](https://github.com/aws/aws-lambda-runtime-interface-emulator/blob/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/internal/lambda/rie/handlers.go#L105-L116); observed E3: the `bootstrap start` line and `INIT START(type: on-demand, phase: init)` appear only after the first POST).

- Status mapping in the handler: already reserved => 400; internal => 500; init/invoke failure => 502 with body; timeout => **200** with text `Task timed out after N.00 seconds` ([handlers.go#L157-L205](https://github.com/aws/aws-lambda-runtime-interface-emulator/blob/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/internal/lambda/rie/handlers.go#L157-L205)).

- Platform support: Linux only, x86-64 and arm64; no X-Ray; "does not emulate Lambda's orchestration, or security and authentication configurations" ([README "Level of support"](https://github.com/aws/aws-lambda-runtime-interface-emulator/blob/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/README.md)). The upstream repo is "generated from an internal AWS source of truth" and does not merge PRs ([README](https://github.com/aws/aws-lambda-runtime-interface-emulator/blob/3ccddd7d980cb7d0f12e8a44adce139b0176a2a5/README.md)), so the three issues below are not expected to be fixed by contribution.

### 4.4 Decision matrix: RIE or a Runtime API hosted by understudy

| Concern | RIE (stock, in image) | understudy-hosted Runtime API |
|---|---|---|
| Works on AWS base images | yes | yes (E6, `AWS_LAMBDA_RUNTIME_API` bypasses RIE in `lambda-entrypoint.sh`) |
| Works on non-AWS container images (no RIE inside) | no, unless RIE is injected via a bind mount of the `aws-lambda-rie` binary and `--entrypoint`, which the README documents ("Test an image without adding RIE to the image") but which still needs the user's image entrypoint to be wrapped | yes, they must already speak the Runtime API |
| `X-Amz-Function-Error`, error shapes, `Unhandled` vs timeout text | not provided; must be inferred by parsing the 200 body | full control (Floci always reports `Unhandled` for `/error`, [RuntimeApiServer.java#L879-L890](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/runtime/RuntimeApiServer.java#L879-L890)) |
| Concurrency safety | crashes on concurrent invoke | the emulator serializes per environment |
| Invoked ARN, version, account, deadline, trace id, client context, cognito identity | ARN hard-coded; deadline from its own clock; tenant/trace partly | all caller-supplied and correct |
| Host to container connectivity | needs a published or reachable port per container (impossible from macOS host to a bridge IP; [Docker Desktop](https://github.com/docker/docs/blob/7ba25eeb0c4c594f79e6efadad1af5eaca0500a8/content/manuals/desktop/features/networking/_index.md): "The `bridge` network cannot be reached from the host") | none: the container dials out to the emulator |
| Timeout enforcement and what happens after | RIE kills and restarts the runtime in the container (cheap) | emulator must kill the container (cold start next time) or implement a process-level reset it cannot do from outside |
| Init phase semantics (10 s init limit, suppressed init after failure) | partially emulated | emulator implements what it chooses |
| Extensions API (`/2020-01-01/extension/*`) | emulated by RIE | emulator must implement or declare unsupported; Floci implements register/next/init-error/exit-error ([RuntimeApiServer.java#L80-L92](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/runtime/RuntimeApiServer.java#L80-L92)) |
| Log lines START/END/REPORT | printed by RIE (not faithful) | emulator synthesizes them (also required for `LogType=Tail`) |
| Cost of cold start | ~one container start | same, plus a Runtime API listener per container |
| Maintenance | RIE is a moving binary baked into upstream images | owns ~600 lines of HTTP handling; spec is stable (`2018-06-01`) |

Both LocalStack and Floci converged on the hosted-API design; MiniStack and SAM CLI use stock RIE and inherit its limits. Stock RIE can remain a documented fallback for functions whose image cannot reach the host (rare) but is not recommended as the default.

### 4.5 Hosting the Runtime API: requirements (all verified against clients)

Endpoints and statuses from the AWS spec ([runtimes-api](https://docs.aws.amazon.com/lambda/latest/dg/runtimes-api.html)); where a client differs from the doc I note it.

- `GET /2018-06-01/runtime/invocation/next` -> `200`, blocking (clients set no timeout). Response headers: `Lambda-Runtime-Aws-Request-Id` (required), `Lambda-Runtime-Deadline-Ms` (**required and parsed as int64 by aws-lambda-go**, failure to parse is an error, [invoke_loop.go#L132-L138](https://github.com/aws/aws-lambda-go/blob/41118539f90fa1989458560031d82a16b3686722/lambda/invoke_loop.go#L132-L138)), `Lambda-Runtime-Invoked-Function-Arn`, optional `Lambda-Runtime-Trace-Id` (an X-Ray trace header string such as `Root=1-...;Parent=...;Sampled=1`; the runtime exports it as `_X_AMZN_TRACE_ID`, [invoke_loop.go#L67-L69](https://github.com/aws/aws-lambda-go/blob/41118539f90fa1989458560031d82a16b3686722/lambda/invoke_loop.go#L67-L69)), `Lambda-Runtime-Client-Context` and `Lambda-Runtime-Cognito-Identity` (JSON strings; unmarshal errors in aws-lambda-go fail the invoke, [invoke_loop.go#L140-L163](https://github.com/aws/aws-lambda-go/blob/41118539f90fa1989458560031d82a16b3686722/lambda/invoke_loop.go#L140-L163)), `Lambda-Runtime-Aws-Tenant-Id`, and the newer `Lambda-Runtime-Invocation-Id` ("optional for backward compatibility"; if the runtime echoes it back on `/response`/`/error` and it does not match, reply `400 InvalidInvocationId`) ([runtimes-api](https://docs.aws.amazon.com/lambda/latest/dg/runtimes-api.html)).
- **Always send `Content-Type: application/json` on `/next`.** Without it the Python RIC's native client segfaults (exit 139); see finding 8. Both of my mock variants differed only in this header: with it, 3 of 3 invocations completed; without it the container exited 139 with zero polls completed (observed E6).
- `POST /2018-06-01/runtime/invocation/<id>/response` -> `202` with body `{"status":"OK"}` (Floci: `Content-Type: application/json`, [RuntimeApiServer.java#L930-L934](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/runtime/RuntimeApiServer.java#L930-L934)). aws-lambda-go treats anything but `202` as a failure ([rapi_client.go#L165-L167](https://github.com/aws/aws-lambda-go/blob/41118539f90fa1989458560031d82a16b3686722/lambda/rapi_client.go#L165-L167)). **The request body is chunked** (observed headers E6: `Transfer-Encoding: chunked`, `Trailer: Lambda-Runtime-Function-Error-Body,Lambda-Runtime-Function-Error-Type`, `Content-Type: application/json`). Go's `net/http` server decodes this natively and exposes trailers on `r.Trailer` after the body is fully read; a hand-rolled parser must too. If the trailer `Lambda-Runtime-Function-Error-Type` is present after a "successful" body, the runtime failed mid-stream and the invocation is an error.
- `POST .../<id>/error` -> `202`. Headers: `Lambda-Runtime-Function-Error-Type` (any string; recommended `Category.Reason`, normalized to `Runtime.Unknown`/`Function.Unknown` when malformed), optional `Lambda-Runtime-Function-Xray-Error-Cause` (JSON; Go runtime sends `{"working_directory":..,"exceptions":[...],"paths":[]}`, observed E6). Body `{"errorMessage","errorType","stackTrace"}`. **Report every `/error` to the Invoke caller with `X-Amz-Function-Error: Unhandled`**: the Python and Node RICs do not even send the error-type header on this path and the Java RIC's vocabulary overlaps with "Runtime.*" so keying on the header misclassifies ([Floci issue #3314 rationale in code](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/runtime/RuntimeApiServer.java#L869-L890)). The Invoke API documents the `X-Amz-Function-Error` header and `200` status for function errors ([API_Invoke](https://docs.aws.amazon.com/lambda/latest/api/API_Invoke.html)); `Handled` is legacy.
- `POST /2018-06-01/runtime/init/error` -> `202`; means initialization failed and the runtime will exit without ever polling `/next`. The pending invocation that triggered the cold start must be failed with the posted payload (Floci marks the environment "faulted" and never reuses it, [RuntimeApiServer.java#L896-L925](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/runtime/RuntimeApiServer.java#L896-L925)). Observed E2: the `provided.al2023` shim posts it with `Runtime.InvalidEntrypoint` when `/var/task/bootstrap` is missing.
- Status codes the clients tolerate: `next` must be exactly `200` for aws-lambda-go ([rapi_client.go#L122-L124](https://github.com/aws/aws-lambda-go/blob/41118539f90fa1989458560031d82a16b3686722/lambda/rapi_client.go#L122-L124)). Anything else makes the loop exit and the container die.
- **Process crash detection comes from outside**: a runtime that dies cannot post an error. Watch the container (`die` event or `wait`) and fail in-flight invocations with the AWS-shaped `Runtime.ExitError` payload `{"errorType":"Runtime.ExitError","errorMessage":"RequestId: <id> Error: Runtime exited with error: exit status <n>"}` (RIE and Floci produce this exact wording, observed E4 and [RuntimeApiServer.java#L1015-L1060](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/runtime/RuntimeApiServer.java#L1015-L1060)); the AWS log format for the same event is `RequestId: <id> Error: Runtime exited without providing a reason` + `Runtime.ExitError` ([lifecycle docs](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)).
- **Identity of the calling container.** The Runtime API address is a bare `host:port` that every client concatenates into `http://<addr>/2018-06-01/...` (aws-lambda-go: [rapi_client.go#L56-L61](https://github.com/aws/aws-lambda-go/blob/41118539f90fa1989458560031d82a16b3686722/lambda/rapi_client.go#L56-L61)), so a path prefix might work for some clients; the Python RIC passes the address to `http.client.HTTPConnection(addr)` ([lambda_runtime_client.py#L82](https://github.com/aws/aws-lambda-python-runtime-interface-client/blob/eec20f67d69b5e7a7918f3eeda9b5020eeb1c147/awslambdaric/lambda_runtime_client.py#L82)) which cannot take a path, and its native client builds a URL from the same string. Treat a path-prefix scheme as UNVERIFIED and unsafe. Source-IP demultiplexing fails on Docker Desktop (the host sees the VM/backend, [Docker Desktop networking](https://github.com/docker/docs/blob/7ba25eeb0c4c594f79e6efadad1af5eaca0500a8/content/manuals/desktop/features/networking/_index.md): "All outbound container network traffic originates from the `com.docker.backend` process"). **One listener port per environment** is the portable choice (Floci allocates a port per environment and releases it on any launch failure, [ContainerLauncher.java#L184-L195](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/launcher/ContainerLauncher.java#L184-L195)); LocalStack instead puts an `executor_id` in the URL because its own init binary builds the URLs ([executor_endpoint.py#L76-L99](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/lambda_/invocation/executor_endpoint.py#L76-L99)).
- **Deadline header and the emulator clock.** Runtimes compute remaining time as `Lambda-Runtime-Deadline-Ms - now()` against the **container's wall clock** (Python `get_remaining_time_in_millis()` returned 5000 then 4960 for a 5 s deadline, observed E6). If the brief's controllable clock is frozen or scaled, the header must still be wall-clock milliseconds, or user code sees nonsensical remaining time. Enforcing the function timeout itself is a design decision (open question 3).

### 4.6 Init-phase and failure semantics to copy from AWS

- Init is limited to 10 s; if it does not finish, Lambda retries Init at the first invocation using the function's configured timeout (the 10 s limit does not apply to provisioned concurrency) ([lifecycle docs](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)).
- After a runtime crash or timeout during an invoke, Lambda performs a reset (shutdown, then a "suppressed init" before the next invocation); `/tmp` is not cleared across the reset ([lifecycle docs](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)). Killing and recreating the container is the faithful-enough local analogue but clears `/tmp` (a documented deviation to note); RIE's in-container runtime restart keeps it (observed E4).
- Environments are recycled "every few hours" even under constant use ([lifecycle docs](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)); optional for a local emulator.

### 5.1 Strategies, with evidence

Recommendation: default to the bind mount when the emulator runs on the host (which is the brief's primary topology), with the tar-copy path (without `ReadonlyRootfs`) as the fallback chosen automatically when `/proc/self/cgroup`/mountinfo shows the emulator is itself in a container or the bind source is not under a host-visible path. A named-volume path can wait.

### 5.2 Zip extraction hygiene (container-relevant parts)

- The extraction directory is shared with the container, so it must contain only the function's code: extract into a per-version content-addressed directory (MiniStack caches by code sha and mounts read-only: [lambda_svc.py#L402-L414](https://github.com/ministackorg/ministack/blob/a63cb7ccc84261291fd41002256698f3de9719af/ministack/services/lambda_svc.py#L402-L414)).
- Lambda requires that "the default Lambda user must be able to read all the files required to run your function code" ([images-create](https://docs.aws.amazon.com/lambda/latest/dg/images-create.html)); chmod extracted files to at least `0644` and directories to `0755` (and executables like `bootstrap` to `0755`) because zip entries from some tools carry mode 0 or 0600, and run containers as non-root only when the emulator also normalizes modes. LocalStack chmods `/var/task` and `/opt` to 0755 when layers are present ([docker_runtime_executor.py#L381-L387](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/lambda_/invocation/docker_runtime_executor.py#L381-L387)).
- Layers (up to 5, [quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html)) are merged into `/opt` in order; mount the merged tree read-only at `/opt` the same way as `/var/task` (Floci copies each layer into `/opt` in order, [ContainerLauncher.java#L398-L411](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/launcher/ContainerLauncher.java#L398-L411)). Package size limits: 50 MB zipped via API, 250 MB unzipped including layers ([quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html)).
- Zip-slip and size-bomb checks are the extractor's job (brief), but the container boundary adds one more rule: never let a symlink inside the extracted tree point outside the extraction root before bind-mounting it, because the bind mount follows the host filesystem view (SAM resolves top-level symlinks specially for the same reason, [container.py#L317-L335](https://github.com/aws/aws-sam-cli/blob/b82defc74a38ab7822aed3cda1d37b745620aee1/samcli/local/docker/container.py#L317-L335)).

### 5.3 Container-image functions

- Lambda's `ImageConfig` has `EntryPoint` (string array, 0-1500 items), `Command` (0-1500 items) and `WorkingDirectory` (<= 1000 chars) that "override the container image Dockerfile settings" ([API_ImageConfig](https://docs.aws.amazon.com/lambda/latest/api/API_ImageConfig.html)); map them 1:1 to Docker create's `Entrypoint`, `Cmd`, `WorkingDir`. SAM merges them as: `Cmd = ImageConfig.Command or image Cmd`; `Entrypoint = RIE + (ImageConfig.EntryPoint or image Entrypoint)`; `WorkingDir = ImageConfig.WorkingDirectory or image WorkingDir` ([lambda_container.py#L117-L137](https://github.com/aws/aws-sam-cli/blob/b82defc74a38ab7822aed3cda1d37b745620aee1/samcli/local/docker/lambda_container.py#L117-L137)). In hosted-API mode only the override merge is needed because there is no RIE to prepend.
- Requirements the emulator can validate at `CreateFunction`: Linux only; one architecture per image; OCI or Docker v2 schema 2 manifest; uncompressed size <= 10 GB; manifest <= ~25,400 bytes recommended; "container image settings size" <= 16 KB ([images-create](https://docs.aws.amazon.com/lambda/latest/dg/images-create.html), [quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html)). Image functions go through `Pending -> Active/Failed/Inactive` states ([images-create "Function lifecycle"](https://docs.aws.amazon.com/lambda/latest/dg/images-create.html)): pulling and inspecting the image is the natural `Pending` work, a pull or architecture failure is `Failed`.
- The function's handler is not configured for image functions (`config.handler is None` for image lambdas, [execution_environment.py#L173-L175](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/lambda_/invocation/execution_environment.py#L173-L175)); SAM sets `AWS_LAMBDA_FUNCTION_HANDLER` from `Command[0]` for RIE's benefit ([lambda_container.py#L125-L128](https://github.com/aws/aws-sam-cli/blob/b82defc74a38ab7822aed3cda1d37b745620aee1/samcli/local/docker/lambda_container.py#L125-L128)); not needed in hosted-API mode.
- Registry names: a Lambda `Code.ImageUri` normally points at ECR (`<acct>.dkr.ecr.<region>.amazonaws.com/<repo>:<tag>`); locally that cannot be pulled without AWS credentials. Floci rewrites AWS-shaped ECR URIs to its own loopback registry ([ContainerLauncher.java#L206-L208](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/launcher/ContainerLauncher.java#L206-L208)); LocalStack documents container-image support via a local ECR registry ([Lambda docs](https://docs.localstack.cloud/aws/services/lambda/)). understudy has no ECR in phase 1: resolve `ImageUri` against the local image store first (user did `docker build -t <uri>`), pull only for non-ECR hosts, and fail with an error that says "ECR is not emulated in phase 1; tag your local image as `<ImageUri>` or use a registry reachable without AWS credentials". (Design recommendation.)

### 5.4 Hot reload from a local directory

- Mechanism used by LocalStack and Floci: bind-mount the host directory read-only at `/var/task` and restart the runtime when files change ([docker_runtime_executor.py#L322-L335](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/lambda_/invocation/docker_runtime_executor.py#L322-L335), [ContainerLauncher.java#L298-L301](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/launcher/ContainerLauncher.java#L298-L301)). LocalStack's configuration surface: `S3Bucket="hot-reload"` and `S3Key=<absolute host path>`, "absolute paths on the host running the LocalStack container", with `$ENV` placeholder expansion; detection delay up to 700 ms (500 ms quiet period + up to 200 ms); "The runtime restarts after each change, so initialization code outside the handler reruns. The container is not restarted" ([LocalStack hot reload docs](https://docs.localstack.cloud/aws/developer-tools/lambda-tools/hot-reloading/)).
- Implication for the hosted-API design: a bind mount alone does not reload code already imported by a warm Python/Node process; the emulator must either (a) kill and recreate the environment (~590 ms cold start for Python, observed E10) when it detects a change, or (b) watch with `fsnotify`-like polling itself (stdlib has no inotify; polling `os.Stat` mtimes/size on the extracted tree is stdlib-only) and recycle environments for that function. A change to the directory must also advance the function's `CodeSha256`/`LastModified` only if understudy defines hot-reload that way (design choice).
- Platform notes from LocalStack's hot reload page: Docker Desktop on macOS needs the folder under a shared path; Rancher Desktop needs `LOCALSTACK_FILE_WATCHER_STRATEGY=polling`; Colima needs `--vm-type vz --mount-type virtiofs` ([hot reload docs](https://docs.localstack.cloud/aws/developer-tools/lambda-tools/hot-reloading/)). With emulator-in-Docker the host directory must be visible at the **same absolute path** inside the emulator container (or understudy must translate paths using `GET /containers/<self>/json` `.Mounts[].Source/Destination`, [MountPoint](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L255); the translation approach is a recommendation I did not see in the other emulators).

## 6. Warm pool, concurrency, timeouts, reaping

### 6.1 What AWS specifies

- One environment serves one request at a time (the Runtime API is an iterator: `next`, then `response`/`error`, then `next`); concurrent requests get separate environments. Managed Instances are the exception and need `AWS_LAMBDA_MAX_CONCURRENCY` ([runtimes-api](https://docs.aws.amazon.com/lambda/latest/dg/runtimes-api.html)).
- After an invocation the environment is frozen and kept "for some time" for reuse (a "warm start"); `/tmp` and in-memory state persist across reuse; environments are retired every few hours ([lifecycle docs](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)). The idle duration is not specified, so any local default is a product choice.
- Limits: 1,000 concurrent executions per account and region by default, 1,000 new environments per function every 10 s, sync invocation rate capped at 10x concurrency, async unlimited by rate ([quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html)). Exceeding function or account concurrency returns `TooManyRequestsException` (HTTP 429, `retryAfterSeconds`) with reasons `ReservedFunctionConcurrentInvocationLimitExceeded` / `ConcurrentInvocationLimitExceeded` ([API_Invoke](https://docs.aws.amazon.com/lambda/latest/api/API_Invoke.html)).
- Payload ceilings: 6 MB sync request and response, 1 MB async ([API_Invoke](https://docs.aws.amazon.com/lambda/latest/api/API_Invoke.html)); `X-Amz-Client-Context` <= 3,583 bytes base64 ([API_Invoke](https://docs.aws.amazon.com/lambda/latest/api/API_Invoke.html)).

### 6.2 What the other emulators do

| | Reuse key | Idle reaping | Start throttle | Notes |

### 6.3 Recommended pool contract

- **State machine** (illegal states unrepresentable): `Starting -> Idle <-> Busy -> Draining -> Gone`, `Starting|Busy -> Faulted -> Gone`. `Busy` is entered only by an exclusive reservation; nothing multiplexes two invocations onto one environment.
- **Pool key** = hash of everything that appears in the container spec: function ARN + version/qualifier resolved to a published version or `$LATEST`, `CodeSha256` (or image digest), runtime/image, architecture, memory, timeout, handler, ImageConfig, layers (ordered ARNs + their SHAs), env vars, role/credential identity, log config, VPC/filesystem config, hot-reload path. Any `UpdateFunctionConfiguration`/`UpdateFunctionCode` bumps a generation counter; idle containers of old generations are drained immediately; busy ones finish their invoke and are not returned to the pool (Floci's "epoch" and MiniStack's fix demonstrate both needs).
- **Cold start path**: create Runtime API listener -> create container -> start -> wait for the first `GET /next` (this is "init done"; bounded by 10 s, then by the function timeout for the first invocation per [lifecycle docs](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)) -> deliver the event. A `/init/error` or an exit before the first `/next` fails the invocation with the posted/derived payload and condemns the environment.
- **Throttle starts** with a semaphore (LocalStack uses 16; Docker Desktop was observed to degrade badly under burst creates: Floci reports `docker create` ballooning to ~80 s when many containers copy code concurrently, [ContainerLauncher.java#L304-L309](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/launcher/ContainerLauncher.java#L304-L309)). Make the number configurable from day one.
- **Concurrency limits** are enforced by understudy before any container work (account and per-function reserved concurrency; stored settings per the brief) and return the 429 shape above; the Lambda researcher owns the exact API semantics.
- **Idle reaping** timers measure *idle wall time since the last release*. Using the controllable emulator clock for this would make a frozen clock keep containers forever and a fast-forwarded clock kill them instantly, but it would also let tests exercise "environment expired" deterministically. Open question 3 in section 13.
- **Max pool size** needs a global cap (host RAM is finite: each environment reserves its configured memory as a cgroup limit, not up front). Floci's `max(4, CPUs)` per function and optional LRU total cap are reasonable defaults.
- **Draining** an environment = remove its Runtime API listener from the lookup table first (so a late `/response` from a half-dead runtime gets 404/400, not delivered to the next invocation), then `DELETE ?force=1&v=1`.

### 6.4 Timeouts

- AWS timeout semantics: the configured timeout covers the whole Invoke phase; on timeout Lambda resets the environment (runtime shut down; next invoke re-inits); REPORT shows `Status: timeout` ([lifecycle docs](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)). The exact synchronous payload for a timeout is not in the pages I read (UNVERIFIED; the Lambda API researcher should pin it).
- RIE's own timeout path restarts the runtime inside the container and answers 200 with `Task timed out after N.00 seconds` (observed E4); with a hosted Runtime API the only portable reset is to kill the container.
- Late replies: after a timeout the old runtime may still POST `/response` for the abandoned request id; reject it (Lambda "rejects with `400 InvalidInvocationId`" when the invocation id header mismatches the active invocation, [runtimes-api](https://docs.aws.amazon.com/lambda/latest/dg/runtimes-api.html)). Since the container is killed this is moot, but the listener must not deliver stale replies if the pool ever recycles instead of killing.
- Init-phase deadline: 10 s on-demand, then re-attempted under the function timeout (lifecycle docs above).

| Observation | Source | Caller-visible result |
|---|---|---|
| Runtime POSTs `/invocation/<id>/error` | Runtime API | 200 + `X-Amz-Function-Error: Unhandled` + payload |

## 7. Function logs to CloudWatch Logs

- **Capture**: one `GET /containers/{id}/logs?follow=1&stdout=1&stderr=1&timestamps=1` stream per environment, opened immediately after `start` (before the first invocation) so init output is not lost; demultiplex per 2.6; reassemble lines per stream. stdout and stderr are copied by separate goroutines ([copier.go#L46-L53](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/daemon/logger/copier.go#L46-L53)), so cross-stream ordering is not guaranteed; the Docker timestamp is receive time on the daemon, not emit time.
- **Destination**: group `/aws/lambda/<function>`, stream `YYYY/MM/DD/[<version>]<id>` per execution environment (both LocalStack and Floci; env vars from 3.4). This matches AWS naming; one stream per environment means continuous capture is enough for plain delivery.
- **Per-invocation attribution** is needed for the `START`/`END`/`REPORT` lines and `LogType=Tail` (last 4 KB, base64 in `X-Amz-Log-Result`, [API_Invoke](https://docs.aws.amazon.com/lambda/latest/api/API_Invoke.html)). Observed E9 (Python 3.13, json-file): the log line reached a follow-reader between 0.2 and 0.5 ms after `print(flush=True)` and the response reached the Runtime API within the same 0.2-0.4 ms, so `response -> log-line` was between -0.1 and +0.3 ms. A reader that stamps "invocation done" on `/response` will mis-assign the last lines. Options, in increasing cost: (1) after `/response`, wait a short settle time (LocalStack exposes `LAMBDA_INIT_POST_INVOKE_WAIT_MS` for exactly this, [config.py#L1099](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/config.py#L1099)); (2) write a unique sentinel line into the container's stdout through `docker exec`-style exec on `/proc/1/fd/1` and wait for it to appear in the stream, then cut the window (exact-but-costly; not exercised here); (3) `since`/timestamp windows. Unflushed runtime stdout buffers can still arrive late; real Lambda has the same property.
- **Synthesized platform lines** (formats from the lifecycle docs). Old style:

```
START RequestId: c3252230-c73d-49f6-8844-968c01d1e2e1 Version: $LATEST
END RequestId: c3252230-c73d-49f6-8844-968c01d1e2e1
REPORT RequestId: c3252230-... Duration: 933.59 ms Billed Duration: 934 ms Memory Size: 128 MB Max Memory Used: 9 MB
```

  New style adds `Status: error Error Type: Runtime.ExitError` or `Status: timeout` to `REPORT`, and `Init Duration: x ms` appears on cold starts ([lifecycle docs](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)). RIE's own REPORT has `Max Memory Used == Memory Size` (observed E3), so do not forward RIE's lines. `Max Memory Used` can come from cgroup stats (`GET /containers/{id}/stats?stream=false`, [swagger L8830](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L8830)) or be omitted/estimated (design choice).
- **Runtime log framing**: the Python image advertises `LOGGING=amzn-stdout-tlv` in `/var/runtime/runtime-release` (observed E2) which is the real service's framed telemetry format, used only when `_LAMBDA_TELEMETRY_LOG_FD` is provided; without it the runtime prints plain text lines (observed E6). `AWS_LAMBDA_LOG_FORMAT` (`JSON`/`Text`) and `AWS_LAMBDA_LOG_LEVEL` are read by the Python RIC ([bootstrap.py#L30-L33](https://github.com/aws/aws-lambda-python-runtime-interface-client/blob/eec20f67d69b5e7a7918f3eeda9b5020eeb1c147/awslambdaric/bootstrap.py#L30-L33)) and by LocalStack's env builder ([execution_environment.py#L155-L159](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/lambda_/invocation/execution_environment.py#L155-L159)), so a function's `LoggingConfig` can be honored by env alone.
- The brief's "log group and stream per trace" for application logs is separate from this platform log and is the CloudWatch Logs researcher's topic.

### 8.2 Facts behind the matrix

- `host-gateway` is substituted by the daemon from `HostGatewayIPs`, which defaults to the IPv4 (and IPv6 if present) gateway of the **default bridge network** unless `--host-gateway-ip` / `host-gateway-ips` is configured; with none available the create fails with `unable to derive the IP value for host-gateway` ([container_operations.go#L82-L90](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/daemon/container_operations.go#L82-L90), [daemon_unix.go#L897-L912](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/daemon/daemon_unix.go#L897-L912), [dockerd.md#L845-L855](https://github.com/docker/cli/blob/e7c0f5c53c079d9c6775069fe5cd87715d228d0f/docs/reference/dockerd.md#L845-L855), [container_run.md#L1280-L1288](https://github.com/docker/cli/blob/e7c0f5c53c079d9c6775069fe5cd87715d228d0f/docs/reference/commandline/container_run.md#L1280-L1288)). Observed E5: `/etc/hosts` in the container had `172.17.0.1 host.docker.internal`.
- Binding matters: the same container reached a host server bound to `0.0.0.0:18772` (`204`) and failed against `127.0.0.1:18771` (`curl: (7) Failed to connect ... Could not connect to server`) (observed E5). Because the brief's default is `127.0.0.1`, the Runtime API (and the AWS endpoint injected into functions) need their own listener bound to the bridge gateway IP (read from `GET /networks/bridge` `IPAM.Config[].Gateway`, or from the container's own `NetworkSettings.Networks.bridge.Gateway`, observed E7: `172.17.0.1`) and, on user-defined networks, that network's gateway. Binding `0.0.0.0` is simplest and exposes the unauthenticated Runtime API on every interface; prefer the specific bridge addresses on Linux. For Docker Desktop and Podman machine the listener must be reachable from the VM's outbound path (UNVERIFIED whether loopback is enough on Desktop; binding the host's non-loopback interfaces is the safe fallback).
- Firewalls: Floci logs this hint on native Linux, and I take it as a lead rather than a verified fact: "On Linux hosts running UFW with the default 'INPUT DROP' policy, this path is blocked and Lambda invocations will time out ... run: 'sudo ufw allow in on docker0'" ([DockerHostResolver.java#L78-L88](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/core/common/docker/DockerHostResolver.java#L78-L88)). I did not reproduce a firewall block here.
- Docker Desktop's backend makes outbound container connections as host-side connections from `com.docker.backend`, and `bridge` networks are not reachable from the host ([Desktop networking](https://github.com/docker/docs/blob/7ba25eeb0c4c594f79e6efadad1af5eaca0500a8/content/manuals/desktop/features/networking/_index.md)). So on macOS, RIE mode needs published ports (`127.0.0.1:<ephemeral>`), while hosted-API mode needs no inbound path to containers at all.
- On the default bridge, containers resolve names only via IP ([bridge.md#L51-L53](https://github.com/docker/docs/blob/7ba25eeb0c4c594f79e6efadad1af5eaca0500a8/content/manuals/engine/network/drivers/bridge.md#L51-L53)); in emulator-in-Docker mode create (or reuse) a user-defined network for function containers and use the alias route verified in E7e.

### 8.3 Emulator inside Docker

- Detect "am I in a container": `/.dockerenv`, `/run/.containerenv`, a `container` env var, `/proc/1/cgroup` markers, `/proc/self/mountinfo` overlay paths ([ContainerDetector.java#L12-L64](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/core/common/docker/ContainerDetector.java#L12-L64)).
- Identify own container: the hostname (`/etc/hostname`) is the short container id by default; `GET /containers/<hostname>/json` returns its `NetworkSettings.Networks` and `Mounts` ([CurrentContainerNetworkResolver.java#L19-L87](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/core/common/docker/CurrentContainerNetworkResolver.java#L19-L87)). `Mounts[].Source` is the **host-side** path, which enables bind-mount path translation for hot reload or shared state directories ([MountPoint](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/swagger.yaml#L255)).
- Function containers: `NetworkMode=<emulator's network>`, optional alias, runtime API address `<emulator container IP>:<per-env port>` (container to container, no published ports). The socket mount `/var/run/docker.sock` gives the emulator root-equivalent power on the host; the README must say so (LocalStack requires the same mount, [Lambda docs](https://docs.localstack.cloud/aws/services/lambda/)).
- Apple Silicon note: images pulled by the sibling are for the daemon's platform; `platform=` must be sent as in 2.4.

### 8.4 Diagnosing "the function cannot reach the emulator"

The dominant failure mode of every emulator in this study is a silent timeout when the Runtime API or SDK endpoint is unreachable (Floci reports `Function.TimedOut`; LocalStack surfaces `Docker not available` and startup timeouts, [Lambda docs](https://docs.localstack.cloud/aws/services/lambda/)). Because the Runtime API is the first thing a runtime calls, a missing first `GET /next` within the init deadline is a precise signal. The error should include the exact address handed to the container, the topology detected, and the three causes in order: listener bound to loopback, firewall on `docker0`, rootless loopback block. A single optional preflight (`understudy doctor`) can run a short-lived labelled container (the `provided.al2023` image already has `curl`, observed E2) against the listener and print the same hints.

### 8.5 DNS, S3 virtual-hosted addressing and SDK endpoints

- Docker's embedded DNS resolves container names and aliases on user-defined networks (observed E7e) but has no wildcard records, so a bucket host such as `my-bucket.s3.<anything>` cannot be resolved through aliases.
- LocalStack solves this by running a DNS server and pointing Lambda containers at it with `HostConfig.Dns` ([docker_runtime_executor.py#L345-L359](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/lambda_/invocation/docker_runtime_executor.py#L345-L359)); Floci calls `withEmbeddedDns` ([ContainerLauncher.java#L277](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/services/lambda/launcher/ContainerLauncher.java#L277)).
- The S3 endpoint rule set in the Smithy model contains both virtual-host templates (`{url#scheme}://{Bucket}.{url#authority}{url#path}`) and path-style templates conditioned on `url#isIp` and `ForcePathStyle` ([S3 model](https://github.com/aws/api-models-aws/blob/1cfdfb4bb9ea858e65623e66d73af04bec353201/models/s3/service/2006-03-01/s3-2006-03-01.json), `smithy.rules#endpointRuleSet`), so SDK behavior with `AWS_ENDPOINT_URL=http://host.docker.internal:PORT` depends on each SDK's default for custom endpoints. Which of Go v2, boto3 and JS v3 pick virtual-host style for a non-IP custom endpoint was **not verified here** (UNVERIFIED). G4 verification (observed, [lambda-runtime-contract.md](lambda-runtime-contract.md) section 5.2): Go v2 and JS v3 use virtual-host style for any non-IP custom endpoint including `localhost` (`bkt.localhost:PORT` failed to resolve in the container), boto3 and the AWS CLI use path style; IP literals give path style in all four. Practical consequence for this area: either hand functions an IP-literal endpoint (SDKs fall back to path style for IP hosts per the `isIp` templates), or provide wildcard DNS. This needs a decision together with the S3 addressing researcher and an end-to-end test inside a function container with all three SDKs.

### 9.2 Graceful shutdown

1. Stop accepting Invokes; fail new ones with a retriable 5xx (`ServiceException`) while draining.
2. Stop the events/log streams.
3. For each environment (in parallel, bounded): `DELETE /containers/{id}?force=1&v=1` (SIGKILL; the Python RIC as PID 1 ignores SIGTERM, observed E8, so `stop` wastes the grace period). RIE containers honor SIGTERM, but there is no reason to wait.
4. Remove networks/volumes created by this instance if empty.
5. Close Runtime API listeners.
Hard bound: a few seconds total; anything left is swept next start.

### 9.3 Startup sweep (crash recovery)

```
GET /containers/json?all=1&filters={"label":["understudy.dev/managed=true"]}
```

- For each result: if `understudy.dev/instance` equals ours, skip. If `understudy.dev/owner` equals ours and the previous instance is gone (no process holds the data-dir lock or listen port), `DELETE ?force=1&v=1`. If the owner differs, leave it (another emulator or another data dir shares the daemon).
- Then networks: `GET /networks?filters={"label":["understudy.dev/managed=true"]}` and remove those with no endpoints; volumes likewise (`prune` accepts a `label` filter since API 1.29, [CHANGELOG v1.29](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/api/docs/CHANGELOG.md#L846), but `containers/prune` only removes *stopped* containers, so use explicit deletes for running ones).
- Need a notion of "previous instance is gone": a lock file in the data directory (`flock`), or the listen port being free. Without one, a second `serve` would delete a live sibling's containers. Floci's lesson: the API port alone collided between two emulators on one daemon, so it added a namespace in front of it ([ContainerStorageHelper.java#L249-L259](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/core/common/docker/ContainerStorageHelper.java#L249-L259)).
- What a crash leaves behind: with the hosted Runtime API, the Python runtime exits (code 1) when its `GET /next` connection fails, leaving a *stopped, still-existing* container (observed E6/E9 after the mock server went away); with stock RIE the container keeps running indefinitely (RIE has no reason to exit). Both are labeled, so one sweep covers both.
- A reaper sidecar is the alternative: Ryuk takes label filters over a TCP connection and deletes matching containers, networks, volumes and images when the connection closes (after `RYUK_RECONNECTION_TIMEOUT`, default 10 s) ([Ryuk README](https://github.com/testcontainers/moby-ryuk/blob/84f4ff002cee21da147748b986d393f2e5d79345/README.md)). It handles `kill -9` of the emulator without a restart, at the price of a privileged socket-mounting helper image; for a single static binary that must work offline, startup sweep plus `understudy cleanup` (a CLI command doing 9.3 on demand) is the proportionate design. Treat a Ryuk-style optional reaper as a stretch.

### 9.4 Naming, retries, idempotence

- Container names: `understudy-<instance>-<function>-<8 hex>`; names must match `^/?[a-zA-Z0-9][a-zA-Z0-9_.-]+$` so sanitize function names (they can contain `-`/`_` only, which is fine, but qualifiers like `$LATEST` must not appear).
- A create that returns a transport error may or may not have created the container. Floci handles the `409 name already in use` on retry by adopting the existing container only when image, labels *and* a per-call `CREATE_ATTEMPT_LABEL` all match ([ContainerLifecycleManager.java#L231-L260](https://github.com/floci-io/floci/blob/da53fc1c051e1a985272cd4532cfe71ffb87ca3b/src/main/java/io/github/hectorvent/floci/core/common/docker/ContainerLifecycleManager.java#L231-L260)). Use unique names plus an attempt label and look up by name on ambiguity.
- Never use `POST /containers/prune` or `docker system prune` equivalents in tests; test cleanup deletes by exact name or by the unique `understudy.dev/test` + per-run label pair. **During this research I once ran `docker ps -q --filter label=understudy.dev/test=1 | xargs docker rm -f`, which removed four containers carrying the shared test label and may have included other agents' test containers; per-run labels avoid that.**
- Disk: `json-file` rotation (2.6) bounds logs; image GC is not our job (pulled runtime images stay, like Docker's normal behavior).

### 10.1 Podman specifics

- Podman is not installed on this machine, so everything in this section comes from source and docs, not from running.
- Two API trees: Docker-compatible (`/v1.xx/...`) and libpod (`/vX.Y.Z/libpod/...`); `GET|HEAD /_ping` is the same for both and is where the version headers live ([version.go#L28-L34](https://github.com/containers/podman/blob/f239badbab04a32bea367d431479c630efbd9dec/version/version.go#L28-L34)). Ping response differs from Docker: `Builder-Version: 1`, `Docker-Experimental: true`, `OSType` (capitalization differs from Docker's `Ostype`; HTTP headers are case-insensitive so use canonicalized lookups), plus `Libpod-Buildah-Version` ([ping.go#L18-L33](https://github.com/containers/podman/blob/f239badbab04a32bea367d431479c630efbd9dec/pkg/api/handlers/compat/ping.go#L18-L33)). Detect Podman by the presence of the `Libpod-API-Version` response header, which the server wrapper sets on every response ([handler_api.go#L51](https://github.com/containers/podman/blob/f239badbab04a32bea367d431479c630efbd9dec/pkg/api/server/handler_api.go#L51); the ping handler's own comment says clients use header availability to tell which engine is in use, [ping.go#L18-L19](https://github.com/containers/podman/blob/f239badbab04a32bea367d431479c630efbd9dec/pkg/api/handlers/compat/ping.go#L18-L19)), and apply the Podman path of 8.1.
- "A compatibility layer offering support for the Docker v1.40 API" per the man page, while `CurrentAPI` is 1.44 in code (docs and code disagree; the code constant is what `Api-Version` reports) ([podman-system-service.1.md#L9-L16](https://github.com/containers/podman/blob/f239badbab04a32bea367d431479c630efbd9dec/docs/source/markdown/podman-system-service.1.md), [version.go#L37-L48](https://github.com/containers/podman/blob/f239badbab04a32bea367d431479c630efbd9dec/version/version.go#L37-L48)).
- Create translation: `NanoCpus` becomes `CPUPeriod=100000`, `CPUQuota=NanoCpus/10000` and errors if both are set ([containers_create.go#L575-L581](https://github.com/containers/podman/blob/f239badbab04a32bea367d431479c630efbd9dec/pkg/api/handlers/compat/containers_create.go#L575-L581)); `ExtraHosts` -> `AddHosts` ([#L403](https://github.com/containers/podman/blob/f239badbab04a32bea367d431479c630efbd9dec/pkg/api/handlers/compat/containers_create.go#L403)); "we only allow specifics of networks to be defined when there is only one network" ([#L400-L401](https://github.com/containers/podman/blob/f239badbab04a32bea367d431479c630efbd9dec/pkg/api/handlers/compat/containers_create.go#L400-L401)), so keep to one endpoint per container there; `Ulimits`, `PidsLimit`, `ReadonlyRootfs`, `Tmpfs`, `MemorySwap` are mapped ([#L478-L547, #L568-L575, #L646](https://github.com/containers/podman/blob/f239badbab04a32bea367d431479c630efbd9dec/pkg/api/handlers/compat/containers_create.go#L478-L547)).
- Images must be fully qualified (`public.ecr.aws/lambda/...` is) because short-name resolution is a Podman policy (UNVERIFIED for the compat pull endpoint).
- Events, logs (`k8s-file`/`journald` default instead of `json-file`) and archive PUT behaviors on the compat tree were not read or run; treat all stream formats in section 2 as Docker-only until tested (UNVERIFIED).

### 10.2 Rootless Docker specifics

- `GET /info` `SecurityOptions` contains `name=rootless`; `CgroupDriver: none` signals ignored limits ([tips.md#L139-L149](https://github.com/docker/docs/blob/7ba25eeb0c4c594f79e6efadad1af5eaca0500a8/content/manuals/engine/security/rootless/tips.md#L139-L149)).
- Network driver defaults: slirp4netns if installed (>= 0.4.0), else pasta, else vpnkit, else gvisor-tap-vsock; `--disable-host-loopback` is on by default and also blocks `10.0.2.2` ([dockerd-rootless.sh#L10-L24](https://github.com/moby/moby/blob/49008a713675b8b4270bf7445fb3028c7aaaa757/contrib/dockerd-rootless.sh#L10-L24)). `DOCKERD_ROOTLESS_ROOTLESSKIT_DISABLE_HOST_LOOPBACK=false` re-enables it.
- File ownership: container uid 0 maps to the invoking user; uid n>=1 maps to `subuid + n - 1`, so a bind-mounted extraction directory owned by the user appears as `root` inside and unprivileged function users would see it as "other" ([uid-gid-mapping.md](https://github.com/docker/docs/blob/7ba25eeb0c4c594f79e6efadad1af5eaca0500a8/content/manuals/engine/security/rootless/uid-gid-mapping.md#L18-L21)). Keep world-readable modes (5.2).

## 11. Security of the function sandbox

- A function is untrusted code: never mount the Docker socket into it, never `Privileged`, no `PidMode`/`IpcMode: host`, no host paths other than the read-only code (and optional layers) directory.
- `SecurityOpt: ["no-new-privileges"]`, `CapDrop: ["ALL"]`, `ReadonlyRootfs: true` (plus writable `/tmp` on a volume or tmpfs) are the obvious hardening steps, but I did not run the Lambda base images under all three; only `ReadonlyRootfs` with a `Tmpfs` `/tmp` was exercised (E7: `/var/task` and `/etc` read-only, `/tmp` writable). tmpfs counts against the container memory limit while Lambda `/tmp` is disk, so a large `/tmp` belongs on the writable layer or a volume (UNVERIFIED trade-off).
- The Runtime API listener is reachable by any process that can reach the bridge IP; with a port per environment the "secret" is only the port number. Keep listeners off non-bridge interfaces where possible (8.2) and never put credentials or the account's secrets in Runtime API responses.
- Environment variables set on the container are visible via `GET /containers/{id}/json` to anyone with Docker access; the Docker socket already implies root, so this is the same trust boundary, but never log the `Env` array (brief: never log secrets). The create body in debug logs must be redacted.

## 14. Implications for understudy

### 14.1 Decisions I recommend (each ties to evidence above)

1. **Host the Runtime API inside understudy; do not depend on RIE for execution.** Evidence: findings 1-3, section 4.4. Keep stock RIE only as a documented escape hatch (not built in phase 1).
2. **One Runtime API listener per execution environment, own port** (section 4.5), bound to the bridge gateway/ container-network address rather than loopback; implemented with `net/http` (it decodes chunked bodies and exposes trailers) and tested against real runtimes (Python RIC, aws-lambda-go) in the conformance suite: always send `Content-Type: application/json` on `/next`, `Lambda-Runtime-Deadline-Ms` as wall-clock ms, 202 for `/response` and `/error`.
3. **Docker client: hand-rolled, in one cohesive package** around a `Client` type with `Ping/Negotiate`, `ImageInspect/Pull(progress)`, `ContainerCreate/Start/Wait/Stop/Kill/Remove/Inspect/List/Logs/Archive`, `Events`, `Network*`, plus a `stdcopy` demultiplexer and a typed `Error` ADT mapped from statuses (2.3). Transport: `http.Transport{DialContext: unix}`; no overall client timeout on streaming calls; per-call contexts. Negotiate to `min(1.44, server)`, refuse below 1.41 with an actionable message; resolve the endpoint via `DOCKER_HOST` then Docker context then well-known sockets (2.1). Decode leniently.
4. **Pull images on `CreateFunction` (state `Pending`)**, never on first invoke; single-flight; send `platform`; pin and record the digest; anonymous pulls only in phase 1 (client-side registry auth is a separate decision, 2.4).
5. **Create containers with `Mounts` (not `Binds`)**, read-only code at `/var/task`, `LogConfig` json-file with rotation, labels (9.1), `Memory`=`MemorySwap`, `PidsLimit`, `Ulimits nofile`, explicit `Env`, no `AutoRemove`, `Tty=false`. Use `Binds ...:ro,z` only on SELinux hosts after an explicit directory check. CPU limits optional (`NanoCpus`), default off to avoid slow, noisy local runs (judgment call: at 128 MB the 1,769 MB = 1 vCPU rule yields ~7% of a core).
6. **Code delivery**: bind mount from a content-addressed extraction directory when the emulator runs on the host; tar-copy (no `ReadonlyRootfs`) when containerized or the path is not daemon-visible; named volume later for large trees. Normalize modes; strip nothing else.
7. **Exit/crash/OOM** are learned from one events subscription (`die`, `oom`, filtered by understudy labels) with reconnect-by-`since`, plus `wait` as a fallback per environment.
8. **Removal is `DELETE ?force=1&v=1`**, not `stop`, for function containers.
9. **Logs**: one `logs?follow=1` per environment, framed demux, per-environment CloudWatch stream, synthesized START/END/REPORT with a settle barrier; never forward RIE-format lines.
10. **Networking**: compute the function-facing address per topology (8.1); emulator needs an extra listener on the bridge gateway (or `0.0.0.0` opt-in) even when the API listens on 127.0.0.1; add `host.docker.internal:host-gateway` only on Linux/Podman, never on Docker Desktop; startup self-check logs the chosen topology and address; first-invoke timeout errors carry the address and top causes.
11. **Cleanup**: labels + instance/owner ids, graceful drain on SIGINT/SIGTERM, startup sweep guarded by an instance lock, `understudy cleanup` command, tests use unique names plus the `understudy.dev/test=1` label and delete by name.
12. **Pool**: exclusive reservation, key on every spec-affecting field, generation counter on updates, idle reaper, configurable start-concurrency semaphore (default 16), global caps.

### 14.2 Suggested package boundaries (stdlib only)

- `internal/docker` (Engine client + typed errors + frame/progress decoders), kept free of Lambda concepts so it is unit-testable against a fake daemon built on `httptest` + a unix-socket listener.
- `internal/lambda/runtimeapi` (the per-environment Runtime API server: state machine around one in-flight invocation; the only code that speaks `2018-06-01`).
- `internal/lambda/pool` (environments, reservation, reaping, generation), `internal/lambda/launcher` (builds the create body from function config; the only place that knows labels, mounts, env).
- Test-time seams: a `Launcher` interface so the Lambda service can run against an in-process fake (no Docker) in unit tests, plus an opt-in `-tags docker` integration suite that uses real containers with `understudy.dev/test=1` and ephemeral ports (brief's rule).

### 14.3 Suggested conformance and integration tests (semantic, not implementation)

1. Python 3.13 and `provided.al2023` Go bootstrap: warm reuse (second invoke has no new init), handler error returns 200 + `X-Amz-Function-Error: Unhandled`, `Runtime.ExitError` on `os.Exit`, timeout kills and next invoke cold, OOM maps to an error and removes the container.
2. Concurrent invokes to one function produce N environments and never share one.
3. Chunked-trailer error from aws-lambda-go surfaces as a function error.
4. Missing `Content-Type` regression test for the Runtime API server (guards finding 8).
5. Hot reload: edit a file in the mounted directory and observe new behavior on the next invoke within the documented bound.
6. Crash recovery: start `serve`, create a function, invoke, `kill -9` the emulator, start again, assert labeled containers are gone and the new instance's containers survive.
7. Topology probes: listener on 127.0.0.1 only produces the documented diagnostic; listener on the bridge IP works.
8. Log ordering: last line printed before returning appears in `LogType=Tail` output (guards the settle barrier).

### 14.4 Open questions for the architecture/ADR stage

1. **Listener exposure**: bind the Runtime API on `0.0.0.0` (simple, exposed to LAN) or on bridge gateway IPs only (needs discovery per network, rootless/Desktop/Podman variants UNVERIFIED)? The brief's "bind 127.0.0.1" default conflicts with Linux bridge reachability (finding 4).
2. **Hosted API versus bundled RIE fallback**: is any fallback needed in phase 1?
3. **Clock semantics for idle reaping and function timeouts**: wall time (matches containers, header deadlines) or the emulator clock (deterministic tests)? Recommend wall time for container mechanics and the emulator clock for any AWS-visible timer; `Lambda-Runtime-Deadline-Ms` must remain wall-clock (4.5). G4 confirmed this with the real runtimes (a -1 h or frozen deadline gives aws-lambda-go an already-cancelled context and Python a remaining time of 0): [lambda-runtime-contract.md](lambda-runtime-contract.md) section 4.
4. **DNS for virtual-hosted S3 inside functions**: IP-literal endpoint, wildcard DNS server (needs a stdlib-only DNS responder; an ADR item per the "stdlib only" rule), or both. Requires the SDK matrix test from 8.5.

## 1. Findings that change the design

1. **Terraform needs more than the S3 API.** With a resolvable account id (any working STS endpoint, so understudy's own), provider 6.68.0 reads bucket tags through S3 Control `ListTagsForResource`: `GET /v20180820/tags/arn%3Aaws%3As3%3A%3A%3A<bucket>` with `Host: <account>.<endpoint host>` and `x-amz-account-id` (PROBE E2, [TF tags.go L177-184](https://github.com/hashicorp/terraform-provider-aws/blob/v6.68.0/internal/service/s3/tags.go#L177-L184)). It falls back to `GetBucketTagging` only on error code `MethodNotAllowed` or a message containing "is not authorized to perform: s3:ListTagsForResource". Against an IPv4 endpoint that host is `123456789012.127.0.0.1`, which does not resolve, and the read fails (PROBE E3).
2. **Every `aws_s3_bucket_lifecycle_configuration` costs about 55 seconds of wall time, and the server cannot shorten it.** The provider polls `GetBucketLifecycleConfiguration` every 5 s after a 10 s delay until the response deep-equals what it sent 10 times in a row, and the response must also carry `x-amz-transition-default-minimum-object-size` ([TF bucket_lifecycle_configuration.go L658-L712](https://github.com/hashicorp/terraform-provider-aws/blob/v6.68.0/internal/service/s3/bucket_lifecycle_configuration.go#L658-L712), PROBE E1/E2: "Creation complete after 55s"). Rule fidelity on read is therefore a correctness requirement, not polish.
3. **New buckets are not empty.** On real AWS a fresh bucket answers `GetBucketOwnershipControls` with `BucketOwnerEnforced`, `GetPublicAccessBlock` with all four flags `true`, `GetBucketEncryption` with an `AES256` rule and `BucketKeyEnabled=false`, and `GetBucketVersioning`/`GetBucketAccelerateConfiguration`/`GetBucketLogging` with an empty success document (REC, section 4.1).
4. **Conditional writes are partially implemented on real S3 and fail loudly elsewhere.** `If-None-Match: *` and `If-Match: <etag>` work on PutObject, CopyObject and CompleteMultipartUpload; any other value, `If-Match: *`, or both headers together return `501 NotImplemented` with `Header` and `additionalMessage` elements; `x-amz-if-match-size` and `x-amz-if-match-last-modified-time` on DeleteObject return 501 on general purpose buckets (REC, section 5.10).
5. **Checksums changed the upload wire format.** Go SDK v2, boto3, the CLI and the JS SDK all send a checksum on every PutObject and UploadPart by default. Over plain HTTP they use a header (`x-amz-checksum-crc32`; the CLI uses `crc64nvme`); the JS SDK uses an `aws-chunked` body with an unsigned trailer for streamed bodies even over HTTP (PROBE E5-E7). Content-MD5 is gone from current clients. Real S3 adds `CRC64NVME` itself when a client sends none, and returns `x-amz-checksum-type: FULL_OBJECT` (DOC, REC). CRC64/NVME is computable with the standard library (section 6.2).
6. **Error bodies carry context elements** (`BucketName`, `Key`, `UploadId`, `Condition`, `ArgumentName`, `ActualObjectSize`, `ETag`, ...) that clients and tests read (REC, section 3.5 of [wire-rest.md](wire-rest.md) and the tables below).
7. **A single `Date` response header is mandatory.** The JS SDK derives its clock-skew correction from it; two `Date` headers produced `RangeError: Invalid time value` on the second request (PROBE E7).
8. **SSE-KMS interacts with the KMS service.** S3 validates the key on PUT, copy, multipart create and on GET: `KMS.NotFoundException`, `KMS.DisabledException`, `KMS.KMSInvalidStateException`, all 400, are real error codes (REC, section 5.7). SSE-KMS and multipart ETags are not MD5s.
9. **CRC and composite checksum rules are non-trivial** (full-object CRCs need a CRC-combine; composite checksums hash the concatenated part checksums). Section 6.5.
10. **Event notifications send an `s3:TestEvent` to SQS/SNS when the configuration is stored**, validate destinations with documented error shapes, and use a different JSON shape for the test message (REC, DOC, section 13).

## 2. What the real clients send to a local endpoint (PROBE)

Method: a logging reverse proxy in front of `moto_server` (installed into a scratch venv), real clients pointed at `http://localhost:5872`, one JSON line per request. Nothing below depends on moto's answers except where a request failed. The proxy and the Terraform/boto3/JS/CLI scripts live in the session scratchpad, not in the repo; to reproduce, put any HTTP stand-in that logs `Host`, request line and headers in front of any S3-compatible server and point the clients at it.

### E1. Terraform 6.68.0, `skip_requesting_account_id = true`, `http://127.0.0.1:5872`, path style

Config: bucket (with tags), versioning, SSE-KMS configuration, public access block, ownership controls, lifecycle, CORS, policy, notification (SQS), object. Request order for `terraform apply` (condensed; every S3 request carries `x-amz-content-sha256: e3b0c442...` when it has no body):

```
HEAD /understudy-probe-bucket/                   -> 404          (pre-create existence check, us-east-1 only)
PUT  /understudy-probe-bucket/  x-amz-acl: private  body: CreateBucketConfiguration (tags, if any)
HEAD /understudy-probe-bucket/                   -> 200  (x2: wait-until-exists and read-back; a third later for the region)
GET  ?policy ?acl ?cors ?website ?versioning ?accelerate ?requestPayment ?logging
     ?lifecycle ?replication ?encryption ?object-lock       (legacy inline attributes of aws_s3_bucket)
HEAD /bucket/ ; GET ?tagging                    (tags; see E2 for the S3 Control variant)
PUT  ?publicAccessBlock ?versioning ?ownershipControls ?encryption ?cors  (each followed by GET of the same key)
PUT  ?policy ; GET ?policy (x2)
PUT  ?lifecycle ; then GET ?lifecycle every 5 s ...      (see section 4.2.8)
PUT  ?notification ; GET ?notification (x2)
PUT  /in/hello.txt?x-id=PutObject ; HEAD /in/hello.txt ; GET /in/hello.txt?tagging
```

Facts read off the trace and the source:
- CreateBucket body was `<CreateBucketConfiguration xmlns="http://s3.amazonaws.com/doc/2006-03-01/"></CreateBucketConfiguration>` (103 bytes) in `us-east-1` with no tags, so the server must accept an empty configuration element, not only a missing body ([TF bucket.go L790-L812](https://github.com/hashicorp/terraform-provider-aws/blob/v6.68.0/internal/service/s3/bucket.go#L790-L812): `LocationConstraint` only when region is not `us-east-1`; `Tags` always passed).
- `x-amz-acl: private` is sent on every CreateBucket ([TF bucket.go L777-L783](https://github.com/hashicorp/terraform-provider-aws/blob/v6.68.0/internal/service/s3/bucket.go#L777-L783)).
- Retry hook: `OperationAborted` whose message contains "A conflicting conditional operation is currently in progress against this resource. Please try again." is retried ([TF service_package.go L62-L72](https://github.com/hashicorp/terraform-provider-aws/blob/v6.68.0/internal/service/s3/service_package.go#L62-L72)).
- With `s3_use_path_style` unset Terraform uses virtual-hosted addressing; with region `us-east-1` it switches the endpoint region to `aws-global` unless `s3_us_east_1_regional_endpoint = "regional"` ([TF service_package.go L44-L62](https://github.com/hashicorp/terraform-provider-aws/blob/v6.68.0/internal/service/s3/service_package.go#L44-L62)); signing still uses `us-east-1`: every captured credential scope was `.../us-east-1/s3/aws4_request`.

### E2. Terraform 6.68.0 with account id resolved, endpoint `http://localhost:5872`

Same config with `skip_requesting_account_id` removed (STS and IAM `GetUser` calls answered by the stand-in), `s3_use_path_style = false`.

```
(the E1 sequence again, all requests virtual-hosted: Host: understudy-probe-bucket.localhost:5872, path /?<subresource>)
GET /v20180820/tags/arn%3Aaws%3As3%3A%3A%3Aunderstudy-probe-bucket
    Host: 123456789012.localhost:5872   x-amz-account-id: 123456789012   (SigV4 scope .../us-east-1/s3/aws4_request)
```

- Virtual-hosted requests used `Host: understudy-probe-bucket.localhost:5872`; the S3 Control call used `Host: 123456789012.localhost:5872`. That is exactly the S3 Control endpoint rule for a custom endpoint, `{scheme}://{AccountId}.{authority}{path}`, which applies when the operation requires an account id ([MODEL s3-control endpointRuleSet](https://github.com/aws/api-models-aws/blob/1cfdfb4bb9ea858e65623e66d73af04bec353201/models/s3-control/service/2018-08-20/s3-control-2018-08-20.json), `RequiresAccountId`).
- Operations: `ListTagsForResource GET /v20180820/tags/{ResourceArn+}`, `TagResource POST` same path, `UntagResource DELETE` same path ([MODEL s3-control](https://github.com/aws/api-models-aws/blob/1cfdfb4bb9ea858e65623e66d73af04bec353201/models/s3-control/service/2018-08-20/s3-control-2018-08-20.json)). On create the tags travel in the CreateBucket body, so S3 Control is touched only on reads and updates.
- Update fallbacks: `TagResource`/`UntagResource` failing with a message containing "is not authorized to perform: s3:TagResource" or "s3:UntagResource", or error code `MethodNotAllowed`, switch to `PutBucketTagging`/`DeleteBucketTagging` ([TF tags.go L234-L244](https://github.com/hashicorp/terraform-provider-aws/blob/v6.68.0/internal/service/s3/tags.go#L234-L244)).
- `bucketListTags` treats `NoSuchTagSet`, `NoSuchTagSetError`, `MethodNotAllowed`, `NotImplemented`, `XNotImplemented`, `UnsupportedOperation` as "no tags" ([TF tags.go L38-L48](https://github.com/hashicorp/terraform-provider-aws/blob/v6.68.0/internal/service/s3/tags.go#L38-L48)).

### E3. Same state, endpoint `http://127.0.0.1:5872`

`terraform plan -refresh` failed: `listing tags for S3 (Simple Storage) Bucket (understudy-probe-bucket): operation error S3 Control: ListTagsForResource, ... request send failed, Get "http://123456789012.127.0.0.1:5872/v20180820/tags/arn%3Aaws%3As3%3A%3A%3Aunderstudy-probe-bucket": dial tcp: lookup 123456789012.127.0.0.1: no such host`. ### E4. Terraform managed uploads (`aws_s3_object`), `http://localhost:5872`

`aws_s3_object` uses the transfer manager's `Uploader` ([TF object.go L588](https://github.com/hashicorp/terraform-provider-aws/blob/v6.68.0/internal/service/s3/object.go#L588)). Trace for a 5-byte `content` and a 12 MiB `source`:

```
PUT /small.txt?x-id=PutObject
    content-length: 5   content-type: text/plain   x-amz-checksum-crc32: NhCmhg==
    x-amz-content-sha256: 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824   (hex SHA-256 of the body, HTTP)
    x-amz-meta-owner: probe   x-amz-tagging: t1=v1
HEAD /small.txt ; GET /small.txt?tagging=            (CORRECTED (G6): HEAD sends x-amz-checksum-mode: ENABLED only when checksum_algorithm is configured, TF object.go L653-L655; observed 6.68.0 with and without it, tf-remaining.md section 8)
POST /big.bin?uploads=    x-amz-checksum-algorithm: CRC32      (no x-amz-checksum-type)

     expect: 100-continue   x-amz-checksum-crc32: <per part>   x-amz-sdk-checksum-algorithm: CRC32

POST /big.bin?uploadId=...   body: <CompleteMultipartUpload><Part><ChecksumCRC32>..</ChecksumCRC32><ETag>..</ETag><PartNumber>1</PartNumber></Part>...
```

Part size is 5 MiB. The same trace shows Go SDK behavior on HTTP: checksum as a header, payload hash signed ([SDK middleware_compute_input_checksum.go L168-L190](https://github.com/aws/aws-sdk-go-v2/blob/ab2110b01f03b3990bfd50208a8a05df1d8c5eac/service/internal/checksum/middleware_compute_input_checksum.go#L168-L190): the trailer path is taken only when `req.IsHTTPS()`; default algorithm CRC32, [middleware_setup_context.go L59](https://github.com/aws/aws-sdk-go-v2/blob/ab2110b01f03b3990bfd50208a8a05df1d8c5eac/service/internal/checksum/middleware_setup_context.go#L59)).

### E6. AWS CLI 2.36 (`aws s3 mb|cp|ls|rm`) against `http://localhost:5872`

Path style, `CreateBucket` with empty body, `CreateMultipartUpload` with `x-amz-checksum-algorithm: CRC64NVME`, parts of 8 MiB (and a 4 MiB tail) with `x-amz-checksum-crc64nvme` and `x-amz-sdk-checksum-algorithm: CRC64NVME`, a 3-byte `PutObject` with `x-amz-checksum-crc64nvme: JYwwIoi0PuE=`, list as `GET /cliprobe?list-type=2&prefix=&delimiter=%2F&encoding-type=url`. ### E7. JS SDK `@aws-sdk/client-s3` 3.1147.0 against `http://localhost:5872`

```
PUT /buf?x-id=PutObject      content-length: 5  x-amz-sdk-checksum-algorithm: CRC32  x-amz-checksum-crc32: NhCmhg==   (Buffer or string body)
PUT /stream?x-id=PutObject   (Readable body, ContentLength 13)
    content-encoding: aws-chunked   transfer-encoding: chunked   x-amz-decoded-content-length: 13
    x-amz-content-sha256: STREAMING-UNSIGNED-PAYLOAD-TRAILER   x-amz-trailer: x-amz-checksum-crc32
    x-amz-sdk-checksum-algorithm: CRC32
    body (after HTTP de-chunking): d\r\nstreamed-body\r\n0\r\nx-amz-checksum-crc32:Nyb53Q==\r\n\r\n
POST /mpu?uploads=  x-amz-checksum-algorithm: CRC32 ; parts 5 MiB; Complete body starts with an XML declaration
POST /?delete=      x-amz-checksum-crc32, body starts with <?xml version="1.0" encoding="UTF-8"?>
GET  /mpu?x-id=GetObject  range: bytes=0-4  x-amz-checksum-mode: ENABLED
```

The streamed PUT is the only case in these traces where an `aws-chunked` body arrives over plain HTTP, in the unsigned-trailer form. HTTP `Transfer-Encoding: chunked` is the outer layer (Go's `net/http` removes it before the handler sees the body); `aws-chunked` is the inner layer. Also: the JS SDK worked out clock skew from the `Date` response header and threw `RangeError: Invalid time value` in `@smithy/signature-v4` when my proxy sent two `Date` headers, so exactly one `Date` header is required.

## 3. Buckets

### 3.1 Naming

Rules, from [DOC bucketnamingrules](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucketnamingrules.html) (listed in full in [wire-rest.md 3.1](wire-rest.md)): 3 to 63 characters; lowercase letters, digits, `.`, `-`; begin and end alphanumeric; no `..`; not shaped like an IPv4 address; not prefixed `xn--`, `sthree-`, `amzn-s3-demo-`; not suffixed `-s3alias`, `--ol-s3`, `.mrap`, `--x-s3`, `--table-s3`; suffix `-an` is legal only in the account regional namespace (`<prefix>-<12-digit account>-<region>-an` with header `x-amz-bucket-namespace: account-regional`). Before 2018-03-01 `us-east-1` allowed up to 255 characters, uppercase and underscores; not any more (same page). Violation: `400 InvalidBucketName`, message "The specified bucket is not valid.", with a `BucketName` element (REC `TestS3::test_s3_uppercase_bucket_name`). The Ceph suite's comments say AWS did not enforce all documented rules in the past and later does ([s3-tests test_s3.py L3775-L3835](https://github.com/ceph/s3-tests/blob/5522d1c351f75bc00ae0f64f742f3f095f5939d9/s3tests/functional/test_s3.py#L3775-L3835)).

## 4. Bucket subresources

Success statuses first, because the S3 model says `200` for every `Put*` and `204` only for `Delete*`/`AbortMultipartUpload`/`DeleteObject` ([MODEL `smithy.api#http` codes, parsed](https://github.com/aws/api-models-aws/blob/1cfdfb4bb9ea858e65623e66d73af04bec353201/models/s3/service/2006-03-01/s3-2006-03-01.json)) while real S3 answers `204` for `PutBucketPolicy`, `PutBucketTagging` and the `Put` of metrics, inventory, analytics and intelligent-tiering configurations (REC: `put-bucket-policy`, `put-bucket-tags`, `put-bucket-tags-empty`, `put_bucket_metrics_configuration`, `put-inventory-config`, `put_bucket_intelligent_tiering_configuration`, `put_config_with_storage_analysis` all recorded with `HTTPStatusCode 204`). Every other recorded `Put*` (versioning, encryption, ownership, public access block, lifecycle, CORS, website, logging, accelerate, request payment, replication, notification, object lock, `PutObjectTagging`) is `200`. SDKs accept any 2xx, so the difference is cosmetic, but conformance suites that compare statuses will see it.

### 4.2 Per-subresource details

#### 4.2.1 Versioning

- Put accepts only `Status` of exactly `Enabled` or `Suspended` (case sensitive). `enabled`, `Disabled` → `400 MalformedXML`. An empty `<VersioningConfiguration/>` → `400 IllegalVersioningConfigurationException`, "The Versioning element must be specified" (REC `test_bucket_versioning_crud`). `MfaDelete` is returned only if it was ever configured ([DOC GetBucketVersioning](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetBucketVersioning.html)).
- Object Lock interaction: `PutBucketVersioning` to `Suspended` on a bucket with an Object Lock configuration → `409 InvalidBucketState`, "An Object Lock configuration is present on this bucket, so the versioning state cannot be changed." (REC `test_disable_versioning_on_locked_bucket`; the provider keys on this message, [TF bucket_versioning.go L289](https://github.com/hashicorp/terraform-provider-aws/blob/v6.68.0/internal/service/s3/bucket_versioning.go#L289)); `PutObjectLockConfiguration` on a bucket whose versioning is not `Enabled` → `409 InvalidBucketState`, "Versioning must be 'Enabled' on the bucket to apply a Object Lock configuration" (REC `test_put_object_lock_configuration_on_existing_bucket`).
- Replication needs versioning `Enabled` on the source: `400 InvalidRequest`, "Versioning must be 'Enabled' on the bucket to apply a replication configuration" (REC `test_replication_config`).
- Terraform's `aws_s3_bucket_versioning` Create/Update waits until `GetBucketVersioning` returns the requested status ([TF bucket_versioning.go L140-L170](https://github.com/hashicorp/terraform-provider-aws/blob/v6.68.0/internal/service/s3/bucket_versioning.go#L140-L170)); no delay is needed.
- How versions behave on objects is in section 8.

#### 4.2.2 Encryption configuration

- `Put` body: `ServerSideEncryptionConfiguration/Rule` with exactly one `Rule`; zero or two rules → `400 MalformedXML` (REC `test_s3_default_bucket_encryption_exc`). `SSEAlgorithm` ∈ `AES256`, `aws:kms`, `aws:kms:dsse`; `KMSMasterKeyID` with `AES256` → `400 InvalidArgument`, `ArgumentName=ApplyServerSideEncryptionByDefault`, "a KMSMasterKeyID is not applicable if the default sse algorithm is not aws:kms or aws:kms:dsse" (same test). `BucketKeyEnabled` is a rule-level element ([MODEL `ServerSideEncryptionRule`](https://github.com/aws/api-models-aws/blob/1cfdfb4bb9ea858e65623e66d73af04bec353201/models/s3/service/2006-03-01/s3-2006-03-01.json)).
- What `Get` returns after an `aws:kms` put (REC `TestS3BucketEncryption::test_s3_bucket_encryption_sse_kms`, `TestS3::test_s3_sse_default_kms_key`; both tests sent `BucketKeyEnabled=True`, [test_s3_api.py L1312-L1351](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/tests/aws/services/s3/test_s3_api.py#L1312-L1351)): `KMSMasterKeyID` as the client sent it (a bare key id in the recording; Terraform sends an ARN and compares strings, so echo whatever form arrived, the ARN/alias forms are UNVERIFIED), `BucketKeyEnabled` as sent, and no `KMSMasterKeyID` at all for a rule written as `aws:kms` without a key, which means the AWS managed key `aws/s3`. Objects written under such a rule report `SSEKMSKeyId` as the full ARN of that managed key (`test_s3_sse_default_kms_key`).
- Existing objects keep the encryption they were written with; only new writes pick up the new default (REC `test_s3_sse_bucket_key_default`: an object written before the KMS default still reads back `AES256`).

#### 4.2.3 Public access block

- `Put`: `PublicAccessBlockConfiguration` with any of the four booleans; REC shows all-`false` accepted and returned verbatim. An empty configuration is rejected (`InvalidRequest`, "Must specify at least one configuration." per moto, EMU; REC not recorded). Block Public Access also changes behavior of policy and ACL writes (`403 AccessDenied` on a public policy or public ACL when the flags are on, [DOC announcement](https://aws.amazon.com/about-aws/whats-new/2023/04/amazon-s3-security-best-practices-buckets-default)); phase 1 does not enforce policies, so storing is enough.
- `Delete` is `204`, idempotent; afterwards `Get` is `404 NoSuchPublicAccessBlockConfiguration`.

#### 4.2.4 Ownership controls and ACLs

- `Put`: exactly one rule, `ObjectOwnership` ∈ `BucketOwnerEnforced`, `BucketOwnerPreferred`, `ObjectWriter`; zero/two rules, a bad value or an empty rule → `400 MalformedXML` (REC `test_bucket_ownership_controls_exc`). `x-amz-object-ownership` at create time is stored as the same rule (REC `get-ownership-at-creation` → `BucketOwnerPreferred`).
- While ownership is `BucketOwnerEnforced`, ACL writes fail: `PutObject`, `CreateMultipartUpload`, `CopyObject` with an ACL other than `bucket-owner-full-control`, and `PutBucketAcl`/`PutObjectAcl` with anything, return `400 AccessControlListNotSupported` (Ceph, run against AWS where noted: [test_s3.py L20148-L20198](https://github.com/ceph/s3-tests/blob/5522d1c351f75bc00ae0f64f742f3f095f5939d9/s3tests/functional/test_s3.py#L20148-L20198); error code and statement in [DOC PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html): "PUT requests that contain other ACLs ... fail and return a `400` error with the error code `AccessControlListNotSupported`"). Exact message text UNVERIFIED. Terraform's `aws_s3_bucket_acl` therefore requires `aws_s3_bucket_ownership_controls` with `BucketOwnerPreferred` or `ObjectWriter`; with those, `GetBucketAcl` after `PutBucketAcl(private)` returns the owner `FULL_CONTROL` grant; a `public-read` canned ACL adds a `Grantee{Type=Group, URI=http://acs.amazonaws.com/groups/global/AllUsers}` `READ` grant (REC `test_s3_bucket_acl`).
- ACL validation errors worth keeping: `InvalidArgument` with `ArgumentName=x-amz-acl` for an unknown canned ACL; `Invalid group uri`; `Invalid id`; `Argument format not recognized`; `MalformedACLError`; `MissingSecurityHeader` (`MissingHeaderName=x-amz-acl`) for an empty PutBucketAcl; `InvalidRequest` "Specifying both Canned ACLs and Header Grants is not allowed" (REC `test_s3_bucket_acl_exceptions`, `test_s3_object_acl_exceptions`).

#### 4.2.5 Policy

- `PutBucketPolicy` → `204`; the body is a JSON document; `GetBucketPolicy` returns the JSON as the raw response body, not XML (MODEL payload `Policy`). Invalid JSON → `400 MalformedPolicy`, "Policies must be valid JSON and the first byte must be '{'"; `{}` → `MalformedPolicy` "Missing required field Statement" (REC `test_bucket_policy_exc`). Full policy-grammar validation is a deeper job (principals, actions, ARNs, public-access-block interplay); phase 1 only stores. Terraform compares policies with semantic JSON equivalence, so the stored text need not be byte-identical; return the JSON as sent.
- `x-amz-expected-bucket-owner` with a wrong account id: `403`, and with a malformed id `400 InvalidArgument` (REC `test_get_bucket_policy_invalid_account_id[...]`, `test_put_bucket_policy_expected_bucket_owner`; message text per the snapshot file).
- Policy `Principal` accounts, `Condition` keys such as `aws:SecureTransport` are not evaluated in phase 1.

#### 4.2.6 CORS

- `Put` body `CORSConfiguration/CORSRule{ID?, AllowedMethod+, AllowedOrigin+, AllowedHeader*, ExposeHeader*, MaxAgeSeconds?}`; `Get` echoes the rules (REC `test_s3_cors.snapshot.json::test_get_cors`); unset → `404 NoSuchCORSConfiguration`. Unsupported methods give `InvalidRequest` "Found unsupported HTTP method in CORS config. Unsupported method is X" (moto, [exceptions.py](https://github.com/getmoto/moto/blob/5cab9c903b2a26d08f353da2afc753b1adc1eb10/moto/s3/exceptions.py), EMU; REC `test_put_cors_invalid_rules` has the other validation cases). Data-plane CORS (OPTIONS preflight, `Access-Control-*` headers) is its own behavior (REC `test_cors_*`); only needed for browser clients, defer.

#### 4.2.7 Website

- `Put` body `WebsiteConfiguration` with `IndexDocument/Suffix`, `ErrorDocument/Key`, `RedirectAllRequestsTo`, `RoutingRules`; `Get` echoes it; delete `204` even when unset (REC `test_crud_website_configuration`). Website hosting (separate endpoint, 404 pages, redirects) is out of phase 1; the object header `x-amz-website-redirect-location` is stored but is only meaningful on website endpoints ([DOC PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html)) and is not copied by `CopyObject` unless supplied.

#### 4.2.8 Lifecycle (the 55-second wait)

- Wire: `PutBucketLifecycleConfiguration` `PUT /?lifecycle` with `LifecycleConfiguration/Rule{ID, Status, Filter|Prefix, Expiration{Days|Date|ExpiredObjectDeleteMarker}, Transition*, NoncurrentVersionExpiration, NoncurrentVersionTransition, AbortIncompleteMultipartUpload{DaysAfterInitiation}}` ([DOC](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutBucketLifecycleConfiguration.html)) and request header `x-amz-transition-default-minimum-object-size` (`all_storage_classes_128K` | `varies_by_storage_class`). `Get` returns the rules plus the same value as a response header; the default when none was sent is `all_storage_classes_128K`; a bad value → `400 InvalidRequest`, "Invalid TransitionDefaultMinimumObjectSize found: value" (REC `TestS3BucketLifecycle::test_s3_transition_default_minimum_object_size`, `test_delete_bucket_lifecycle_configuration`).
- Terraform's read-back test: `reflect.DeepEqual` of each returned `LifecycleRule` against the rule it sent, plus equality of the header value, ten consecutive times, 5 s apart after a 10 s delay ([TF bucket_lifecycle_configuration.go L658-L712](https://github.com/hashicorp/terraform-provider-aws/blob/v6.68.0/internal/service/s3/bucket_lifecycle_configuration.go#L658-L712)). So `Get` must preserve exactly what `Put` stored, with no re-ordering of rules that matter to `DeepEqual` (the check is order-insensitive across rules via `slices.ContainsFunc`, but each rule must be structurally identical, including which of `Filter.Prefix` / `Filter.And` / `Filter.Tag` / `Filter.ObjectSizeGreaterThan` form was used, and including empty versus absent optional blocks). Observed cost: 55 s per apply (PROBE E1, E2). Nothing server-side shortens it.
- Validation recorded against AWS (REC `TestS3BucketLifecycle::test_put_bucket_lifecycle_conf_exc`, inputs read from [test_s3.py L9035-L9160](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/tests/aws/services/s3/test_s3.py#L9035-L9160)). All `400 MalformedXML` ("The XML you provided was not well-formed or did not validate against our published schema"): a rule without `ID`; a rule without `Filter` (the modern API requires `Filter`, so Terraform always sends one, even `Filter{}`); `NoncurrentVersionExpiration` with neither `NoncurrentDays` nor `NewerNoncurrentVersions`; a `Filter` that sets both `Prefix` and `And`; a `Filter` that sets `ObjectSizeGreaterThan` next to `Prefix` (these need `And`); `ExpiredObjectDeleteMarker` combined with `Days`. `400 InvalidArgument` with `ArgumentName=Date`, `ArgumentValue=<the date>`, "'Date' must be at midnight GMT" for an `Expiration.Date` that is not midnight. `400 InvalidRequest`, "Duplicate Tag Keys are not allowed." for repeated tag keys inside `Filter/And`.
- Execution of lifecycle rules (expiration, transitions) is time-based; understudy's controllable clock makes this a feature. The `x-amz-expiration` response header on Put/Get/Head/Copy of matching objects carries `expiry-date="<RFC 1123>", rule-id="<url-encoded id>"` ([DOC PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html)). Whether phase 1 runs the rules is a scope decision for the planner.

#### 4.2.9 Bucket tagging

- `PutBucketTagging` `PUT /?tagging` with `Tagging/TagSet/Tag{Key,Value}` → `204`; `GetBucketTagging` → `Tagging/TagSet`; `DeleteBucketTagging` → `204` (REC `test_bucket_tagging_crud`). An empty `TagSet` put is `204` (`put-bucket-tags-empty`). Limits: at most 50 tags per bucket, keys up to 128 and values up to 256 Unicode characters ([DOC tagging](https://docs.aws.amazon.com/AmazonS3/latest/userguide/tagging.html), [object-tagging](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-tagging.html)).
- Validation (REC `test_tagging_validation`): duplicate keys → `400 InvalidTag`, "Cannot provide multiple Tags with the same key" (+`TagKey`); `,` in a key → `InvalidTag` "The TagKey you have provided is invalid" (+`TagKey`); `,` in a value → "The TagValue you have provided is invalid" (+`TagKey`, `TagValue`); `aws:` prefix → bucket: "System tags cannot be added/updated by requester" (+`TagKey`), object: "Your TagKey cannot be prefixed with aws:" (+`TagKey`); missing `Key` or `Value` element → `MalformedXML`.
- Terraform path: the S3 Control `TagResource`/`ListTagsForResource`/`UntagResource` flow in PROBE E2 (section 2). Shapes of the three operations, from the S3 Control model ([MODEL s3-control](https://github.com/aws/api-models-aws/blob/1cfdfb4bb9ea858e65623e66d73af04bec353201/models/s3-control/service/2018-08-20/s3-control-2018-08-20.json)): protocol `restXml`, XML namespace `http://awss3control.amazonaws.com/doc/2018-08-20/` (not the S3 namespace), host prefix `{AccountId}.`, required header `x-amz-account-id`. `ListTagsForResource GET /v20180820/tags/{ResourceArn+}` → `200`, `ListTagsForResourceResult` with `Tags/Tag{Key,Value}` (up to 50). `TagResource POST` same path, body `TagResourceRequest` with `Tags/Tag{Key,Value}` → `204`. `UntagResource DELETE` same path with repeated query `tagKeys=<key>` (up to 50) → `204`. The resource ARN in the path is `arn:aws:s3:::<bucket>` percent-encoded (PROBE E2). A missing bucket should answer the S3 Control error form (`NoSuchBucket` is an S3 code; S3 Control's own error shapes for these operations are not modeled, UNVERIFIED), so the safest emulation for a missing bucket is `404 NoSuchBucket` with `BucketName`.

#### 4.2.10 Object Lock configuration

- `Get` on a lock-enabled bucket with no default rule: `ObjectLockConfiguration/ObjectLockEnabled=Enabled`; with a default rule: plus `Rule/DefaultRetention{Mode=GOVERNANCE|COMPLIANCE, Days|Years}` (REC `test_get_put_object_lock_configuration`). `Put` on an existing versioned bucket enables it (`200`); without `ObjectLockEnabled` or with `Days` and `Years` together, a bad mode, an empty rule → `400 MalformedXML` (REC `test_put_object_lock_configuration_exc`).
- Objects written to a lock-enabled bucket with a retention period need `Content-MD5` or `x-amz-sdk-checksum-algorithm` ([DOC PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html)); the enforcement error is UNVERIFIED (moto uses `MissingUploadObjectWithObjectLockHeaders`, EMU). Terraform's `aws_s3_object` mentions the same rule ([TF object.go L583](https://github.com/hashicorp/terraform-provider-aws/blob/v6.68.0/internal/service/s3/object.go#L583)). Retention and legal-hold enforcement on delete is not phase 1.

#### 4.2.11 Subresources outside phase 1

Unimplemented subresources and operations must fail loudly with S3's error shape and the unimplemented message (brief rule). The legacy `aws_s3_bucket` read tolerates `NotImplemented`, `MethodNotAllowed`, `XNotImplemented` for its inline attributes (section 4.1 table), so `501` there is silent for Terraform by design. For `Put` on ACL and object lock Terraform tolerates HTTP 501 as well (TF bucket_acl.go L208, bucket_object_lock_configuration.go L140).

## 5. Objects: PutObject, GetObject, HeadObject

### 5.1 Keys

- Length 1 to 1,024 bytes of UTF-8 ([DOC object-keys](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-keys.html)); longer → `400 KeyTooLongError` ([DOC error list](https://docs.aws.amazon.com/AmazonS3/latest/API/API_Error.html)). Message "Your key is too long" with `MaxSizeAllowed=1024`, `Size=<n>` is from LocalStack's validation code, not a recording (EMU [validation.py L428-L437](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/s3/validation.py#L428-L437); the elements are UNVERIFIED).
- Keys are case sensitive (REC `TestS3::test_s3_uppercase_key_names`: a lower-cased lookup is `404 NoSuchKey`). Any UTF-8 is legal. `a//b`, a trailing `/`, a leading `/`, `.`/`..` segments, `%`, `+`, spaces and emoji are all distinct valid keys (REC `test_put_get_object_special_character` with `file%2Fname`, `test@key/`, `test%123`, `test%percent`, `test key/`, `test key//`, `a/%F0%9F%98%80/`). A key ending in `/` with an empty body is an ordinary object (the console's "folder"). Routing hazards for these are in [wire-rest.md 3.3](wire-rest.md).
- `NoSuchKey` carries a `Key` element; GetObjectTagging's error shows `Key` as `<bucket>/<key>` while DeleteObjectTagging and PutObjectTagging show the bare key (REC `TestS3BucketObjectTagging::test_object_tagging_exc`), a quirk worth copying only if a test compares it.

### 5.2 PutObject

Request: `PUT /{Key+}` with body; headers [MODEL `PutObjectRequest`](https://github.com/aws/api-models-aws/blob/1cfdfb4bb9ea858e65623e66d73af04bec353201/models/s3/service/2006-03-01/s3-2006-03-01.json): `Content-Length`, `Content-Type`, `Content-MD5`, `Content-Encoding`, `Content-Language`, `Content-Disposition`, `Cache-Control`, `Expires`, `x-amz-meta-*`, `x-amz-tagging`, `x-amz-storage-class`, `x-amz-acl` and `x-amz-grant-*`, `x-amz-website-redirect-location`, SSE headers (section 5.7), checksum headers (section 6), `If-Match`, `If-None-Match`, `x-amz-expected-bucket-owner`, `x-amz-request-payer`, object lock headers, `x-amz-write-offset-bytes` (directory buckets only). Size: a single PUT carries up to 5 GB ([DOC upload-objects](https://docs.aws.amazon.com/AmazonS3/latest/userguide/upload-objects.html)); larger → `400 EntityTooLarge` ([API_Error](https://docs.aws.amazon.com/AmazonS3/latest/API/API_Error.html)). `Content-Length` absent without chunked framing → `411 MissingContentLength`; fewer bytes than declared → `400 IncompleteBody` (same list).

Response `200`, empty body. Headers, from REC (`TestS3BucketEncryption::test_s3_bucket_encryption_sse_s3` and many others): `ETag` (quoted), `x-amz-server-side-encryption: AES256` **always** (the SSE-S3 default is applied and reported even when the client asked for nothing), `x-amz-checksum-<alg>` plus `x-amz-checksum-type: FULL_OBJECT` for whichever checksum was stored (section 6), `x-amz-version-id` only when the bucket versioning is `Enabled` (a `Suspended` bucket returns `null` ids, section 8), `x-amz-expiration` when a lifecycle rule matches, and for SSE-KMS `x-amz-server-side-encryption-aws-kms-key-id` (full key ARN), `x-amz-server-side-encryption-bucket-key-enabled: true` (only when true). No `Last-Modified` and no `Location`.

Overwrite semantics: the last writer wins; there is no per-key lock visible to clients except conditional writes (section 5.10) and, on versioned buckets, a new version per write ([DOC PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html)). Putting an object replaces tags: a PUT without `x-amz-tagging` clears the previous object's tags (REC `test_object_tags_delete_or_overwrite_object`: after overwrite `TagSet` is empty). The previous version's metadata is not merged; "You cannot use PutObject to only update a single piece of metadata" ([DOC](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html)).

Errors with REC-backed shapes: `NoSuchBucket` 404 (+`BucketName`); `InvalidStorageClass` 400 (section 5.6); `InvalidDigest`/`BadDigest` (section 5.11); checksum errors (section 6.3); `NotImplemented` 501 and `PreconditionFailed` 412 for conditional headers (section 5.10); `AccessControlListNotSupported` 400 on ACL headers when ownership is `BucketOwnerEnforced` (section 4.2.4); `KMS.*` 400 (section 5.7); `InvalidArgument` for a malformed `x-amz-tagging` (section 11). Metadata errors: section 5.4.

### 5.3 ETag rules

- Single PUT and CopyObject, plaintext or SSE-S3: the lowercase hex MD5 of the object bytes, quoted in headers and listings. Verified: `md5("test-encrypted")` = `16b66fb6b9c0e864b0291fa0dbb5a946` equals the recorded SSE-S3 ETag (REC `test_s3_bucket_encryption_sse_s3`; I recomputed it locally).
- SSE-KMS and SSE-C objects: "not an MD5 digest of their object data" ([DOC API_Object](https://docs.aws.amazon.com/AmazonS3/latest/API/API_Object.html)). Observed: the same body `test-sse` written to KMS-default buckets produced a different 32-hex ETag on every write (`8c4f00a5...`, `59252a09...`, `8a33ac88...`, REC `test_s3_sse_default_kms_key`), so a random 128-bit hex value per write matches. Do not derive it from the content: a client that compares MD5 to ETag would then succeed locally where it fails on AWS.
- Multipart objects: `"<hex>-<N>"` where `<hex>` = MD5 of the concatenation of each part's raw 16-byte MD5, `N` = number of parts ([DOC checking-object-integrity-upload](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html): "Amazon S3 concatenates the bytes for the MD5 digests together and then calculates the MD5 digest of these concatenated values ... adds a dash with the total number of parts"; implemented that way in [LocalStack models.py L508-L625](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/s3/models.py#L508-L625), EMU; REC shows `-1` for single-part MPUs and `-2` for two). Part ETags of a plaintext or SSE-S3 upload are plain MD5s (REC `upload-part` ETag `8d777f385d3dfec8815d20f7496026dc` = md5 of the 4-byte part). Under SSE-KMS a part's ETag is random, like a single PUT's, and the object's ETag is still the MD5 of the raw part ETags with `-N` (REC `test_s3_multipart_upload_sse`: part `1a9f0234...`, object `93a0cb8e...-1`).
- CopyObject of a multipart object produces a single-part object whose ETag is the MD5 of the full content: source `"b972025b...-1"` copied to `"eee506dd7ada7ded524c77e359a0e7c6"`, while its full-object CRC64NVME stayed `BsLNlKumA5I=` (REC `TestS3::test_multipart_copy_object_etag`).
- XML form: `<ETag>&quot;1d921b22...&quot;</ETag>` (entity-escaped quotes) in listings ([FIXTURE s3-list-objects.xml](https://github.com/boto/botocore/blob/bfb412faf00c249a54816e287a09a8bb79442c65/tests/unit/response_parsing/xml/responses/s3-list-objects.xml)); the HTTP header form is `ETag: "1d921b22..."`. DOC samples show literal quotes in XML; both parse identically in SDKs. Event notification JSON carries the ETag **without** quotes (REC, section 13).
- Matching: `If-Match`/`If-None-Match` accept the value with or without the quotes (REC `etag-missing-quotes` case: an unquoted `If-None-Match` still returned `304`).

### 5.4 Metadata (user and system)

- User metadata: request headers `x-amz-meta-<name>`; the name is lower-cased by S3 ([DOC UsingMetadata](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingMetadata.html): "Amazon S3 stores user-defined metadata keys in lowercase"). Underscores and a leading underscore are allowed (REC `test_metadata_header_character_decoding`: `test_meta_1`, `__meta_2` round-trip). Same-name headers (case-insensitive) are combined into one comma-separated value on retrieval ([DOC](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingMetadata.html)).
- Limits: the request header block is limited to 8 KB; user-defined metadata within it is limited to 2 KB, measured as the sum of UTF-8 bytes of every key and value ([DOC UsingMetadata](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingMetadata.html)). Overflow → `400 MetadataTooLarge`, "Your metadata headers exceed the maximum allowed metadata size." ([API_Error](https://docs.aws.amazon.com/AmazonS3/latest/API/API_Error.html)); extra elements on the error are UNVERIFIED. (Go's `net/http` server enforces its own header limit, `DefaultMaxHeaderBytes` 1 MiB, far above 8 KB: enforce 8 KB explicitly or accept the divergence.)
- Non-US-ASCII values: S3 decodes RFC 2047 encoded-words on store and re-encodes on return; pure ASCII passes through (the DOC example: `x-amz-meta-nonascii: ÄMÄZÕÑ S3` is returned as `=?UTF-8?B?w4PChE3Dg8KEWsODwpXDg8KRIFMz?=`, [DOC UsingMetadata](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingMetadata.html)). REC (`test_user_metadata_rfc2047_encoded`, `..._bad_b64_encoded`): inputs written as valid `=?UTF-8?Q?...?=` / `=?UTF-8?B?...?=` words come back as encoded words; `safe-chars` (`!"#$%&'()*+,-./:;<=>?@[\]^_`{|}~`) round-trip literally; a word with invalid base64 is kept as an encoded word of the replacement-character bytes. Unprintable values are dropped from the response and counted in `x-amz-missing-meta` ([DOC GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html)).
- System metadata (`Cache-Control`, `Content-Disposition`, `Content-Encoding`, `Content-Language`, `Content-Type`, `Expires`, `x-amz-website-redirect-location`) is stored as given and returned on GET/HEAD; `Expires` is returned as the original string (SDKs expose `ExpiresString`; REC `test_s3_object_expires`: past and future values both stored and returned). `Content-Encoding: gzip` is stored and the body is **not** decoded (REC `test_s3_upload_download_gzip`). `aws-chunked` is removed from `Content-Encoding` on store, and an `aws-chunked`-only value leaves it empty ([DOC sigv4-streaming](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-streaming.html)).
- **Default `Content-Type` is `binary/octet-stream`** (not `application/octet-stream`) when the PUT sends none; a CopyObject with `x-amz-metadata-directive: REPLACE` and no `Content-Type` also resets it to `binary/octet-stream` (REC `test_s3_copy_object_in_place_metadata_directive`: `ContentType: binary/octet-stream` after REPLACE).
- Response-header overrides on GET (`response-cache-control`, `response-content-disposition`, `response-content-encoding`, `response-content-language`, `response-content-type`, `response-expires`) apply only to a `200`/`206`, and require a signed request ([DOC GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html); REC `test_s3_get_object_header_overrides`). The error for an unsigned override request is UNVERIFIED.

### 5.5 Timestamps

- `Last-Modified` header: RFC 1123 in GMT with **second** precision (`Wed, 12 Oct 2009 17:50:00 GMT`, [DOC samples](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html)). XML `LastModified`: ISO 8601 with milliseconds, always `.000Z` in AWS samples (`2009-10-12T17:50:30.000Z`, [DOC ListObjects](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjects.html), [FIXTURE](https://github.com/boto/botocore/blob/bfb412faf00c249a54816e287a09a8bb79442c65/tests/unit/response_parsing/xml/responses/s3-list-objects.xml)). So store the write time truncated to the second and render both forms from it. All precondition comparisons are done at second resolution (REC `precondition-if-unmodified-since-is-object`: an `If-Unmodified-Since` equal to the object's own `Last-Modified` string passes; the object's true time has sub-second parts that a header cannot carry; LocalStack implements it by rounding to seconds, [utils.py L1002-L1041](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/s3/utils.py#L1002-L1041), EMU).
- The CopyObject response `LastModified` XML sample in the docs lacks the millisecond part (`2009-10-28T22:32:00`, [DOC CopyObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CopyObject.html)); SDKs parse both.
- The CopyObject result and a new MPU object both take "now" as Last-Modified; for a multipart object the version ordering follows the upload's initiation time ("the current version ... is determined by which upload started most recently (`createdDate`)", [DOC mpuoverview](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)); whether `Last-Modified` itself equals the initiation or the completion time is UNVERIFIED.
- Bucket `CreationDate` in ListBuckets is the creation time; all time-based behavior runs on the emulator clock per the brief.

### 5.6 Storage class

- `x-amz-storage-class` values accepted on general purpose buckets: `STANDARD`, `REDUCED_REDUNDANCY`, `STANDARD_IA`, `ONEZONE_IA`, `INTELLIGENT_TIERING`, `GLACIER`, `DEEP_ARCHIVE`, `GLACIER_IR` (the full enum also lists `OUTPOSTS`, `SNOW`, `EXPRESS_ONEZONE`, `FSX_*`, `AWS_BACKUP_*`, [DOC PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html)). Others → `400 InvalidStorageClass`, "The storage class you specified is not valid" with a `StorageClassRequested` element (REC `test_put_object_storage_class_outposts`: `OUTPOSTS` on a normal bucket, for both PutObject and CreateMultipartUpload).
- **HEAD/GET omit `x-amz-storage-class` for `STANDARD`** (REC: every `head-object`/`get-object` snapshot of a default object has no `StorageClass`; `GetObjectAttributes` and listings do show `STANDARD`). This confirms the "omitted for STANDARD" guess in [wire-rest.md 3.8](wire-rest.md).
- `GLACIER` and `DEEP_ARCHIVE` objects: `GetObject` → `403 InvalidObjectState`, "The operation is not valid for the object's storage class" with `StorageClass` element; `HeadObject` works and shows the class (REC `test_put_object_storage_class[GLACIER-False]`). `CopyObject` from such a source → `403 ObjectNotInActiveTierError` ([MODEL](https://github.com/aws/api-models-aws/blob/1cfdfb4bb9ea858e65623e66d73af04bec353201/models/s3/service/2006-03-01/s3-2006-03-01.json)). RestoreObject is outside phase 1.

### 5.7 Server-side encryption

Applies to PutObject, CopyObject, CreateMultipartUpload (the SSE settings live on the upload; UploadPart and Complete echo them), and GetObject/HeadObject responses.

- Request headers: `x-amz-server-side-encryption` (`AES256`, `aws:kms`, `aws:kms:dsse`), `x-amz-server-side-encryption-aws-kms-key-id`, `x-amz-server-side-encryption-context` (base64 of UTF-8 JSON), `x-amz-server-side-encryption-bucket-key-enabled`, and the SSE-C trio `...-customer-algorithm`, `...-customer-key`, `...-customer-key-MD5` ([DOC PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html)). These headers must not be sent on GET for SSE-S3/KMS objects: "you'll get an HTTP `400 Bad Request` error" ([DOC GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html)).
- Resolution (REC `test_s3_sse_default_kms_key`, `test_s3_sse_bucket_key_default`, `test_s3_multipart_upload_sse`, `test_s3_bucket_encryption_sse_kms`): no SSE headers → the bucket's default rule decides (AES256 unless changed); `aws:kms` without a key id → the AWS managed key `aws/s3`; responses always report `x-amz-server-side-encryption` and, for KMS, the full key ARN in `x-amz-server-side-encryption-aws-kms-key-id` whatever form the request used (key id, ARN or alias, [DOC](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html): "Key ID, Key ARN, or Key Alias"). `BucketKeyEnabled` is reported `true` when the bucket default rule or the request says so, and absent otherwise (REC `put-object-encrypted-bucket-key-disabled` has no such header). A header-level choice overrides what an object had: copying a KMS-encrypted object over itself with `x-amz-server-side-encryption: AES256` re-encrypts it as SSE-S3 and the response reports `AES256` (REC `TestS3::test_s3_copy_object_in_place_with_encryption`, `copy-object-in-place-with-aes`); that an explicit `AES256` on a plain PUT to a KMS-default bucket wins over the bucket default is the natural reading of the DOC and is not separately recorded (UNVERIFIED).
- Objects keep the settings they were written with; changing the bucket default affects later writes only (REC `get-obj-default-after-setting`).
- **KMS validation and failure modes are real S3 error codes**, all `400` with the code literally prefixed `KMS.` (REC `TestS3::test_s3_sse_validate_kms_key`, `test_s3_sse_validate_kms_key_state`):

| Situation | Code | Message |
|---|---|---|
| key id that is not a valid id/ARN/alias form (`fake-key-id`) | `KMS.NotFoundException` | `Invalid keyId 'fake-key-id'` |
| well-formed id/ARN of a key that does not exist | `KMS.NotFoundException` | `Key 'arn:<partition>:kms:<region>:<account>:key/<uuid>' does not exist` |
| ARN naming a different region than the bucket | `KMS.NotFoundException` | `Invalid arn <region>` |
| key disabled, on PUT, CopyObject or GET of an existing KMS object | `KMS.DisabledException` | `<key ARN> is disabled.` |
| key pending deletion | `KMS.KMSInvalidStateException` | `<key ARN> is pending deletion.` |

  The same checks run on `CreateMultipartUpload` and `CopyObject`. So a GET of an existing SSE-KMS object depends on the key's current state, which makes the KMS-S3 link observable (brief: "SSE-KMS buckets"). Which KMS operations S3 performs per request (GenerateDataKey on write, Decrypt on read; a data key per bucket-key period) is DOC-only detail; the emulator needs the key lookup and state check, and may store plaintext.
- Encryption context: stored and echoed; `CopyObject` needs it passed again to keep it (DOC `x-amz-server-side-encryption-context`).
- SSE-C: a new general purpose bucket rejects SSE-C writes with `403 AccessDenied` since April 2026 unless the bucket's encryption config unblocks it (DOC [blocking-unblocking-s3-c-encryption-gpb](https://docs.aws.amazon.com/AmazonS3/latest/userguide/blocking-unblocking-s3-c-encryption-gpb.html)). When enabled: algorithm `AES256`, 256-bit key base64, MD5 header must match; ETag not an MD5 (REC `TestS3SSECEncryption::*` shows the error family). Phase 1 can reject SSE-C with the 403 and leave the rest as a documented gap.

### 5.8 GetObject and HeadObject

- Success `200` (or `206`), headers from [MODEL `GetObjectOutput`/`HeadObjectOutput`](https://github.com/aws/api-models-aws/blob/1cfdfb4bb9ea858e65623e66d73af04bec353201/models/s3/service/2006-03-01/s3-2006-03-01.json): `Accept-Ranges: bytes`, `Last-Modified`, `Content-Length`, `ETag`, `Content-Type`, system metadata headers, `x-amz-meta-*`, `x-amz-version-id` (versioned buckets), `x-amz-server-side-encryption` (always, `AES256` by default; REC), `x-amz-tagging-count` (only when > 0; REC `head-obj-after-removal` has none), `x-amz-storage-class` (non-STANDARD), `x-amz-mp-parts-count` (with `partNumber` on a multipart object), `x-amz-expiration`, `x-amz-delete-marker`, `x-amz-restore`, `x-amz-missing-meta`, `x-amz-website-redirect-location`, `x-amz-object-lock-*`, `x-amz-replication-status`.
- Checksums are returned only when the request carries `x-amz-checksum-mode: ENABLED` ([DOC GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html)); both boto3 and the JS SDK send it on every GET by default (PROBE E5, E7), and botocore then **validates the body against the header** unless the value contains `-` (composite) ([SDK httpchecksum.py L548-L612](https://github.com/boto/botocore/blob/bfb412faf00c249a54816e287a09a8bb79442c65/botocore/httpchecksum.py#L548-L612)). Rule that keeps that validation safe on ranged reads (LocalStack code validated against AWS; [provider.py L1039-L1066](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/s3/provider.py#L1039-L1066), EMU, and REC `test_get_object_part_checksum`): on a ranged `206` return a checksum header only when the range covers the whole object; with `partNumber` on a composite multipart object return that part's checksum with `x-amz-checksum-type: COMPOSITE`; otherwise omit it. Returning the full-object checksum next to a partial body makes boto3 raise `FlexibleChecksumError`.
- Missing key: `404 NoSuchKey` with `Key`; missing bucket: `404 NoSuchBucket`. `HEAD` errors have no body (section 3.3; REC `head-object-404` → `Code "404"`). Without `s3:ListBucket`, real S3 answers `403` instead of `404`; phase 1 does not enforce IAM, so `404` ([DOC GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html)).
- `versionId`: on an **unversioned** bucket any value other than `null` → `400 InvalidArgument`, `ArgumentName=versionId`, "Invalid version id specified"; `null` returns the object (REC `test_get_object_with_version_unversioned_bucket`). On versioned buckets: unknown id → `404 NoSuchVersion`, "The specified version does not exist." (+`Key`, `VersionId`); a delete marker addressed by id → `405 MethodNotAllowed`, "The specified method is not allowed against this resource." with `Method=GET`, `ResourceType=DeleteMarker`, response headers `x-amz-delete-marker: true` and `Last-Modified` ([DOC GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html), REC `test_delete_object_versioned`); a current delete marker without id → `404 NoSuchKey` plus `x-amz-delete-marker: true`.
- `partNumber` (1 to 10000): returns that part's bytes as `206` with `Content-Range`, `Content-Length` of the part and `x-amz-mp-parts-count`; works for `HEAD` too (REC `test_get_object_part`: `ContentRange "bytes 5242896-5242911/5242912"`, `PartsCount 2`). Part number beyond the count → `416 InvalidPartNumber`, "The requested partnumber is not satisfiable" with `ActualPartCount`, `PartNumberRequested`. `partNumber` together with `Range` → `400 InvalidRequest`, "Cannot specify both Range header and partNumber query parameter" (REC, same test). For a non-multipart object `partNumber=1` behaves as the whole object; other values UNVERIFIED.
- Streaming a large object must not buffer it; the response body is a stream and `Content-Length` is known up front.

### 5.9 Range requests

- One range per request; multiple ranges are not supported ([DOC GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html): "Amazon S3 doesn't support retrieving multiple ranges of data per GET request"); how S3 reacts to a multi-range header (full `200` per RFC 9110 vs an error) is UNVERIFIED.
- Forms: `bytes=a-b`, `bytes=a-`, `bytes=-n`. Answer `206 Partial Content` with `Content-Range: bytes first-last/size`, `Content-Length` equal to the range length (REC `test_range_header_body_length`: `bytes 0-1023/2048` and `bytes 1024-2047/2048`; Ceph `test_ranged_big_request_response_code`: end beyond the object is clipped but a `bytes=3145728-5242880` request on an 8 MiB object returned exactly `bytes 3145728-5242880/8388608`, [test_s3.py L7580-L7600](https://github.com/ceph/s3-tests/blob/5522d1c351f75bc00ae0f64f742f3f095f5939d9/s3tests/functional/test_s3.py#L7580-L7600)).
- Start at or beyond the object size → `416`, code `InvalidRange`, message "The requested range is not satisfiable", with `<ActualObjectSize>8</ActualObjectSize>` and `<RangeRequested>bytes=1024-4096</RangeRequested>` (REC `test_invalid_range_error`). Any range on an empty object is also `416 InvalidRange` ([test_s3.py L7640-L7653](https://github.com/ceph/s3-tests/blob/5522d1c351f75bc00ae0f64f742f3f095f5939d9/s3tests/functional/test_s3.py#L7640-L7653)). A missing key with a Range header is plain `404 NoSuchKey` (REC `test_range_key_not_exists`).
- A syntactically invalid `Range` header is ignored by S3 and the full object is returned with `200` per RFC 9110 section 14.2 (S3's behavior for each malformed variant is UNVERIFIED); `x-amz-copy-source-range` is different and strict: malformed → `400 InvalidArgument`, out of bounds → `400/416 InvalidRange` (Ceph `test_multipart_copy_improper_range`, `test_multipart_copy_invalid_range`, [test_s3.py L6110-L6165](https://github.com/ceph/s3-tests/blob/5522d1c351f75bc00ae0f64f742f3f095f5939d9/s3tests/functional/test_s3.py#L6110-L6165)).

### 5.10 Conditional requests

**Reads (GetObject, HeadObject).** Headers `If-Match`, `If-None-Match`, `If-Modified-Since`, `If-Unmodified-Since`. REC (`TestS3::test_s3_get_object_preconditions[get_object|head_object]`, `test_precondition_failed_error`, validated 2026-02-21):

| Request | Result |
|---|---|
| `If-Match` ≠ ETag | `412`, `PreconditionFailed`, "At least one of the pre-conditions you specified did not hold", extra element `<Condition>If-Match</Condition>`; HEAD: bare `412` |
| `If-Unmodified-Since` earlier than `Last-Modified` | same, `<Condition>If-Unmodified-Since</Condition>`; equal or later → `200` |
| `If-None-Match` equal to ETag (quotes optional) | `304`, no body (HEAD and GET); other value → `200` |
| `If-Modified-Since` ≥ `Last-Modified` (not in the future) | `304`; earlier → `200`; **a date in the future is ignored** → `200` |
| none of the above | `200` |

Evaluation order, per RFC 9110 section 13.2.2 and the DOC statements: `If-Match` first; `If-Unmodified-Since` is evaluated only when `If-Match` is absent (DOC: "If-Match ... true, and If-Unmodified-Since ... false; then, S3 returns 200 OK and the data requested", [GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html)); then `If-None-Match`; `If-Modified-Since` only when `If-None-Match` is absent (DOC: `If-None-Match` false and `If-Modified-Since` true → `304`). LocalStack's implementation evaluates `If-Unmodified-Since` even when `If-Match` is true and so disagrees with the DOC on that one combination ([utils.py L1002-L1041](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/s3/utils.py#L1002-L1041), EMU); follow the DOC/RFC.

**Copy source conditions** (`x-amz-copy-source-if-match|none-match|modified-since|unmodified-since`). Every failure is `412 PreconditionFailed` with `<Condition>x-amz-copy-source-If-Match</Condition>` etc., including `none-match` and `modified-since` (where GET would say `304`) (REC `TestS3CopySourcePreconditions::test_s3_copy_object_preconditions`, validated 2026-02-23). A future `modified-since` is ignored. A quote-less ETag matches. DOC combination rules ([CopyObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CopyObject.html)): `if-match` true with `if-unmodified-since` false → proceeds (`200`); `if-none-match` false with `if-modified-since` true → `412`. Versioned: `if-modified-since` and `if-unmodified-since` compare the source version's `Last-Modified` (REC `..._versioned` cases).

**Conditional writes** (PutObject, CopyObject destination, CompleteMultipartUpload). REC `TestS3ObjectWritePrecondition::*` (validated 2026-02-21):

| Request | Result |
|---|---|
| `If-None-Match: *`, key does not exist | `200` |
| `If-None-Match: *`, key exists (a current delete marker counts as not existing) | `412`, `PreconditionFailed`, `<Condition>If-None-Match</Condition>` |
| `If-None-Match: <anything but *>` | `501 NotImplemented`, "A header you provided implies functionality that is not implemented", `<Header>If-None-Match</Header>`, `<additionalMessage>We don't accept the provided value of If-None-Match header for this API</additionalMessage>` |
| `If-Match: <etag>` equal | `200` |
| `If-Match: <etag>` not equal | `412`, `<Condition>If-Match</Condition>` |
| `If-Match: <etag>`, key missing (or current delete marker) | `404 NoSuchKey` (+`Key`) |
| `If-Match: *` | `501 NotImplemented`, `<Header>If-Match</Header>`, same `additionalMessage` text |
| both headers | `501 NotImplemented`, `<Header>If-Match,If-None-Match</Header>`, `<additionalMessage>Multiple conditional request headers present in the request</additionalMessage>` |

Races: if another write or a delete lands between the check and the commit → `409 ConditionalRequestConflict`, "The conditional request cannot succeed due to a conflicting operation against this resource." with `Condition` and `Key` (REC `test_multipart_if_none_match_with_delete`, `test_multipart_if_match_with_put`). Documented retry guidance ([DOC conditional-writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)): for PutObject retry; for CompleteMultipartUpload restart the whole upload. Multipart specifics: the condition is evaluated at **CompleteMultipartUpload** time against the object that exists then; an object written by someone else while the upload was open makes `If-None-Match: *` fail with `412` (REC `test_multipart_if_none_match_with_put`), and `If-Match` is compared to the ETag at completion (REC `test_multipart_if_match_etag`). The conditions apply to the current version only. Conditional writes require SigV4 ([DOC](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)). Evaluation must be atomic with the commit (one lock per key), and a failing condition must not leave a stored object behind.

**Conditional deletes** (DeleteObject, DeleteObjects element `ETag`). DeleteObject with `If-Match: <etag>`: mismatch → `412 PreconditionFailed` `<Condition>If-Match</Condition>` (REC `TestS3DeletePrecondition::test_delete_object_if_match_non_express`); `x-amz-if-match-last-modified-time` and `x-amz-if-match-size` on a general purpose bucket → `501 NotImplemented` with `<Header>` naming it and no `additionalMessage` (REC `..._modified_non_express`, `..._size_non_express`). DOC adds `If-Match: *` ("only succeed if the object exists", `412` if the latest version is a delete marker) and per-object results in DeleteObjects, where a failed precondition goes to `<Error>` (DOC [conditional-deletes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-deletes.html)); a missing object under either precondition is a `404`-class error (same page).

### 5.11 Content-MD5

- `Content-MD5` is the base64 of the 16-byte MD5 of the body. Not base64, wrong length, or wrong decoded length → `400 InvalidDigest`, "The Content-MD5 you specified was invalid.", extra element `<Content-MD5>` echoing the header (REC `TestS3::test_s3_invalid_content_md5`: `__invalid__`, `000`, `not base64 encoded checksum`, `MTIz`, `dGVzdC1zdHJpbmc=` all rejected, for PutObject and UploadPart).
- Valid but not matching → `400 BadDigest`, "The Content-MD5 you specified did not match what we received.", elements `<ExpectedDigest>` and `<CalculatedDigest>` (the recording shows `ExpectedDigest` as hex for PutObject and as the base64 of the sent header for UploadPart, `CalculatedDigest` as base64; a reading quirk, copy only if a test needs it).
- Current clients no longer send it by default. boto3 and the JS SDK send `x-amz-checksum-crc32` on `DeleteObjects`, `PutBucketTagging` etc. (PROBE E5, E7); DOC still says Content-MD5 "is required for all Multi-Object Delete requests" ([DeleteObjects](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteObjects.html)) but the MODEL models these as `requestChecksumRequired` with any flexible checksum acceptable (`httpChecksum` trait on 25 operations, [wire-rest.md 3.4](wire-rest.md)). The error for a request that carries neither is UNVERIFIED; accepting it is the lenient choice. Object Lock retention writes need MD5 or an `x-amz-sdk-checksum-algorithm` ([DOC PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html)).
- With a single-PUT `Content-MD5`, the ETag equals the MD5 only for SSE-S3/plaintext objects ([DOC checking-object-integrity-upload](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html): the legacy `Content-MD5` header "remains available for single part uploads using SSE-S3").

## 6. Checksums and `aws-chunked`

### 6.1 Algorithms

Ten algorithms exist as of the 2026-10 docs ([DOC checking-object-integrity](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity.html), [MODEL `ChecksumAlgorithm`](https://github.com/aws/api-models-aws/blob/1cfdfb4bb9ea858e65623e66d73af04bec353201/models/s3/service/2006-03-01/s3-2006-03-01.json)). Header `x-amz-checksum-<lowercase name>`, value = base64 of the big-endian digest bytes ([SDK botocore httpchecksum.py L60-L134](https://github.com/boto/botocore/blob/bfb412faf00c249a54816e287a09a8bb79442c65/botocore/httpchecksum.py#L60-L134): 4-byte and 8-byte CRCs via `int.to_bytes(n, 'big')`).

| Algorithm | Digest | Go stdlib? | Multipart full-object | Multipart composite | SDK support (computes) |
|---|---|---|---|---|---|
| `CRC32` | 4 B | `hash/crc32.IEEE` | yes | yes | all |
| `CRC32C` | 4 B | `hash/crc32.Castagnoli` | yes | yes | all (Python needs CRT) |
| `CRC64NVME` | 8 B | `hash/crc64` with `MakeTable(0x9a6c9329ac4bc9b5)`; matches the catalog check value `0xae8b14860a799888` for `"123456789"` and the AWS CLI's wire value `JYwwIoi0PuE=` for `"hi\n"` (I ran both) | yes | no | Go, botocore (CRT), JS, CLI (the CLI default) |
| `SHA1` | 20 B | yes | no | yes | all |
| `SHA256` | 32 B | yes | no | yes | all |
| `SHA512` | 64 B | yes | no | yes | Go (`AlgorithmSHA512`), botocore, Java v2, C++ ([algorithms.go](https://github.com/aws/aws-sdk-go-v2/blob/ab2110b01f03b3990bfd50208a8a05df1d8c5eac/service/internal/checksum/algorithms.go)); not Rust |
| `MD5` | 16 B | yes | no | yes | no SDK computes it as a flexible request checksum: Go, botocore and C++ lack it, Java throws `MD5 is not supported`, Rust aliases it to CRC32; the docs say "AWS SDKs do not automatically calculate MD5 checksums" (corrected from "enum only in Go", sources in [s3-checksum-residuals-and-record-backlog.md](s3-checksum-residuals-and-record-backlog.md) section 1.5) |
| `XXHASH64` | 8 B | **no** | no | yes | botocore, Java v2, C++, all through the AWS CRT; digest = 8-byte big-endian XXH64, seed 0 |
| `XXHASH3` | 8 B | **no** | no | yes | same; digest = 8-byte big-endian XXH3-64, seed 0 |
| `XXHASH128` | 16 B | **no** | no | yes | same; digest = 16 bytes, `high64` big-endian then `low64` big-endian (XXH3-128, seed 0) |

The brief lists "every flexible checksum algorithm". The three XXHash variants need an in-repo implementation (XXH64, XXH3-64 with default secret and seed 0, XXH3-128). SETTLED by [s3-checksum-residuals-and-record-backlog.md](s3-checksum-residuals-and-record-backlog.md) section 1 (previously UNVERIFIED here): the AWS CRT's `finalize()` writes the digest big-endian with seed 0 ([aws-checksums xxhash.c L227-L252](https://github.com/awslabs/aws-checksums/blob/12cd22e81543b8547132762023076ab6afa25559/source/xxhash.c#L227-L252)), botocore, Java v2 and the C++ SDK all wrap the CRT, and the base64 of those bytes goes into `x-amz-checksum-xxhash64|xxhash3|xxhash128`. ### 6.2 Request-side rules (single-part uploads)

REC (`TestS3PutObjectChecksum::*`, `test_s3_checksum_no_algorithm`, validated 2025-2026):
- Client sends exactly one `x-amz-checksum-<alg>` header with a valid value: S3 recomputes, compares, stores that algorithm and value. Mismatch → `400 BadDigest`, "The CRC32 you specified did not match the calculated checksum." (algorithm name upper-case; REC `test_multipart_upload_part_checksum_exception[CRC32]`).
- The header value is not valid base64 or has the wrong decoded length → `400 InvalidRequest`, "Value for x-amz-checksum-sha256 header is invalid."
- Two `x-amz-checksum-*` headers → `400 InvalidRequest`, "Expecting a single x-amz-checksum- header. Multiple checksum Types are not allowed."
- `x-amz-sdk-checksum-algorithm` without a matching checksum header or trailer → `400` ([DOC PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html)); a value that disagrees with the header's algorithm → `BadDigest` (same page). The header is informational when the matching `x-amz-checksum-*` is present.
- **No checksum sent at all**: S3 computes and stores `CRC64NVME` (full object) and reports it with `x-amz-checksum-type: FULL_OBJECT` (REC `test_s3_checksum_no_automatic_sdk_calculation`: `head-obj-no-checksum` → `ChecksumCRC64NVME`; DOC: "S3 automatically chooses the CRC-64/NVME ... algorithm", [checking-object-integrity-upload](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html)). The `PutObject` response carries that server-chosen checksum too (REC `TestS3::test_s3_copy_object_with_default_checksum[CRC64NVME]`, step `put-object-no-checksum`: response has `ChecksumCRC64NVME` and `ChecksumType FULL_OBJECT`), so always include it.
- Presigned PUT and POST uploads without a checksum also get `CRC64NVME` (REC `test_presigned_url_v4_x_amz_in_qs` head: `ChecksumCRC64NVME`; `S3PresignedPost::test_post_object_default_checksum`).
- A checksum header together with `Content-MD5`: both are validated (UNVERIFIED which error wins).
- Over plain HTTP the SDKs put the checksum in a header and sign `x-amz-content-sha256` = hex SHA-256 of the body (PROBE E4-E6); over HTTPS they use an unsigned trailer (SDK middleware above). The server cannot rely on `x-amz-content-sha256` being the hex digest: it may be `UNSIGNED-PAYLOAD` or a `STREAMING-*` value (section 6.3). When signature validation is on, a hex value is a promise about the body and mismatch is `400 XAmzContentSHA256Mismatch` (UNVERIFIED code, standard S3 behavior).

### 6.3 `aws-chunked` bodies and trailers

`x-amz-content-sha256` values ([DOC sigv4-auth-using-authorization-header](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-auth-using-authorization-header.html)): a hex SHA-256 (single chunk), `UNSIGNED-PAYLOAD`, `STREAMING-UNSIGNED-PAYLOAD-TRAILER`, `STREAMING-AWS4-HMAC-SHA256-PAYLOAD`, `STREAMING-AWS4-HMAC-SHA256-PAYLOAD-TRAILER`, and the SigV4A forms `STREAMING-AWS4-ECDSA-P256-SHA256-PAYLOAD[-TRAILER]`.

Headers on a chunked upload ([DOC sigv4-streaming](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-streaming.html)): `Content-Encoding: aws-chunked` (possibly `aws-chunked,gzip` with the custom coding after it), `x-amz-decoded-content-length: <object bytes>` **required for all** such requests, and either `Content-Length` (the encoded length) or `Transfer-Encoding` other than `identity` (then no `Content-Length`); with a trailer: `x-amz-trailer: x-amz-checksum-<alg>` ([DOC sigv4-streaming-trailers](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-streaming-trailers.html)).

Body grammar:

```
Unsigned, trailing checksum (STREAMING-UNSIGNED-PAYLOAD-TRAILER; SDK source and PROBE E7):
<hex chunk size>\r\n<chunk bytes>\r\n   ... repeated
0\r\n
x-amz-checksum-crc32:Nyb53Q==\r\n
\r\n

Signed (STREAMING-AWS4-HMAC-SHA256-PAYLOAD[-TRAILER]; DOC):
<hex size>;chunk-signature=<64 hex>\r\n<chunk bytes>\r\n   ... repeated
0;chunk-signature=<64 hex>\r\n                              (final, zero-length chunk is signed too)
x-amz-checksum-crc32c:sOO8/Q==\r\n                          (trailer, only with ...-TRAILER)
x-amz-trailer-signature:<64 hex>\r\n
\r\n
```

Facts: chunk size is hex without a prefix; the SDK default chunk is 64 KiB and signed chunks (except the last) must be at least 8 KiB ([DOC sigv4-streaming](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-streaming.html); [SDK aws_chunked_encoding.go L12-L28, L74-L78](https://github.com/aws/aws-sdk-go-v2/blob/ab2110b01f03b3990bfd50208a8a05df1d8c5eac/service/internal/checksum/aws_chunked_encoding.go#L12-L78) with the format comment). Signed chunk signatures chain: `string-to-sign = "AWS4-HMAC-SHA256-PAYLOAD\n" + timestamp + "\n" + scope + "\n" + previous-signature + "\n" + hex(sha256("")) + "\n" + hex(sha256(chunk))`; the trailer's string-to-sign is `"AWS4-HMAC-SHA256-TRAILER\n" + timestamp + "\n" + scope + "\n" + previous-signature + "\n" + hex(sha256("<name>:<value>\n"))`, with the DOC worked example (`x-amz-checksum-crc32c:sOO8/Q==` hashed with its trailing newline, trailer signature `d81f82fc...`) available as a test vector ([DOC sigv4-streaming-trailers](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-streaming-trailers.html)). The decoded bytes are what is stored and what `Content-Length` of a later GET reports; the stored `Content-Encoding` excludes `aws-chunked`. The server verifies `x-amz-decoded-content-length` equals the decoded byte count (mismatch is `400 IncompleteBody`, UNVERIFIED code) and that the trailer checksum matches the data (`BadDigest`).

Which clients send which (all observed): Go v2 over HTTP: header checksum, no chunking; Go v2 over HTTPS: `STREAMING-UNSIGNED-PAYLOAD-TRAILER` ([SDK](https://github.com/aws/aws-sdk-go-v2/blob/ab2110b01f03b3990bfd50208a8a05df1d8c5eac/service/internal/checksum/middleware_compute_input_checksum.go#L168-L190)); botocore over HTTPS for streaming-input operations: trailer, over HTTP: header ([httpchecksum.py L384-L393](https://github.com/boto/botocore/blob/bfb412faf00c249a54816e287a09a8bb79442c65/botocore/httpchecksum.py#L384-L393)); JS v3: unsigned trailer for streamed bodies **even over HTTP** (PROBE E7); older SDKs and signed uploads: `STREAMING-AWS4-HMAC-SHA256-PAYLOAD`. So the body parser is mandatory even for a plain-HTTP local endpoint.

HTTP-level framing: with `Transfer-Encoding: chunked` plus `aws-chunked`, the HTTP chunking is the outer layer and Go's `net/http` removes it; `aws-chunked` decoding is a separate inner step (PROBE E7). With `Expect: 100-continue` validate headers (bucket exists, preconditions, SSE key checks) before reading the body, then read.

### 6.4 Multipart checksums

## 7. CopyObject and UploadPartCopy

- Request: `PUT /{Key+}` with `x-amz-copy-source: [/]<bucket>/<key>[?versionId=<id>]`, URL-encoded (parsing hazards in [wire-rest.md 3.3](wire-rest.md)); pattern `\/?.+\/.+` ([DOC CopyObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CopyObject.html)). Not matching → `400 InvalidArgument`, `ArgumentName=x-amz-copy-source`, `ArgumentValue=<the header>`, "Invalid copy source object key" (REC `test_s3_copy_object_wrong_format`). Special characters in the source key (`file%2Fname`, `test@key/`, `test key//`, emoji, `+`) all copy correctly (REC `test_copy_object_special_character`).
- Limits: source up to 5 GB; bigger sources need UploadPartCopy ([DOC CopyObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CopyObject.html)).
- Source errors: missing source bucket → `404 NoSuchBucket` (+`BucketName` of the source); missing key → `404 NoSuchKey` (+`Key`); a source whose current version is a delete marker → `404 NoSuchKey`; a source `versionId` that names a delete marker → `400 InvalidRequest`, "The source of a copy request may not specifically refer to a delete marker by version id." (REC `test_s3_copy_object_src_not_exists`).
- Copying an object onto itself with nothing changed → `400 InvalidRequest`, "This copy request is illegal because it is trying to copy an object to itself without changing the object's metadata, storage class, website redirect location or encryption attributes." What counts as a change: `x-amz-metadata-directive: REPLACE`, a different `x-amz-storage-class`, a `x-amz-website-redirect-location`, different SSE attributes (REC `test_s3_copy_object_in_place*`: no change → 400; REPLACE → 200; a new storage class on an unchanged `STANDARD` object succeeded in the recording; SSE-KMS to SSE-S3 → 200). Adding only an ACL does not count (REC `copy-object-in-place-with-acl` → 400). With a checksum algorithm change the in-place copy succeeded and returned the new `ChecksumSHA256` (REC `copy-object-in-place-with-storage-class` step).
- Metadata: `x-amz-metadata-directive: COPY` (default) copies user and system metadata (`Content-Type`, `Content-Language`, ...) and ignores any metadata headers in the request; `REPLACE` takes metadata only from the request: user metadata not resent is lost, `Content-Language` is lost, `Content-Type` falls back to `binary/octet-stream` when omitted (REC `test_s3_copy_object_in_place_metadata_directive`, `test_s3_copy_metadata_replace`, `test_s3_copy_metadata_directive_copy`). `x-amz-website-redirect-location` is never inherited, it must be restated ([DOC CopyObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CopyObject.html)); an in-place copy that sets it keeps it (REC `test_s3_copy_object_in_place_website_redirect_location`).
- Tags: `x-amz-tagging-directive: COPY` (default) carries the source tags and **ignores** `x-amz-tagging` in the request; `REPLACE` takes tags from `x-amz-tagging` and an empty value clears them (REC `test_s3_copy_tagging_directive[COPY|REPLACE|None]`: `COPY` and the absent header both kept `key1=value1`; `REPLACE` with `key2=value2` gave `key2=value2`; `REPLACE` with an empty header gave an empty TagSet).
- Encryption: the destination uses the destination bucket's default unless the request names SSE headers; a KMS source copied without SSE headers into a plain bucket is re-encrypted with the bucket default, SSE-S3 (REC `copy-object-in-place-without-kms-sse` → `AES256`). The new ETag is a fresh value for KMS destinations and the MD5 of the content for SSE-S3 (section 5.3).
- Checksums: the copy keeps the source's stored algorithm and full-object value; a source with none gets `CRC64NVME` computed; `x-amz-checksum-algorithm` on the copy recomputes under the new algorithm (REC `test_s3_copy_object_with_checksum[...]`, `test_s3_copy_object_with_default_checksum[...]`). A multipart source becomes a single-part object (ETag changes to the content MD5, section 5.3). The result carries `ChecksumType FULL_OBJECT`.
- Response: `200` with `CopyObjectResult{ETag, LastModified, ChecksumType, Checksum<ALG>}`, headers `x-amz-server-side-encryption`, `x-amz-server-side-encryption-aws-kms-key-id`, `x-amz-version-id` (destination version, when versioned), `x-amz-copy-source-version-id` (source version, when the source bucket is versioned) (REC `test_s3_copy_object_if_source_modified_since_versioned`: `CopySourceVersionId`, `VersionId`). The body may be an `<Error>` under a `200` (section 3.7 of [wire-rest.md](wire-rest.md)).
- Conditions: section 5.10 (copy-source and destination conditions).
- **UploadPartCopy** (`PUT /{Key+}?partNumber=&uploadId=` plus `x-amz-copy-source`): optional `x-amz-copy-source-range: bytes=first-last` with zero-based inclusive offsets; anything else → `400 InvalidArgument`, `ArgumentName=x-amz-copy-source-range`, `ArgumentValue=<value>`, "The x-amz-copy-source-range value must be of the form bytes=first-last where first and last are the zero-based offsets of the first and last bytes to copy" (REC `TestS3Multipart::test_upload_part_copy_range`: `0-8`, `bytes=1-0`, `bytes=-1-`, `bytes=0--1` all rejected); a range beyond the source size → `416`/`400` `InvalidRange` (Ceph accepts either status, [test_s3.py L6110-L6130](https://github.com/ceph/s3-tests/blob/5522d1c351f75bc00ae0f64f742f3f095f5939d9/s3tests/functional/test_s3.py#L6110-L6130)). No range = the whole source. Response `CopyPartResult{ETag, LastModified, Checksum...}` (the ETag is the MD5 of the copied bytes) plus `x-amz-copy-source-version-id` and SSE headers. The same copy-source conditions apply (REC `test_upload_part_copy_with_*`). Parts may be smaller than 5 MiB until the Complete call (REC `list-parts` shows parts of 9, 1 and 1 bytes). Events: an UploadPartCopy-built object is reported by `s3:ObjectCreated:CompleteMultipartUpload` ([DOC notification types](https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-how-to-event-types-and-destinations.html)).

## 8. Deleting objects, and the minimum version model

### 8.1 DeleteObject

- Always `204` with an empty body for an existing key, a missing key, and a key in an unversioned bucket alike (REC `test_delete_object`: delete, then delete-nonexistent, both `204`). Missing bucket → `404 NoSuchBucket`.
- Unversioned bucket: `versionId=null` deletes the object; any other `versionId` → `400 InvalidArgument`, `ArgumentName=versionId`, `ArgumentValue=<id>`, "Invalid version id specified" (REC `test_delete_object`).
- Versioned bucket (`Enabled`): no `versionId` → adds a delete marker, response `204` with `x-amz-delete-marker: true` and `x-amz-version-id: <marker id>`; deleting a key that does not exist still adds a marker (REC `delete-wrong-key`); `versionId=<id>` removes that version permanently, `204` with `x-amz-version-id: <id>` (plus `x-amz-delete-marker: true` when it was a marker); an id that is syntactically wrong → `400 InvalidArgument` "Invalid version id specified" (REC `delete-with-bad-version`, `test_delete_object_versioned`). `Suspended`: a delete without id adds a delete marker; a PUT writes the `null` version and returns no `x-amz-version-id` header (REC `test_put_object_on_suspended_bucket`, `test_delete_object_on_suspended_bucket`; the marker's literal id string in that case is UNVERIFIED).
- Version ids are 32-character strings from `[A-Za-z0-9._]` (REC `test_object_version_id_format`, "tested against more than 100 AWS VersionIds"; example `gS53zabD7XTvkrwbjMnXlBylVWetO8ym`).
- `x-amz-bypass-governance-retention`, `x-amz-mfa` and Object Lock enforcement: outside phase 1.

### 8.2 DeleteObjects

- `POST /?delete` (query key `delete`), body `Delete{Quiet?, Object{Key, VersionId?, ETag?, LastModifiedTime?, Size?}+}`, up to 1,000 keys ([DOC DeleteObjects](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteObjects.html)); the error for more than 1,000 is UNVERIFIED (LocalStack leaves a TODO, [provider.py L1376](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/s3/provider.py#L1376)); zero objects → `MalformedXML` (EMU, same code). Needs a checksum header (`x-amz-checksum-*`) or `Content-MD5` from clients (section 5.11); both SDKs send `x-amz-checksum-crc32` (PROBE E5, E7).
- Response `200`, `DeleteResult` with `Deleted{Key, VersionId?, DeleteMarker?, DeleteMarkerVersionId?}*` and `Error{Key, VersionId?, Code, Message}*` (MODEL `DeleteObjectsOutput`; REC): keys that do not exist are reported as `Deleted` (REC `test_delete_non_existing_keys`); `Quiet=true` omits all `Deleted` entries and returns only errors (REC `test_delete_non_existing_keys_quiet`: empty `DeleteResult`); missing bucket → `404 NoSuchBucket`. Versioned: `Deleted` entries carry `DeleteMarker=true` and `DeleteMarkerVersionId` for the markers created, and `VersionId` + (`DeleteMarker`, `DeleteMarkerVersionId` when it was a marker) for explicit ids (REC `test_delete_objects_versioned`); a bogus `VersionId` is an `Error`: `Code=NoSuchVersion`, `Message="The specified version does not exist."`, `Key`, `VersionId` — with HTTP status `200` for the call (REC `test_delete_objects`, which shows boto3's `Errors` list).
- With `encoding-type=url` the returned keys are URL-encoded (REC `test_delete_objects_encoding`: `a%2Fb`, `a/%F0%9F%98%80`).
- Conditional entries: `ETag` (or `*`) per object triggers a precondition on that key; failure lands in `Error` (DOC [conditional-deletes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-deletes.html)).
- One `ObjectRemoved:Delete` (or `DeleteMarkerCreated`) event per key (REC `TestS3NotificationsToSQS::test_delete_objects`).

### 8.3 What phase 1 needs from versions

Bucket versioning is a documented subresource and Terraform sets and reads it, but the brief's S3 list does not name version listing. Evidence says a minimum is unavoidable: `terraform destroy` with `force_destroy` empties the bucket through `ListObjectVersions` (section 2, E4), and `aws_s3_object` deletes use the stored `version_id`. Two valid designs:
1. Always keep a version chain (null version for unversioned buckets, `VersionId` = the literal string `null` in `ListObjectVersions` for objects written before versioning or while suspended; LocalStack does this and its recordings are consistent, `test_list_object_versions_order_unversioned`).
2. Keep versions only where `Enabled`/`Suspended`, and synthesize the single `null` version for unversioned buckets in `ListObjectVersions`.
Either way the observable rules are the ones in 8.1, 8.2, section 5.8 (`NoSuchVersion`, 405 on markers), and the listing in 9.3. Object Lock, replication, MFA delete and `x-amz-restore` are outside phase 1.

### 9.1 ListObjectsV2 and ListObjects (v1)

Parameters ([DOC ListObjectsV2](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectsV2.html), [ListObjects](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjects.html)): `prefix`, `delimiter`, `max-keys` (default and cap 1,000), `encoding-type` (`url`), v2: `list-type=2`, `continuation-token`, `start-after`, `fetch-owner`; v1: `marker`. Both accept `x-amz-optional-object-attributes: RestoreStatus`.

Response `ListBucketResult` (same root for both): `Name`, `Prefix` (empty element when none), `Delimiter` (only when sent), `MaxKeys`, `EncodingType` (only when requested), `IsTruncated`, `Contents*` (`Key`, `LastModified`, `ETag`, `Size`, `StorageClass`, `ChecksumAlgorithm*`, `ChecksumType`, `Owner` where applicable, `RestoreStatus`), `CommonPrefixes/Prefix*`; v1 adds `Marker` (always, empty when none) and `NextMarker`; v2 adds `KeyCount`, `ContinuationToken` (echo), `NextContinuationToken`, `StartAfter` (echo). Wire form: `<Prefix></Prefix>` and `<Marker></Marker>` empty elements ([FIXTURE](https://github.com/boto/botocore/blob/bfb412faf00c249a54816e287a09a8bb79442c65/tests/unit/response_parsing/xml/responses/s3-list-objects.xml)).

Semantics, REC unless noted (`test_s3_list_operations.snapshot.json`, validated 2026-02-21):
- Order: ascending by the key's UTF-8 bytes (`test_0, test_1, test_10, test_11, test_2`); with `encoding-type=url` the order is by the raw key and encoding is applied afterwards (Ceph `test_bucket_list_encoding_basic`: `foo%2B1/`, `foo/`, `quux%20ab/` because `foo+1/` < `foo/`, [test_s3.py L237-L262](https://github.com/ceph/s3-tests/blob/5522d1c351f75bc00ae0f64f742f3f095f5939d9/s3tests/functional/test_s3.py#L237-L262)).
- `delimiter`: keys that contain the delimiter after `prefix` collapse into one `CommonPrefixes/Prefix` (= prefix + text up to and including the first delimiter); each common prefix counts as one against `max-keys`; the delimiter may be longer than one character (DOC "the string specified by a delimiter"); a `prefix` without a trailing slash works (`prefix=test/foo`, `delimiter=/` → `test/foo/`; `test_list_objects_v2_with_prefix_and_delimiter`). Common prefixes not greater than the marker or `start-after` are dropped (DOC).
- Truncation: `IsTruncated=true` when more entries remain; v1 returns `NextMarker` **only when `delimiter` was sent** (`test_list_objects_next_marker`: without a delimiter a truncated page has no `NextMarker` and the client continues from the last key); the value is the last key or last common prefix returned. v2 returns an opaque `NextContinuationToken` and echoes `ContinuationToken` on the follow-up page. The token is opaque; `ContinuationToken` and `StartAfter` together: the token wins (`test_list_objects_v2_continuation_start_after`). A made-up token → `400 InvalidArgument`, `ArgumentName=continuation-token`, "The continuation token provided is incorrect". Tokens must survive any key characters, including `%`, `+` and non-ASCII (`test_list_objects_v2_continuation_token_safe_chars`); a base64url encoding of the last key plus a marker bit is enough.
- `start-after` / `marker` are compared literally against raw keys; they are not URL-decoded, and when `encoding-type=url` is on, `StartAfter` is echoed encoded ([wire-rest.md 3.4](wire-rest.md); REC `test_list_objects_v2_continuation_token_safe_chars` cases `list-objects-start-after-url-type`).
- `max-keys=0`: empty page, `IsTruncated=false` (Ceph `test_bucket_list_maxkeys_zero`, [test_s3.py L1030-L1052](https://github.com/ceph/s3-tests/blob/5522d1c351f75bc00ae0f64f742f3f095f5939d9/s3tests/functional/test_s3.py#L1030-L1052), EMU run against RGW; AWS UNVERIFIED). A non-integer `max-keys` → `400 InvalidArgument` (same suite). Values above 1,000 are capped (DOC).
- `encoding-type`: only `url`; anything else, including an empty value, → `400 InvalidArgument`, `ArgumentName=encoding-type`, "Invalid Encoding Method specified in Request" (also for ListObjectVersions and ListMultipartUploads; `test_list_ops_encoding_type_validation`). Encoded fields: [wire-rest.md 3.4](wire-rest.md).
- `Owner` appears on v1 entries always and on v2 entries only with `fetch-owner=true` (v1 REC shows `Owner{ID}`; DOC for v2). `Owner.DisplayName` is not returned in the recordings.
- `StorageClass` is present on every entry, including `STANDARD`; in-progress multipart uploads are never listed ([DOC ListObjectsV2](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectsV2.html)).
- Missing bucket → `404 NoSuchBucket` (+`BucketName`; virtual-hosted and path-style alike, REC `test_bucket_does_not_exist`).
- boto3 adds `encoding-type=url` by default and decodes with `unquote_plus`, so a literal `+` in a key must be written as `%2B` ([wire-rest.md 3.4](wire-rest.md)); the AWS CLI also sends it (PROBE E6) and Go does not.

## 12. Presigned URLs

Scope: what an emulator validates when SigV4 checking is on (opt-in per the brief). Everything below is from [DOC sigv4-query-string-auth](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-query-string-auth.html), [DOC using-presigned-url](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html) and REC `TestS3PresignedUrl::*` (validated 2025-2026) unless stated.

- Query parameters: `X-Amz-Algorithm=AWS4-HMAC-SHA256`, `X-Amz-Credential=<access key>/<yyyymmdd>/<region>/s3/aws4_request`, `X-Amz-Date=<yyyymmddThhmmssZ>`, `X-Amz-Expires=<seconds>` (**1 to 604,800**), `X-Amz-SignedHeaders=<names>` (must include `host`, plus every `x-amz-*` header that will be sent), `X-Amz-Signature=<hex>`; optional `X-Amz-Security-Token`.
- Canonical request for S3: method, URI-encoded path **encoded once and not normalized** (the Go S3 client sets `DisableURIPathEscaping = true`; [SDK api_client.go L696-L699](https://github.com/aws/aws-sdk-go-v2/blob/ab2110b01f03b3990bfd50208a8a05df1d8c5eac/service/s3/api_client.go#L696-L699)), canonical query (all parameters except `X-Amz-Signature`, sorted, URI-encoded), canonical headers, signed headers, and the literal payload hash `UNSIGNED-PAYLOAD` ("you don't include a payload hash ... you use a constant string"). Header-signed requests use the `x-amz-content-sha256` value instead ([DOC sigv4-auth-using-authorization-header](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-auth-using-authorization-header.html)); `UNSIGNED-PAYLOAD` is also valid there.
- Expiry: the request is valid from `X-Amz-Date` to `X-Amz-Date + X-Amz-Expires`. Expired → `403 AccessDenied`, "Request has expired", extra elements `X-Amz-Expires`, `Expires` (the expiry time), `ServerTime` (REC `test_s3_presigned_url_expired[s3v4]`). The skew rule for header-signed requests is 15 minutes (`RequestTimeTooSkewed` 403, [API_Error](https://docs.aws.amazon.com/AmazonS3/latest/API/API_Error.html); the 15-minute figure is from the SigV4 spec, UNVERIFIED in the pages read). G4 correction: the expiry comparison (`X-Amz-Date + X-Amz-Expires`) uses the emulator clock so tests can advance it, but the 15-minute header skew check and the "not yet valid" check must use the wall clock, because every SDK signs `X-Amz-Date` with its own wall clock ([lambda-runtime-contract.md](lambda-runtime-contract.md) section 3 rows 9 and 10; Go and botocore signing sources cited there).
- Missing required query parameters → `400 AuthorizationQueryParametersError`, "Query-string authentication version 4 requires the X-Amz-Algorithm, X-Amz-Credential, X-Amz-Signature, X-Amz-Date, X-Amz-SignedHeaders, and X-Amz-Expires parameters." (REC `test_s3_put_presigned_url_missing_sig_param[s3v4]`).
- Bad signature → `403 SignatureDoesNotMatch`, "The request signature we calculated does not match the signature you provided. Check your key and signing method." with elements `AWSAccessKeyId`, `StringToSign`, `StringToSignBytes`, `SignatureProvided`, `CanonicalRequest`, `CanonicalRequestBytes` (REC `test_presigned_url_signature_authentication[s3v4-*]`). Signed `Content-Type` or `Content-Encoding` that differs from the sent header → `SignatureDoesNotMatch` (REC `test_s3_put_presigned_url_with_different_headers[s3v4]`); a header that must be signed but is not (for example `x-amz-expires` sent as a header) → `403 AccessDenied`, "There were headers present in the request which were not signed" with `HeadersNotSigned` (REC `test_s3_put_presigned_url_same_header_and_qs_parameter`).
- Unknown access key → `403 InvalidAccessKeyId` (DOC error list). The account is derived from the access key (brief); IAM is not enforced.
- Presigned PUT without a checksum header stores `CRC64NVME` like any other write (REC). Presigned POST (`multipart/form-data` browser uploads with a policy document) is a separate feature: error codes `MalformedPOSTRequest`, `InvalidPolicyDocument`, `IncorrectNumberOfFilesInPostRequest`, `UserKeyMustBeSpecified`, event `ObjectCreated:Post`; not in the phase 1 list.
- Response-header overrides (`response-content-disposition` etc.) are part of the signed query string and require a signed request (section 5.4).

## 13. Event notifications

Phase 1 is "should-have: SQS, SNS and Lambda destinations". Sources: [DOC notification content structure](https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-content-structure.html), [DOC types and destinations](https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-how-to-event-types-and-destinations.html), [DOC PutBucketNotificationConfiguration](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutBucketNotificationConfiguration.html), REC `test_s3_notifications_{sqs,sns,lambda}.snapshot.json` and `TestS3BucketNotificationConfiguration::*`.

### 13.1 Configuration

- `PUT /?notification` replaces the whole configuration atomically; an empty `<NotificationConfiguration/>` clears it; `GET` returns the stored configuration, or the empty element ([DOC](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutBucketNotificationConfiguration.html)). Optional request header `x-amz-skip-destination-validation: true`.
- Wire element names differ from the model's member names ([MODEL](https://github.com/aws/api-models-aws/blob/1cfdfb4bb9ea858e65623e66d73af04bec353201/models/s3/service/2006-03-01/s3-2006-03-01.json)): `TopicConfiguration{Id, Topic, Event+, Filter}`, `QueueConfiguration{Id, Queue, Event+, Filter}`, `CloudFunctionConfiguration{Id, CloudFunction, Event+, Filter}` for Lambda, `EventBridgeConfiguration` (empty element enables it). `Filter/S3Key/FilterRule{Name, Value}`; `Name` is `prefix` or `suffix`, case-insensitive on input and **returned capitalized** `Prefix`/`Suffix`; an empty `Value` is accepted (REC `test_filter_rules_case_insensitive`, `test_filter_rules_empty_value`). Invalid name → `400 InvalidArgument`, `ArgumentName=FilterRule.Name`, `ArgumentValue=<name>`, "filter rule name must be either prefix or suffix"; a rule missing `Name` or `Value` → `MalformedXML` (REC `TestS3BucketNotificationConfiguration::*`). `Id` is optional; S3 generates one when absent (EMU/REC: the Id in `GET` is never empty). The `Event` strings come from the 31-value enum in the model, for example `s3:ObjectCreated:*`, `s3:ObjectCreated:Put|Post|Copy|CompleteMultipartUpload`, `s3:ObjectRemoved:*|Delete|DeleteMarkerCreated`, `s3:ObjectTagging:*|Put|Delete`, `s3:ObjectAcl:Put`, `s3:LifecycleExpiration:*`, `s3:ObjectRestore:*`, `s3:Replication:*`, `s3:ReducedRedundancyLostObject`; an unknown event → `InvalidArgument` ("The event 'x' is not supported for notifications ...", moto, EMU; REC not recorded).
- Per-destination ARN checks happen first and are not skippable: a malformed ARN → `400 InvalidArgument`, `ArgumentName=Queue|Topic|CloudFunction`, `ArgumentValue=<arn>`, "The ARN could not be parsed" (REC `test_invalid_sqs_arn`, `test_invalid_topic_arn`, `test_invalid_lambda_arn`). Note the XML element name in `ArgumentName` (`Queue`, `Topic`, `CloudFunction`).
- Destination validation (skipped by the header): S3 checks that each destination exists and that S3 may publish, by sending a test message. Failure → `400 InvalidArgument`, "Unable to validate the following destination configurations", with numbered pairs `ArgumentName1`/`ArgumentValue1`, `ArgumentName2`/`ArgumentValue2` when several fail; `ArgumentName` is the destination ARN, `ArgumentValue` one of "The destination queue does not exist", "Permissions on the destination queue do not allow S3 to publish notifications from this bucket" (topic: "...topic..."), "The destination Lambda does not exist" or "Not authorized to invoke function [<arn>]" (with `ArgumentName` = `<arn>, null`) (REC `test_queue-does-not-exist` and `test_multiple_invalid_sqs_arns`: `ArgumentName1/2`, `ArgumentValue1/2`; `lambda-does-not-exist` recorded as `ArgumentName1: "<arn>, null"`, `ArgumentValue1: "Not authorized to invoke function [<arn>]"`; topic and "permissions" wording from LocalStack's validation code that was written against AWS, [notifications.py L400-L600](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/localstack-core/localstack/services/s3/notifications.py#L400-L600), EMU). Destinations must be in the same region as the bucket; SQS FIFO queues and SNS FIFO topics are not allowed ([DOC types and destinations](https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-how-to-event-types-and-destinations.html)). The Lambda check is a permission check (resource policy allowing `s3.amazonaws.com` for the bucket ARN), not a test invocation ([DOC PutBucketNotificationConfiguration](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutBucketNotificationConfiguration.html)).
- **TestEvent**: on a successful configuration of SQS or SNS destinations S3 delivers one message `{"Service":"Amazon S3","Event":"s3:TestEvent","Time":"2014-10-13T15:57:02.089Z","Bucket":"<bucket>","RequestId":"...","HostId":"..."}` to each destination ([DOC notification content structure](https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-content-structure.html)). It is not in the `Records` format. Recorded tests had to skip it when draining queues (REC [test_s3_notifications_sqs.py L136-L142](https://github.com/localstack/localstack/blob/8b9a79f05846835cf4dff63ab7eefdde9df83783/tests/aws/services/s3/test_s3_notifications_sqs.py#L136-L142)), so real S3 sends it. Lambda receives no test invocation.
- Terraform: `aws_s3_bucket_notification` sends the configuration in one call with generated `Id`s and reads it back; for a bucket that already has notification configuration it replaces it ([TF bucket_notification.go L317-L330](https://github.com/hashicorp/terraform-provider-aws/blob/v6.68.0/internal/service/s3/bucket_notification.go#L317-L330); PROBE E1: `PUT ?notification`, `GET ?notification` twice). A destroy sends an empty `<NotificationConfiguration/>` (PROBE E4).
- A policy on the queue/topic and a Lambda permission are what real S3 needs; phase 1 does not enforce IAM, so skip the permission checks but keep the existence checks, or make the permission check a lenient lookup of the stored policy.

### 13.2 Delivery

- Event names map from operations: `PutObject` → `ObjectCreated:Put`; browser POST → `ObjectCreated:Post`; `CopyObject` → `ObjectCreated:Copy`; `CompleteMultipartUpload` (and UploadPartCopy-built objects) → `ObjectCreated:CompleteMultipartUpload`; `DeleteObject` on an unversioned bucket or with a version id → `ObjectRemoved:Delete`; simple delete on a versioned bucket → `ObjectRemoved:DeleteMarkerCreated`; `DeleteObjects` → one event per key; `PutObjectTagging` → `ObjectTagging:Put`; `DeleteObjectTagging` → `ObjectTagging:Delete`; `PutObjectAcl` → `ObjectAcl:Put` (DOC; REC `test_object_created_*`, `test_object_tagging_*`, `test_object_put_acl`, `test_delete_objects`).
- A configuration matches when its event list covers the event (wildcards `*`) and the key satisfies **both** filter rules; prefix and suffix compare against the raw key (REC `test_notifications_with_filter`). An object that matches several configurations produces one message per configuration, each with its own `configurationId` (DOC; each destination one message).
- Message body for SQS: the JSON event document as the SQS message body. For SNS: published to the topic with `Subject: "Amazon S3 Notification"`; the SNS envelope's `Message` is the event JSON string (REC `TestS3NotificationsToSns::test_object_created_put`: `Type Notification`, `Subject "Amazon S3 Notification"`, `TopicArn`, `Message {Records:[...]}`). For Lambda: asynchronous invocation (event type) with the event JSON as the payload (REC `TestS3NotificationsToLambda`; the invoke type is DOC/EMU, not itself recorded).
- Event JSON ([DOC](https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-content-structure.html), REC): `Records[]` with `eventVersion`, `eventSource "aws:s3"`, `awsRegion` (the **bucket's** region), `eventTime` (ISO 8601 with milliseconds, `...000Z`), `eventName` without the `s3:` prefix, `userIdentity{principalId}`, `requestParameters{sourceIPAddress}`, `responseElements{x-amz-request-id, x-amz-id-2}`, `s3{s3SchemaVersion "1.0", configurationId, bucket{name, ownerIdentity{principalId}, arn}, object{key, size, eTag, versionId?, sequencer}}`. `object.key` is **URL-encoded** (space as `+`, `@` as `%40`; REC `test_key_encoding`: `a@b` → `a%40b`), `eTag` has **no quotes**, `size` is a number; `versionId` only on versioned buckets; `sequencer` is a hex string that increases per key (compare after left-padding). `ObjectRemoved:*` events have no `size` or `eTag` (REC `test_object_created_and_object_removed`); `ObjectTagging:*` and `ObjectAcl:Put` events carry `eTag` but no `size` or `sequencer` and used `eventVersion` `2.3` in the recordings.
- Version string: DOC says `2.6` for current schemas; the 2025 recordings show `2.1` (general events) and `2.3` (tagging, ACL). Clients are told to compare only the major version, so either works; use `2.1`-compatible content with `2.6` if matching the doc, UNVERIFIED which AWS emits today.
- Delivery is at least once and unordered; message size ≤ 64 KB; an SQS queue with a smaller `MaximumMessageSize` drops the message ([DOC](https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-content-structure.html)). Real delivery latency is seconds; on the emulator it should be prompt and go through the journal and clock (brief: causal journal).
- The notification must not be sent for a failed request, and the PutObject response must not wait for delivery.

## Implications for understudy

Each item is a decision the S3 implementer can take directly. Items marked (scope) are for the planner.

### Data model

1. **Bucket record = identity plus a typed subresource set.** One struct per subresource, each `Option`-like (absent means "not configured"), not a bag of XML strings. Seed at `CreateBucket`: ownership `BucketOwnerEnforced`, public access block all `true`, encryption `AES256` with `BucketKeyEnabled=false`, versioning absent, ACL owner `FULL_CONTROL` (section 4.1). Deleting encryption restores the default rule rather than leaving it unset. Drive the not-configured errors from one table (code, status, message, `BucketName`) shared with `wire-rest.md` 3.6; wrong or missing bucket always wins with `NoSuchBucket`.
2. **Versioning state is a sum type: `Unversioned | Enabled | Suspended`**, and each key holds a version chain whose members are `Object | DeleteMarker` with a `VersionId` that is either the literal `null` or a 32-character `[A-Za-z0-9._]` token (sections 8.1, 8.3). Build the chain from day one: `terraform destroy` with `force_destroy` calls `ListObjectVersions` even on unversioned buckets, and `DeleteObjects` addressing `VersionId` is common.
3. **Object record fields that must be stored per write:** bytes (opaque storage id, never the key, per the brief's traversal rule), size, `Last-Modified` truncated to seconds on the emulator clock, ETag string (MD5 hex, multipart `hex-N`, or random 128-bit hex for SSE-KMS/SSE-C), one stored full-object checksum (algorithm plus value, `CRC64NVME` by default) plus `ChecksumType`, system headers, lower-cased user metadata (2 KB cap), tags (10 max), storage class, SSE settings as a sum type (`S3Managed | Kms{keyArn, bucketKey, context} | CustomerKey`; there is no "none" because every object reports at least `AES256`) and website redirect. A PUT replaces all of it, tags included.
4. **Multipart upload record** carries everything final-object-affecting from `CreateMultipartUpload` (metadata, tags, SSE, storage class, checksum algorithm and type), the part table keyed by part number (size, MD5, per-part checksum) and an `uploadId` that is unguessable and URL-safe. Complete validates in this order: non-empty, strictly ascending, each listed part exists with the stated ETag (`InvalidPart`), each non-last part at least 5 MiB (`EntityTooSmall`), checksum mode and values; then atomically replace the key and delete the upload.

### Wire behavior to get exactly right

5. **Bucket naming and `CreateBucket`:** implement the table in section 3.2 literally, including the `us-east-1` special cases (`LocationConstraint` of `us-east-1` is an error there, empty or absent is fine, `GetBucketLocation` returns an empty element), `BucketAlreadyOwnedByYou` only outside `us-east-1` or with tags, `409 BucketAlreadyExists` across accounts. Accept an empty `<CreateBucketConfiguration/>` and `x-amz-acl: private` unconditionally (Terraform sends both). Per-region isolation is still the open decision from wire-rest.md item 11; this research adds no new constraint beyond: never emit `IllegalLocationConstraintException` outside `CreateBucket`.
6. **Serve S3 Control `ListTagsForResource`/`TagResource`/`UntagResource`** (item 6 of section 14.2), or Terraform's bucket tag reads fail on a host-name endpoint with an account id. The cheap alternative is to answer these with `405 MethodNotAllowed`, which makes the provider fall back to `GetBucketTagging` ([TF tags.go](https://github.com/hashicorp/terraform-provider-aws/blob/v6.68.0/internal/service/s3/tags.go#L172-L190)); that costs fidelity for no real saving. Document that IPv4-literal endpoints cannot resolve `<account>.<ip>` (PROBE E3) and that `localhost` or `skip_requesting_account_id` are the supported Terraform configurations.
7. **Terraform read-back fidelity** is the acceptance test: lifecycle `Get` must return structurally identical rules plus `x-amz-transition-default-minimum-object-size` (default `all_storage_classes_128K`); the 55 s per lifecycle apply is the provider's fixed polling and cannot be reduced by the server (section 4.2.8), so state this in user docs rather than chase it. Every Terraform-read subresource listed in the section 4.1 tables needs Put/Get/Delete with the recorded statuses (`204` for the policy, tagging, metrics-family Puts).
8. **ETag, ranges, conditionals:** unquoted ETag in event JSON and `GetObjectAttributes`, quoted elsewhere; `206`/`416` per section 5.9 including `ActualObjectSize`/`RangeRequested`; reads follow RFC 9110 order, copy-source failures are always `412`, conditional writes accept only `If-None-Match: *` and `If-Match: <etag>` alone and return `501 NotImplemented` with `Header` and `additionalMessage` otherwise (section 5.10). Evaluate conditional writes under the same per-key lock as the commit and surface `409 ConditionalRequestConflict` for lost races.
9. **Checksums are the largest fidelity surface.** Compute and store `CRC64NVME` when the client sends none and always return it with `x-amz-checksum-type: FULL_OBJECT`; return a checksum on GET/HEAD only with `x-amz-checksum-mode: ENABLED` and only when it describes the bytes sent (whole object or the requested part), or boto3 raises `FlexibleChecksumError` (section 5.8). Algorithms with stdlib support: CRC32, CRC32C, CRC64NVME (polynomial `0x9a6c9329ac4bc9b5`), SHA1, SHA256, SHA512, MD5. XXHASH64, XXHASH3, XXHASH128 need an in-repo implementation or an ADR to defer them (the standard-library-only rule); their client-side digest encoding is settled (big-endian, seed 0, section 6.1 and the vectors in [s3-checksum-residuals-and-record-backlog.md](s3-checksum-residuals-and-record-backlog.md)), so implement them rather than returning the unimplemented error; live-S3 acceptance of the header and trailer forms stays UNVERIFIED (record-backlog item R08).
10. **`aws-chunked` decoding is mandatory on plain HTTP** (JS SDK streamed PUTs, signed uploads from older SDKs): unsigned-trailer and signed variants per section 6.3, with `x-amz-decoded-content-length` checked against the decoded byte count and trailer checksum verified. Validate headers before reading the body when `Expect: 100-continue` is present. Property tests: encode/decode round-trip over arbitrary chunk sizes, trailer present or absent, chunk-signature chain against the DOC test vector.
11. **SSE-KMS touches the KMS service.** On PutObject, CopyObject, CreateMultipartUpload and GetObject of an SSE-KMS object, resolve the key (id, ARN or alias; default `aws/s3`) through the KMS package and return `KMS.NotFoundException`, `KMS.DisabledException` or `KMS.KMSInvalidStateException` as `400` with the messages in section 5.7. Report the full key ARN in `x-amz-server-side-encryption-aws-kms-key-id`. Whether the stored bytes are really encrypted is an implementation choice; the brief's KMS "real local cryptography" means a data-key envelope is available if wanted. The ETag of such objects is random hex, not MD5.
12. **Listing:** one shared pager for ListObjects v1/v2 and versions: byte-wise key order, `CommonPrefixes` counted against `max-keys`, opaque continuation tokens that round-trip any key (base64url of the last key plus a bit), `NextMarker` only with a delimiter, `encoding-type=url` on every key-bearing field with `%2B` for `+`, `400 InvalidArgument` for bad `encoding-type`/continuation token. Property test: concatenating pages equals one unpaginated listing for random keys, prefixes and delimiters.
13. **Metadata edge cases that bite in tests:** default content type `binary/octet-stream`; `x-amz-meta-*` lower-cased and RFC 2047 aware; 2 KB metadata cap enforced explicitly because Go's header limit is far larger; `HEAD` errors have no body; always exactly one `Date` header (JS SDK clock skew, section 1 item 7).
14. **Presigned URLs:** when signature validation is on, implement query-string SigV4 with `UNSIGNED-PAYLOAD`, path encoded once and not normalized, expiry 1 to 604,800 s judged on the emulator clock (skew and "not yet valid" on the wall clock, see the G4 correction in section 12 and [lambda-runtime-contract.md](lambda-runtime-contract.md) rows 9 and 10), and the three error shapes (`AccessDenied` expired, `AuthorizationQueryParametersError`, `SignatureDoesNotMatch` with debug elements). Share the canonicalization code with header-signed SigV4 (sigv4-checksums-endpoints.md owns the algorithm); presigned POST is out of the phase 1 list.
15. **Event notifications (should-have):** store the configuration with the recorded validation order (ARN parse, then destination existence, then permission check relaxed), send `s3:TestEvent` to SQS and SNS destinations when stored, deliver `Records` JSON with URL-encoded key, unquoted `eTag`, bucket-region `awsRegion` and a per-key increasing `sequencer`, one message per matching configuration, SNS subject `Amazon S3 Notification`, Lambda via asynchronous invoke. Deliver through the journal so the causal chain PutObject -> SQS -> Lambda is recorded, and on the emulator clock. The event carries `eventVersion` `2.1` compatible content; major-version compatibility is all clients check. (scope) Lifecycle execution and S3 Inventory/Replication are not needed for phase 1 and can return their stored configuration without acting on it, which should be documented as stored-only.
16. **Unimplemented surface fails loudly.** Everything not named above (Select, Restore, Object Lock enforcement, replication execution, analytics, website serving, POST object, directory buckets, SigV4A) returns `501 NotImplemented` in the S3 error format naming the operation. Terraform tolerates `501` for ACL and Object Lock puts and for the legacy inline attributes by design (section 4.2.11).

# Security

understudy is a development and test tool. It emulates AWS's APIs; it is not a security boundary. Its opt-in IAM enforcement exists for testing policies, not for protecting data. This page says what it does protect, what it deliberately does not, and how to report a vulnerability.

## Reporting a vulnerability

Report it privately through GitHub's private vulnerability reporting on this repository (the Security tab, "Report a vulnerability"). Do not open a public issue.

Include the understudy version or commit (`understudy version`), how understudy was started, the steps or a request that shows the problem, and what an attacker gains. The maintainer will acknowledge the report, work with you on a fix, and agree on a disclosure date. Before 1.0, only the latest release receives fixes: a fix lands on `main` and ships in the next release.

## What understudy protects

These are promises; a way around any of them is a vulnerability:

- **Loopback by default.** `serve` binds `127.0.0.1`. Listening on any other address on a host needs an admin token (`UNDERSTUDY_ADMIN_TOKEN`, at least 16 characters) for the admin API under `/_understudy/` and an explicit `--allow-unauthenticated-aws-api`. Inside a container with its own network, the published port is the control instead, and the image documents publishing it on `127.0.0.1` only.
- **Browsers and DNS rebinding.** A loopback listener answers only host names an outside DNS server cannot point at it. The AWS API answers a browser only from a page on a loopback origin with a port other than understudy's own, so a page from another site cannot drive it.
- **The web UI's session.** The admin API answers no call a web page makes, with one exception: the [web UI](docs/guide/ui.md)'s own calls. `serve` draws a new secret from `crypto/rand` at every start and prints it only in the fragment of the banner's `ui` URL (`/_understudy/ui/#s=<secret>`), which a browser sends neither to a server nor in a `Referer`. The page removes it from the address bar, keeps it in memory only (never in a cookie, `localStorage` or `sessionStorage`), and sends it in the `Understudy-UI-Session` header. A browser call passes only with that secret, marked `Sec-Fetch-Site: same-origin`, and with no `Origin` but understudy's own; any other page's call is refused. Another site cannot send the header without a CORS preflight, and the admin API approves none. The UI's files hold no secret; they are served with a Content-Security-Policy that runs only the UI's own scripts and forbids framing it, and with `Cross-Origin-Opener-Policy: same-origin`. The page writes what events and answers contain as text, never as markup.
- **Files.** S3 keys never become file paths: object bodies are stored by content hash under a rooted directory. Lambda zip extraction refuses non-local names and symlinks and caps sizes. Snapshot loading checks every archive entry name before writing.
- **Input limits.** Request bodies are capped per operation, and headers by Go's HTTP server limit. The XML decoder also bounds size and nesting depth, and the CBOR decoder nesting depth.
- **Secrets in logs.** Members AWS's models mark sensitive, session tokens and minted credentials are redacted from logs and from the journal, and request signatures are never logged. Secret values and KMS plaintext never appear in error messages.
- **Containers.** Function containers run with every capability dropped, `no-new-privileges`, memory and process limits, read-only code and no Docker socket. Every container understudy starts is labeled and removed when it stops, and leftovers of a crashed run are swept.
- **Outbound traffic only to hosts you list.** understudy sends no telemetry and makes no network calls at runtime except Docker image pulls and SNS `http` and `https` deliveries, which go only to the hosts `sns.httpDelivery.allow` lists, none by default. Whatever the list says, a delivery never reaches a name under an AWS domain (in the URL or anywhere in its CNAME chain), the instance metadata or ECS credentials addresses, a link-local, unspecified or multicast address, understudy's own listeners or the addresses a `tcp://` Docker Engine's host resolved to when `serve` started. That host is resolved only then: if it does not resolve (a CI `docker` service that starts later), `serve` logs a warning and cannot refuse the Engine, and an address it moves to later is not refused. The address is checked after the name resolves and the checked address is the one dialed, so DNS rebinding cannot redirect a delivery. Only a `localhost` or IP literal entry reaches loopback; a DNS-name entry never does, but may reach a private (RFC 1918 or IPv6 ULA) address, so that a receiver in Docker Compose or Kubernetes can be listed by name. A delivery uses no proxy, follows no redirect and always verifies TLS. understudy starts DynamoDB Local with that program's telemetry turned off.
- **Cryptography.** KMS uses AES-256-GCM with key material from `crypto/rand`, even when identifiers are seeded.
- **Sealing in this repository.** `scripts/sealed` must never let a command reach a non-loopback endpoint or read real AWS credentials.

## What understudy does not protect, by design

- **Anyone who can reach the port has full access.** Request signatures are parsed, not verified, by default; under `--sigv4 verify` every client may still sign with the public dummy pair `test`/`test`. IAM, resource and key policies are stored and deny nothing unless `--iam-enforce enforce` is set. Even then, calls signed with the dummy keys act as the account root, which needs no policy. Any client that reaches the AWS API can read every secret and object and run any container image as a Lambda function.
- **A listed host receives what any client sends.** Any client that reaches the AWS API can subscribe a host in `sns.httpDelivery.allow` and publish to it; with raw delivery and a `DeliveryPolicy` `requestPolicy` it chooses the POST's body and its `Content-Type`. List only receivers built to take that, and no DNS name you do not control.
- **The Docker socket is root on the host.** understudy needs it for Lambda and DynamoDB Local; so does anyone who controls understudy. Mounting it into the understudy container grants the same.
- **Function code is trusted.** Lambda functions run your code in containers on your Docker daemon. The Lambda Runtime API has no authentication in AWS's protocol; each environment gets its own port on the container network. On a Linux host with the default loopback listener, functions reach only the AWS API and the read-only health and clock endpoints. When understudy runs in a container, on Docker Desktop, or with `--listen` already binding the address functions reach (`0.0.0.0`, or the bridge gateway), function code calls the main listener instead, so it can also reach the rest of the admin API: it can reset state, change the clock or read the journal. On a host, such a `--listen` already requires the admin token, which closes the admin API to functions. In a container you can close that: start understudy with `UNDERSTUDY_ADMIN_TOKEN` and `--allow-unauthenticated-aws-api` (`serve` refuses the token alone, because it guards only the admin API and leaves the AWS API open to every peer) and give the token only to your own clients. Function code then gets `401` from every admin path, health and clock included. On Docker Desktop, `serve` refuses a token on the default loopback listener, so the exposure stays there. The alternative is to listen beyond loopback with the token and `--allow-unauthenticated-aws-api`: functions, which reach understudy through `host.docker.internal`, should then get `401` from the admin API, but every peer on your network can use the AWS API. That setup is untested on Docker Desktop. Run only function code you trust.
- **The UI secret keeps out web pages, not people.** On a loopback listener any local process can call the admin API without it, as the CLI does. Anyone who can read `serve`'s output (the terminal, a CI log, a log file) can open the UI with full admin access until `serve` restarts and draws a new secret. Beyond loopback the admin token still guards every admin call: the page asks for it once, when the server first answers `401`, and keeps it in memory only. Open the UI at `localhost` or `127.0.0.1`, through a port forward from a loopback port when the listener is remote or bound to one specific address. Opened at a name that is not loopback, such as the listener's network address, the page has not been tried in a browser: the edge refuses every request under `/_understudy/` whose `Origin` is not loopback, so the page's `POST`, `PUT` and `DELETE` calls are refused, and so is its module script if the browser sends an `Origin` for it, which would leave the page blank. Over plain HTTP at such a name a browser sends no `Sec-Fetch-*` headers, so the page's reads would pass as calls from a program, not through the session secret; the admin token still guards them.
- **Archives hold everything.** A snapshot, or the `--persist` directory, contains every stored secret and object together with the KMS key material that encrypts them. Treat them as secrets.
- **DynamoDB Local and the Lambda base images** are AWS's software, pulled at runtime under their own terms. understudy pins them by digest but does not audit them. DynamoDB Local is pulled on the first DynamoDB call, and understudy logs a one-line notice naming its licence when it first starts it: at `serve` when the image is already present, otherwise on that first call. Neither happens when the configuration sets `dynamodb.enabled` to `false`. understudy is not built to serve several users, and DynamoDB Local's licence does not allow running it as a hosted service for others.
